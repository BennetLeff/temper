## 1. Operating rules — violating these is expensive

These are not style preferences. Each one cost real time today, and three of
them were already documented in `AGENTS.md` before I walked into them.

### 1.1 DRC: use `_drc_api.run_drc()`, never bare `kicad-cli`

Raw `kicad-cli pcb drc` omits two things the wrapper supplies and documents:

* `--all-track-errors` — without it KiCad reports only a **subset** of each
  track's errors, and which subset varies between runs on a byte-identical
  board. With it, counts are stable and **rise** (clearance 337 → 499 in the
  wrapper's own recorded measurement) because the lower figure was a sample.
* a single-threaded worker env — with the default pool the count itself moves.

I ran the bare tool, saw `726 / 726 / 725` on an unchanged board, and dismissed
the jitter as small. It was the documented defect announcing itself.

**Check your number against a known one.** `main` measures **379 errors** through
the wrapper. 379 + 339 unconnected = 718, the figure this repo already records.
My three earlier baselines (755, 695, and a scratchpad 824) reproduced nothing.

### 1.2 A scratch board needs its whole project context

Copying `temper.kicad_pcb` and `temper.kicad_pro` to a scratch dir is **not**
enough. Without siblings it silently measures a different world:

| missing | effect |
|---|---|
| `pcb/temper.kicad_dru` | 33 KB of custom rules (`HV to LV`, `AC Mains to LV`) never run |
| `pcb/fp-lib-table` + `pcb/libs/` | every footprint fails resolution; `lib_footprint_issues` fires board-wide |

The two push the count in **opposite directions**, which is why a wrong baseline
still looked plausible. Prefer measuring **in place** (`git checkout main --
pcb/temper.kicad_pcb`, measure, restore) over building a scratch copy.

### 1.3 Rust: CI lints with `--all-features`

`cargo clippy --manifest-path X --all-targets -- -D warnings` without
`--all-features` reproduces a configuration **nobody ships**. `temper-design-bundle`
reports **46 dead-code errors** that way and **11** the correct way, because
`parse_kicad_pcb_impl` is `#[cfg(feature = "python")]` and an entire live call
chain beneath it reads as unreachable.

I nearly deleted 46 items as dead. What stopped it was a contradiction I could
not explain — clippy called `calculate_footprint_bounds` dead while line 1744
plainly called it. **Chase the contradiction; do not dismiss it.**

### 1.4 Some gates are environment-dependent — treat their verdict as local

`scripts/check_rust_coverage_illusions.py` reported `1 new, 5 stale` in the
morning and `2 new, 7 stale` hours later, **on unmodified `main` with no file
changed between**. The variable is which pyo3 extensions were built in the shared
venv, which changes what its reachability and symbol analysis can see.

A **shrink-only ledger cannot be maintained against a non-deterministic gate.**
Any attempt to true it up records one environment's snapshot. This is unfixed —
see §5.1.

### 1.5 The shared venv is evicted constantly

`ImportError: cannot import name 'write_types' from 'temper_io_types'` hit
**four times** today. It is a concurrent `uv sync` reverting the shared `.venv`,
not a code defect. `make extensions` fixes it (unset `CONDA_PREFIX` first — maturin
refuses when both it and `VIRTUAL_ENV` are set).

**Treat any ImportError here as suspect before treating it as a finding.** A
stale `.so` and a genuinely missing function are indistinguishable from the error
text alone. `hasattr()` after a fresh `maturin develop` is the discriminator.

### 1.6 Uncommitted work is not safe in this checkout

Mid-session, two verified test edits were **reverted by an external process** —
`git status` clean, both files back to original, no branch switch in my reflog.
60+ agent worktrees share this `.git`.

**Commit before you verify**, not after. It inverts the usual habit and is
correct here. `git stash` is blocked by a repo hook (shared stash stack); use a
patch file: `git diff > /tmp/p.diff`, switch, `git apply`.

### 1.7 Generated files are symptoms; fix the generator

**Four** generator-level defects today. In every case editing the `.rs` or `.yml`
alone would have been undone by the next generation run:

| generator | defect |
|---|---|
| `gen_wasm_test_registry.py` | wrong path for **nested** test modules |
| `oracle_freeze_specs/operating_point.py` | emitted `&[(f64)]` — unnecessary parens |
| `oracle_freeze_specs/slot_grid_validator.py`, `zone_aware_slot_generation.py` | complex frozen-fixture types |
| `oracle_freeze_specs/measure_closure.py`, `schema_validator.py` | `mod frozen_tests` missing attributes |

Also: `gen_wasm_test_registry.py --check` **defaults to `--crate temper-drc-rs`**.
A bare `--check` prints "up to date: 3283 tests across 34 modules" while
`temper-io-types` is broken. It answers a question you did not ask.

## 3. The board thread — what actually happened to C6 and K1

This is the part with engineering content rather than CI archaeology.

### 3.1 The "worst determinate mains shortfall" was never real

The published figure — `U1.2↔C6.2` at **4.7652 mm**, 0.0348 mm short of the
4.80 mm reinforced barrier — was measured against a **10 mm-pitch disc cap the
design does not specify.** `elec/`, the BOM, and `pcb/libs/` all call for a
22.5 mm-pitch film cap. Only the board disagreed.

With the specified part, C6 clears by **+3.2677 mm**.

### 3.2 The rotation was not cosmetic

At 22.5 mm pitch the pad moves 12.5 mm. Measured at all four rotations, worst
C6↔HV gap:

| rot | gap | vs 4.80 mm |
|---|---|---|
| 0 | 1.7900 | short 3.01 |
| **90** | **8.0677** | **clears +3.27** ← chosen |
| 180 | 5.7978 | clears +1.00, but breaks the 6.0 mm `ACMains` rule |
| 270 *(as-built)* | **0.0000** | **direct metallic contact with U2.1** |

**Swapping the footprint while keeping 270° puts C6 in metallic contact with a
mains net.** A naive resync of the drift gate's two lines does exactly that.

rot 180 has the *lowest total violation count* (721 vs 726) and is still wrong:
its violations include `AC Mains to LV` creepage of **6.3978 mm against 12.6
required**. rot 90's are entirely courtyard overlaps and silkscreen clips.
**Total count is the wrong objective when composition differs in severity.**

Cross-validated: at 180° the pad-geometry kernel puts C6.2 at board
`(44.49, 201.51)` measuring 5.7978 mm to C1.2 — the same position *and* distance
`kicad-cli` independently reports.

### 3.3 K1 cannot be placed — measured, not assumed

K1's old Omron contacts were **#250 Faston tabs with zero PCB copper** (datasheet
labels them "Tab Terminal" vs "PCB Terminal" for the coil). The Schrack
`RT33K012` — swapped in on 2026-08-13 because the Omron's coil↔contact gap is
**8.000 mm against the 12.6 mm PD3 target**, while the Schrack clears at 17.8 —
has **real THT contacts.**

Landing them at K1's existing site produces violations the phantom pads hid:

```
K1.3 [power_in.ntc-no] <-> R56.1 [+3V3]           creepage  5.0356 / 12.6
K1.3 <-> track [discharge.r_snub1-p2] on In3.Cu   clearance 0.6900 /  2.0
K1 <-> C7                                         courtyard overlap
```

**Revealed, not created.** A geometric sweep found **6 viable sites on the entire
board** (after correcting a filter that saw only 125 of 168 courtyards — 30 draw
theirs as `fp_line` polylines, 13 have none), all ~345 mm of wire from the nets
K1 must reach, and the best still measures worse under DRC. On a board with 4553
routed segments, a THT pad moved anywhere lands on existing copper.

**K1 needs place-and-reroute, not a move.** This is the top open engineering item.

### 3.4 R9 was overtaken, not answered

`docs/brainstorms/2026-07-29-...-requirements.md` R9 asks whether K1's contacts
reach the board by wire jumper or PCB copper. **The creepage part swap settled
it**: the Schrack has real THT contacts, so the answer is PCB copper and there
was never a wiring decision left to make. That also explains why
`power_in.ntc-no` and `w1_2` have **zero segments and zero vias** today — the
router cannot reach a relay whose board footprint still has phantom tabs.

Note: the 2026-08-14 work reporting `power_in.ntc-no` as `fully_connected=True`
verified it over **K1.13, a pad with no copper**, on a branch that never reached
main.

## 5. Known-unfixed, with evidence

### 5.1 `check_rust_coverage_illusions.py` is non-deterministic

Same commit, same files, different verdict hours apart (§1.4). The ledger edit
was reverted in `8c1beb5d3` rather than re-chased, because truing it up records
one environment's snapshot.

**Fix belongs upstream:** resolve reachability and Python-visible symbols from
source rather than from what happens to be importable, or declare the
environment as a pinned input — the way `_drc_api.run_drc()` pins
`--all-track-errors` and a single-threaded pool for exactly this reason.

### 5.2 `ORPHANED temper_placer.io.kicad_exporter` — undiagnosed

Appeared in run 32507532303 on #1432. Was **not** failing on `main`'s last run
and that branch does not touch the file. **I did not look.** Do not assume it is
collateral without checking.

### 5.3 `temper-rust-router`'s wasm registry is stale on `main`

Verified by running `main`'s **own copy** of the generator. Regenerating it is
**not safe**: the generator wants to widen a `#[cfg(test)] mod
frozen_terminal_tree_tests` into a `wasm-registry` module, taking that crate
from **0 clippy errors to 13**. Left deliberately untripped.

### 5.4 `tests/io/test_dsn_pbt.py` cannot be collected

Imports `tests.io._dsn_py_oracle`, deleted by `11e0fbf6c` (#1427, "retire oracle
batch 3") — which is a recent HEAD of `main`. Interrupts collection for the whole
`tests/io/` directory.

### 5.5 Six pre-existing failures in `tests/io/test_netclass_loader.py`

From the safety-figure work: one asserts an `IEC 60335-1` citation against a
field that now reads `UNSOURCED legacy 6.0mm (debunked 'Table 16 ...' citation)`;
another wants `('FinePitch', 'GateDriveSELV')` to match the `GateDriveHV` half of
the split.

### 5.6 `temper-design-bundle`'s test binary will not run locally

`error while loading shared libraries: libpython3.9.so.1.0` against a 3.12 venv.
Does not affect the Clippy step, which compiles test targets without running
them.

### 5.7 The 4 "tautological assertion" findings are likely false positives

`assert prod.nets is prod.nets` is flagged as "always true". `nets` is a
**`getset_descriptor`** (pyo3-backed), so `X is X` genuinely distinguishes
"returns the stored object" from "returns a copy" — which is what makes the very
next line, `bus.nets.append(x)`, persist. **I verified one** of the four.
