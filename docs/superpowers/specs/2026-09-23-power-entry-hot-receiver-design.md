# Power-entry HOT receiver and retained shutdown design

Status: architecture specification for review, 2026-09-23. This does not authorize a mains build, claim a completed schematic, or select an MCU part.

## Decision and boundary

Develop one integrated power-entry authorization candidate with a small HOT-side receiver MCU. Keep fault detection, retained fault inhibit, and gate disable in HOT hardware. The MCU owns command identity and sequencing; it cannot make a stopped power stage run by an ordinary START command after a captured fault. The SELV ESP32-S3 owns the user interface and creates a fresh start intent only after observing a released button followed by a new press in the new session.

This work attaches to the 54-component passive-rectifier baseline identified in `zapote/power-entry/passive-reva/protection/ARCHITECTURE-REDUCTION.md`. It covers PFC gate authorization and the related stop/restart path. F1/F2 interruption, capacitor energy, cooling, inverter safety, insulation, and the rest of the appliance retain their own acceptance work. The design follows the reduction decision: local hardware shutdown and fresh arm belong in a separate protection function; precharge, startup deadline, and downstream load sequencing belong to system control with explicit interfaces.

### Alternatives considered

| Approach | Benefit | Decisive unresolved cost |
| --- | --- | --- |
| HOT receiver MCU plus hardware fault memory (selected development path) | Explicit session and single-use START semantics; restart sequencing stays legible | MCU firmware, persistent session identity, isolation channels, reset behavior, and physical qualification are still needed |
| ESP-only source plus hardware memory | Removes a HOT processor | Requires an implemented, bounded GPIO/queue/reset contract and a hardware handshake that rejects delayed old revalidation and ARM edges; Rev37 does not prove either |
| Entirely discrete handshake | Avoids receiver firmware | Requires more stateful logic and a proof that old edges cannot clear a fault or create a new session; no such circuit exists |

This selection is for the next design experiment, not proof that the other approaches are impossible. Rev35 and Rev37 are different-scope connectivity fixtures; their component counts are not a reliability comparison. The ATmega328P in Rev35 is not the selected production part. Microchip currently marks it not recommended for new designs. The bounded-reset contract below is selected for this implementation candidate; its allowable duration and electrical implementation remain unqualified.

## Safety invariants

1. A qualified latched trip removes PFC gate permission through hardware, independently of ESP scheduling and HOT receiver firmware. Recovery of the detector output does not restore permission.
2. START can set RUN only for the single current, outstanding, unexpired intent in the current session. START cannot load or repair the retained HOT fault memory. A duplicate, expired, cancelled, or prior-session message cannot start the PFC.
3. Physical HOT PERMIT low directly clears RUN. Once PERMIT has been observed high in a session, its subsequent loss also invalidates that session. Reconnection alone cannot restore either state. The source must observe physical disarm before it may seek a new session.
4. A new session requires a physical PERMIT-low observation *after* the invalidating event, healthy HOT inputs, RUN held low, and one controlled revalidation operation. A new user press after that session is published is required for START.
5. Loss of a required rail, broken isolator path, missing required execution, or unpowered logic leaves the gate path off within a separately specified response bound. A valid logic level in an unpowered or partly powered device is not assumed.
6. A qualified trip during preparation cancels that attempt even when `HOT_SESSION_OK` is already low. A fault arriving at revalidation or immediately before START wins. Once a session is published, neither receiver firmware nor an old command may reload the HOT fault memory inside that session.

These invariants assume the source does not invent user presses and the local command link is protected against accidental corruption, not an active adversary. A HOT MCU cannot independently witness a UI button connected only to the ESP. Fault containment claims apply only to enumerated reset, execution-loss, interconnect, and output-pin failure cases with identified detection and inhibition paths. A watchdog that sees timely WDI edges does not detect arbitrary incorrect firmware execution.

## Circuit partition and signal ownership

```text
SELV ESP/UI -- command + maintained PERMIT --> isolation --> HOT receiver MCU
             <-- response ------------------- isolation <-- HOT receiver MCU
             <-- physical PERMIT readback --- isolation <-- HOT PERMIT node
             <-- retained HOT validity ------ isolation <-- HOT fault memory

HOT detector/rail/permit/watchdog trips + RECEIVER_ABORT_N low
    --> retained HOT_SESSION_OK clear + HOT_RUN clear
HOT_SESSION_OK + HOT_RUN + physical PERMIT + rail/driver-valid
    --> local default-off gate-driver permission --> UCC27624 ENA --> STW gate
```

`HOT_SESSION_OK` is the canonical memory of a captured, session-invalidating HOT event. The proposed implementation class is an HCS74-style D flip-flop with D tied high, asynchronous `/CLR` driven by the qualified trip/POR network, `/PRE` held inactive, and a single controlled revalidation clock. Its Q is low after a trip. This is a topology candidate, not a pin-complete electrical design: clear pulse width, POR, recovery/removal, logic fan-in, and rail-ramp behavior must be proven against the selected devices. Do not assert asynchronous preset and clear together as a substitute for reset dominance.

`HOT_RUN` is separate retained state. Its clear path includes `HOT_SESSION_OK` low, physical PERMIT low, and faults that demand immediate gate inhibition. A retained `PERMIT_SEEN_IN_SESSION` bit is set by the first qualified physical PERMIT high after preparation. Only `(PERMIT_SEEN_IN_SESSION AND NOT physical PERMIT)` is a PERMIT-loss trip to `HOT_SESSION_OK`. Keep the seen bit asserted through that trip until the controlled next preparation, or its feedback could release the clear condition prematurely. Normal PERMIT low before the first high must not hold session memory in clear, since that would deadlock preparation. A fast direct inhibit may parallel the latch output, but every condition classified as requiring a new user session must also be captured in retained memory. Intentionally recoverable switching-cycle limits must be classified separately; they must not accidentally masquerade as session-invalidating trips.

The source has a separate retained `SOURCE_PERMIT_READBACK_SEEN` condition. Normal physical readback low before the first PERMIT assertion does not block source preparation. The first qualified readback high sets this memory; a subsequent readback low asynchronously clears the source PERMIT latch and remains a loss condition until controlled source preparation. In deliberate preparation, the source resets its seen memory only while its physical latch Q and HOT PERMIT readback have both been observed low, its permit-set output is held inactive, and receiver preparation has supplied the matching challenge. Source health loss may independently clear the seen memory while holding the source latch clear. Clearing the seen bit cannot itself raise PERMIT. Release of the source clear path and a later fresh permit-set operation require the current transaction's health and READY checks. The joined circuit must prove the readback pulse and reset/clear overlap electrically; this is a behavioral contract, not credit for Rev37's unjoined fixture.

The receiver owns an explicit active-low `RECEIVER_ABORT_N` hardware output. An accepted STOP, session-invalidating decoder error, explicit receiver abort, or receiver boot/reset recovery asserts it to clear `HOT_SESSION_OK` and `HOT_RUN` and to inhibit the gate path. Its default state while the receiver is reset, unpowered, or its pin is high impedance must be asserted by local hardware. The MCU may release it only after boot and health qualification; merely stopping RUN-set pulses does not clear retained RUN. The actual output default, pulse duration, rail sequence, and clear fan-in are mandatory circuit checks. If a specific execution-loss case relies on watchdog expiry instead, the plan must identify that case, its maximum response bound, and the watchdog output's physical clear path. STOP in READY before PERMIT has ever gone high must still assert receiver abort; an already-low PERMIT cannot convey it.

The revalidation clock requires a retained `DISARM_SEEN_AFTER_TRIP` condition derived from the *physical* HOT PERMIT node, fault-free rails, RUN-low observation, a matching source disarm acknowledgement, and a single-use preparation authorization. `DISARM_SEEN_AFTER_TRIP` must be cleared by a new trip and set only after PERMIT is seen low following that trip. A wire break can satisfy the physical-low condition; it does not by itself authorize revalidation. Preparation may begin with the historical `PERMIT_SEEN_IN_SESSION AND NOT physical PERMIT` loss condition asserted. Active external detector and rail faults may not be masked to permit preparation.

From PREPARE_CHALLENGE publication through READY publication, every newly occurring qualified external trip, STOP, or receiver abort must set an independently observable, retained preparation-abort condition, even if `HOT_SESSION_OK` is already low. The already-retained historical PERMIT-loss level and the receiver abort level held through initial lockout are not new events; neither can permanently prevent preparation. A new trip discards the pending identifier and acknowledgement. If a rail collapse removes the abort memory's supply, POR must instead discard the pending session and force a new attempt. Recovery requires a newly allocated identifier and matching disarm acknowledgement; the abort memory may be cleared only in that new controlled preparation while RUN and physical PERMIT are low and external faults are inactive. Restored detector health or continued PERMIT low cannot resume the old attempt. The effective revalidation clock must be a consumed, one-shot operation. A held-high or previously issued request cannot create a rising clock edge when eligibility recovers; directly ANDing a held request with eligibility is insufficient. Clear-release, setup, and simultaneous trip/clock cases must be proved against the selected flip-flop. The exact latch, clock-generation, and cancellation realization is an electrical design task, not an assumed property of this block diagram.

The reverse path needs three distinct meanings: receiver protocol response, physical HOT PERMIT readback, and retained HOT validity. A raw rail-health bit cannot replace retained validity, and a PERMIT-dependent health bit causes startup deadlock if required before PERMIT can rise. Rev35's single reverse ISO7741F channel is therefore insufficient for these independent functions as currently allocated; the next joined schematic must allocate and audit the added isolated channels. No direct conductive connection crosses the SELV/HOT boundary.

At UCC27624, ENA receives an actively driven permission with a local default-low network sized from worst-case input threshold, internal pull-up, output leakage, and rail sequence. A floating ENA is enabled by the part's internal pull-up. Driver supply present while logic supply is absent must leave ENA low and the loaded STW gate off. Driver disable propagation is only one term in the detector-to-current-cessation budget. The direct-drive baseline, Rev35 control candidate, and proposed driver must be joined into one source/native schematic before claiming the path exists.

## Session transaction

1. **Trip, STOP, or abort.** An external qualified trip clears `HOT_SESSION_OK` and `HOT_RUN` in hardware. An accepted STOP, receiver-detected invalidating error, or receiver reset asserts `RECEIVER_ABORT_N` low to perform the same physical clear, including when the system is only READY and PERMIT has never risen. The receiver discards the session and pending intents. Source hardware clears its permit latch on retained HOT invalid feedback, established physical PERMIT readback loss, or source-health loss. Software state change alone is not a clear action; recovered detector output does not undo the clear.
2. **Prove disarm.** The source requests PERMIT low and observes both its local latch output and the physical HOT-side PERMIT readback low. HOT hardware records physical PERMIT low after the invalidating event. A missing readback, partial power, or timeout stays locked out.
3. **Prepare without starting.** RUN stays low. Active external detector and rail conditions must permit preparation; the historical retained PERMIT-loss condition may still be asserted. The receiver durably allocates a session identifier that cannot repeat after receiver reset or power loss, then sends PREPARE_CHALLENGE(session) while `HOT_SESSION_OK` remains low. The source replies DISARM_ACK(session) only after step 2 and controlled reset of its source-side readback-seen memory with source Q held low. The receiver accepts the acknowledgement only for its pending identifier and while physical HOT PERMIT is still low. It then clears the historical HOT `PERMIT_SEEN_IN_SESSION` condition while Q/RUN remain low, releases its abort output only under qualified conditions, and checks that every required asynchronous clear is inactive. Only then may it consume one revalidation authorization, check retained validity feedback, and publish READY(session). An active detector or rail fault cannot be masked during this sequence. A new qualified trip at any point cancels the attempt, even if Q was already low; a later attempt requires a new identifier and DISARM_ACK.
4. **Create fresh intent.** After receiving READY for the new session, the ESP observes button release and a later press. It sets its source PERMIT latch, waits for both local and physical HOT PERMIT-high readbacks, then sends REQUEST(session, intent). The receiver replies ACK(session, intent). A held press, prior queued request, or old intent is rejected. Loss of either readback aborts this transaction.
5. **Start once.** The ESP sends START for the matching outstanding session and intent. At the point of the physical RUN-set operation, the receiver rechecks session, intent, expiry, and independent hardware conditions. It consumes the authorization once. Further, cancelled, or expired START frames cannot create another RUN transition.

The receiver owns a monotonic preparation deadline beginning when it publishes PREPARE_CHALLENGE and ending at READY publication. It owns a separate monotonic START deadline beginning when it accepts REQUEST and ending at the physical RUN-set operation. The source owns corresponding response deadlines beginning at challenge receipt and its own REQUEST transmission. Timeout, cancellation, supersession, STOP, or any invalidating event permanently discards the associated identifier/intent; a later frame cannot revive it. On an unsuccessful start-transaction timeout the source drops PERMIT and the receiver rejects START even if a matching frame was queued earlier. The plan must assign maximum durations from the hazards and communication envelope, including the maximum queue-to-pin time. Healthy ordinary execution or repeated traffic does not extend an accepted intent's fixed START deadline.

The receiver's session identity must be committed durably before a challenge is published. The implemented storage scheme must survive interrupted writes, reject ambiguous/corrupt state, and fail closed at counter exhaustion. CRC/framing checks detect accidental message corruption; they do not provide freshness. The receiver must reject prior identifiers after its own reset. The source must discard pending intents on its reset and must not attach an old intent to a newly published session. Rev13's model is a logical starting point, not a wire decoder or persistence implementation.

Watchdog service and communication liveness depend on state. Local execution progress and fresh end-to-end traffic are distinct evidence; the implementation plan must assign each watchdog's WDI owner, communication timer owner, allowed feed conditions, and physical timeout trip in every state:

| State | Required progress and fail-off rule |
| --- | --- |
| Boot/disarmed | Source WDI is withheld until physical source Q and HOT PERMIT-low disarm are observed. Monitored local safety cycles may then restore watchdog health without READY or RUN. Receiver stays physically aborted through boot qualification. |
| Fault lockout | No RUN permission; local monitoring may continue, but stale or repeated traffic cannot qualify a new session. Preparation requires a new identifier and disarm acknowledgement. |
| Preparation | Both endpoints must make fresh local safety progress and fresh bidirectional challenge/acknowledgement progress before the fixed preparation deadline. Loss cancels the attempt and trips the named hardware path. |
| READY while waiting for a person | RUN remains low. Independent local safety work and fresh numbered bidirectional liveness traffic may continue; a held button or repeated frame cannot create intent. Missing required progress invalidates the session. |
| REQUEST/ACK/START | The fixed START deadline runs regardless of watchdog service. Missing local or fresh communication progress aborts; timely heartbeat cannot keep an expired START valid. |
| RUNNING | Both local safety work and fresh bidirectional communication progress remain required. Loss triggers the identified source/HOT clear or watchdog path within its specified bound. |

Neither watchdog may be disabled merely to make its output appear healthy; TPS3431 WDO can be high while its watchdog is disabled. A watchdog detects missing qualifying WDI edges, not arbitrary wrong code that continues to feed it. The plan must separate local execution loss from link loss and show which of these hardware signals actually clears `HOT_SESSION_OK`, `HOT_RUN`, and the source permit latch.

## Reset and timing contract

The ESP32-S3 can perform a CPU-only reset without resetting most peripherals. Therefore an ESP boot routine setting GPIO low is insufficient evidence that the pins were low throughout reset. On every boot, source policy discards pending intent, stops software-owned WDI edges, requests outputs low, and waits for physical source-latch and HOT PERMIT-low readbacks before any new session. GPIO pulse generation must have one software owner, no DMA/timer pulse source, no surviving deferred write queue, and an explicit maximum sample-to-pin-write interval.

An MCU receiver cannot instantly observe an ESP CPU reset that leaves external signals unchanged. The selected **candidate** contract therefore permits one genuinely authorized START already committed to transmission before an unexpected CPU-only reset to produce at most one RUN transition, provided its current session and fixed command deadline remain valid and no independent hardware trip, physical PERMIT loss, or other invalidation has occurred. Rebooted source code may neither generate nor retransmit that old START. START acceptance cannot restart or extend the source-execution watchdog deadline. The same reset-to-shutdown bound applies to an already-running PFC and one that begins running during reset detection; starting does not earn another watchdog interval. After reset, source initialization invalidates external authorization and establishes physical disarm before watchdog service capable of preserving permission resumes. A later start requires a new session and fresh user intent. A deliberate software restart must first request disarm and observe physical acknowledgement, before invoking restart.

This is authorization for a bounded-reset **engineering candidate**, not numerical acceptance of the interval or a protected-operation claim. Its worst-case reset-to-off time is post-reset WDI feed tail plus maximum watchdog timeout at selected component corners plus the complete watchdog-trip-to-sustained-switch-current-cessation path. Any possible unbounded post-reset WDI feed makes the candidate fail. The implementation must independently derive an allowable time for both first-start and already-running conditions and prove the candidate worst case plus margin is no greater than the smaller allowable time. If it cannot, revise the watchdog, protection, or reset architecture; do not relax the allowable time to fit the circuit. Rev35/37 establish neither side of this inequality.

Each session-invalidating fault class needs a named electrical producer, polarity, guaranteed pulse/level at the receiving latch, and response-time limit. A fault shorter than a detector's or latch's guaranteed capture time is outside its claim. Rev37's TPS3890 MR requires at least 1 µs low to guarantee RESET; it must not be used as the only memory for shorter qualified faults. Rail collapse must default invalid when logic returns. For each interruptible fault class, derive allowable response time independently from its electrical/system hazard, operating envelope, tolerances, and derated limits. Separately bound implementation time through detection, qualification, isolation where applicable, retained clear, driver disable, loaded gate, and sustained switch-current cessation. Require implementation worst case plus margin no greater than allowable time. Faults a healthy gate cannot interrupt need their own containment/interruption path. Gate-off and switch-current cessation do not mean the bus is de-energized or every fault current has ceased.

No numerical allowable fault-to-current-cessation limits are accepted here. The first engineering package must identify the missing parameters, retrieve available circuit/component evidence, and produce calculations and physical test requirements to close each gap. Parameterized protocol tests, reset-driver work, circuit design, and timing analysis may proceed with gaps explicit. Numerical timing acceptance and physical qualification remain mandatory before protected-operation or mains-build claims. No limit is assigned by whichever parts happen to be selected.

## Implementation and verification boundary

The next implementation should be one joined Atopile candidate with exact source/receiver, physical readbacks, retained fault memory, actual F2/PFC detector outputs, AUX/logic rail supervisors, and UCC27624/STW path. It needs an exact-pin netlist audit with deliberate miswire mutations, a source-to-native KiCad parity review, and a complete component/isolator channel census. Rev35's 226 instances and Rev37's 30 instances must not be added or compared as whole-system totals. Keep the 54-part canonical baseline unchanged until the joined candidate is independently accepted.

The first engineering package is a state-transition and fault-response table plus a per-fault timing analysis. Assign every invalidating event an electrical clear/inhibit action and either a derived allowable/implementation bound or an explicit missing-input status. Include normal STOP in READY, STOP in RUNNING, receiver reboot while latches stay powered, source reboot with retained outputs, PERMIT loss, short trips during preparation, each detector/rail fault, watchdog expiry, and expired transactions. Work on the receiver decoder, durable session identity, watchdog feed ownership, actual ESP GPIO driver, and joined circuit may proceed under the selected candidate contract while numerical limits are derived; protocol model tests alone are never physical acceptance.

Tests must inject: normal start followed by PERMIT loss and a legitimate new preparation without masking an active external fault; receiver STOP in READY before PERMIT has ever risen; receiver abort/reset while RUN and PERMIT remain high; short qualified trip followed by delayed old frames; trips before, during, and immediately after the effective revalidation edge with a held-high request and `HOT_SESSION_OK` already low; a matching START delayed beyond its deadline while ordinary traffic stays healthy; receiver reset and interrupted counter write; ESP CPU-only reset with retained outputs and an in-flight START; stalled MCU; logic-rail loss with driver supply present; isolator partial-power states; and all defined fault classes. These tests must check hardware permission and pending-session disposition, not merely the receiver's final software state.

The first physical campaign is low-voltage fault injection on an assembled prototype with captures of detector output, retained latch, PERMIT, driver EN, loaded gate and switch current. The existing `interface-integration-24/bench-capture.md` is a protocol starting point. A mains build decision additionally requires reviewed schematic, BOM, native board, insulation/creepage, ERC/DRC, thermal and fuse/interconnect qualification. The passive milestone remains NOT MET until its separate requirements close.
