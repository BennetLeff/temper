# A rule that matches nothing reads as coverage

## Context

Two DRC rules generated by `scripts/generate_kicad_dru.py` — Rule 5 ("HV
internal same footprint") and Rule 7 ("Power internal same footprint") —
carried the condition `A.insideCourtyard(B.Reference)`, intended to test
whether two pads on the same net class belong to the same physical
footprint instance. It never binds. `docs/evidence/2026-07-28-drc-courtyard-
condition-fix.md` root-caused this by fetching KiCad's own source —
`pcbnew/pcbexpr_functions.cpp` at release tags `10.0.4` and `10.0.5`, via
the official GitHub mirror — and reading `intersectsCourtyardFunc`
directly: `insideCourtyard`'s argument is evaluated as a **selector
string** matched with `wxString::Matches()`, and the function has a special
case only for the literal tokens `'A'`/`'B'` (which require the item under
test itself to be a `FOOTPRINT`, useless here since the rules match `Pad`
vs. `Pad`). **There is no code path that evaluates a dynamic property
expression like `B.Reference` and uses its computed value as the
selector.** The string is parsed, resolves correctly in isolation, and is
then simply never consulted.

A structurally identical, independently-discovered defect sits in Rule 1
("Same footprint pads"): `A.Footprint == B.Footprint`. `pcbnew/pad.cpp` and
`pcbnew/footprint.cpp`'s `PROPERTY_MANAGER::AddProperty(...)` calls
register `"Reference"`, `"Library Link"`, `"Pad Number"` — **no property
named `"Footprint"` exists anywhere in either class.** The comparison
resolves both sides to an undefined value and never matches. Two rules,
two different reasons (a function-argument evaluation gap; a
never-registered property name), the same observable effect: **the
condition parses, looks like it encodes the intended constraint, and
matches nothing, on any board, regardless of the constraint's own
threshold value.**

**The reusable technique that found this, and confirmed no other rule
shared it:** override every rule's own condition (unchanged) with an
absurdly generous threshold — 999mm for a clearance rule — and run the real
board through it. A rule that matches *anything* produces an unmissable
violation at 999mm; a rule that matches nothing produces exactly zero,
regardless of how permissive or strict its real value is. Running this
against all 12 pairwise-condition rules on the real 168-footprint,
2482-copper-item board (13 checks, ~20s each) separated them cleanly:
`NetClass`/`Type`-only conditions (rules 2–4, 6, 8–10) all bind correctly
where their net classification exists (rule 4 alone produced 498 matches at
999mm); every rule built on `A.Footprint` or `insideCourtyard(B.Reference)`
(rules 1, 1a, 5, 7) produced zero, on every threshold, board-wide.

**The audit also caught its own predecessor's mistaken conclusion.** A
prior investigation into the same rule pair had reasoned that "Rule 1 masks
Rule 5's pad pair by being more permissive" — a plausible story, since
Rule 1's threshold (0.1mm) is looser than Rule 5's. This session tested
that claim directly at 999mm and found Rule 1's condition produces **zero
matches**, not "matches, trivially." Rule 1 isn't out-permissioning Rule
5 — neither rule binds on any pad pair, for two independent reasons. The
practical bottom line (this board's same-footprint HV pad pairs are
unprotected) was already correctly flagged; the *mechanism* attributed to
it was wrong until re-tested at an absurd threshold instead of inferred
from the two rules' relative strictness.

## The pattern

**A condition that fails to bind is invisible in exactly the way a
`continue-on-error` flag or an `all([])` reduction is invisible** — it
produces a rule that exists in the generated file, parses without error,
carries a real and specific numeric threshold, and is backed by a
generator that has its own passing unit tests. Nothing about reading the
rule's text distinguishes "this will fire when it should" from "this can
never fire, for a reason buried three layers into the expression engine's
own dispatch order." `docs/solutions/best-practices/gate-neutering-
mechanisms-2026-07-26.md` catalogs four such mechanisms
(`continue-on-error`, a default-off flag with no caller, an uninvoked code
path, vacuous `all([])`) — this is a fifth, distinct from all four: **the
rule is wired in, invoked, and its own aggregation is sound; the defect is
entirely inside the expression engine's evaluation of one specific
argument shape**, a class of failure none of the first four would catch,
because all four assume the condition itself is semantically correct and
ask only whether it runs.

Verifying a fix by re-running it on the one board it was written for is not
enough when that board's own violation count for the rule in question is
zero either way: 0 → 0 is consistent with "the fix works, and this board
happens to have no matching pad pairs" and with "the fix didn't work."
Distinguishing them needs a fixture engineered to match (§3a of the
courtyard-fix doc: an isolated 2-pad, 1.95mm-gap fixture, base condition
0→0, fixed condition 0→1 at exactly the threshold crossing) — the real
board alone cannot tell the two apart when the answer is already zero.

## Guidance

1. **When a generated rule's condition uses a dynamic property lookup
   (`A.SomeProperty`) as the argument to a function, rather than a literal
   value, verify against the engine's own source or a minimal fixture that
   the function actually consults the argument's *computed value* — not
   just that the expression parses and the property itself resolves.**
   `B.Reference` correctly evaluates to a reference-designator string;
   whether `insideCourtyard` ever looks at that string is a separate
   question the parse cannot answer.
2. **Before relying on any property name in a rule condition, confirm it is
   registered by the engine** (here, `PROPERTY_MANAGER::AddProperty` in the
   relevant source files) rather than assuming a plausible-sounding name
   like `Footprint` exists because `Reference` and `Value` do.
3. **Audit an entire rule corpus at an absurd, unmissable threshold before
   trusting any one rule's real-world silence.** 999mm on a clearance rule
   turns "zero violations" into a clean binary: either the rule matches
   nothing (a condition defect) or the board genuinely has zero instances
   of the geometry the rule is looking for (not a defect). This is cheap —
   13 rules, ~20s each — relative to trusting a rule's silence at its
   intended threshold, which cannot distinguish the two cases.
4. **When two rules could plausibly interact (one masking the other), test
   the interaction directly at an absurd threshold rather than inferring it
   from which one's stated value is looser.** A rule with a permissive
   threshold and a rule with a broken condition produce the identical
   symptom (zero enforcement); only re-testing each condition in isolation
   tells you which one is actually true.
5. **A fail-before/pass-after pair on the real board is insufficient
   verification when the real board's own answer is 0 → 0.** Build an
   isolated fixture sized to make the fix's effect observable (a pad pair
   just inside vs. just outside the corrected threshold), and use the
   generator's own real emitted condition string in the regression test —
   not a hand-copied substitute — so a regression that silently
   reintroduces the broken form is caught structurally.

## Why This Matters

Two of the four rules this project's own DRC generator emits for
same-footprint high-voltage and power clearance — the exact class of check
whose purpose is catching an IGBT's own coil-to-contact-style internal
pads sitting too close together — matched nothing, on any board, at any
threshold, since the moment they were written. The rule existed in the
generated `.dru` file, referenced a real clause
(`HIGH_VOLTAGE_CLEARANCE_SPEC.md` §6.4), carried a specific, defensible
number (2.0mm reinforced clearance), and every review that read the rule's
text rather than tested its condition would have every reason to believe
it was enforcing something. It was enforcing nothing, for two independent
reasons, and — even after the condition was fixed — the board's actual
TO-247 IGBT pair (`U5`, `U6`) still is not protected by the corrected rule
today, because those same two components' pins are *also* not classified
into `HighVoltage` at all (the same rename-orphaning drift covered in
`docs/solutions/best-practices/rename-orphans-derived-keys-2026-07-28.md`).
A corrected condition and a correct classification are both necessary, and
finding one gap doesn't confirm the absence of the other.

## When to Apply

- Auditing any generated rule/lint/DRC corpus for silent
  non-enforcement — run every rule's own condition at an absurd threshold
  against real data and treat zero matches as a question, not a clean bill
  of health.
- Before trusting a rule condition that passes a dynamic property
  (`A.SomeField`) as a function argument — confirm the function consults
  the argument's computed value, not just that the property resolves.
- Before relying on a property name (`Footprint`, or any field not
  confirmed in the engine's own registration code) in a comparison —
  verify it is a real, registered property.
- When two rules could interact (one seemingly masking another) — test the
  interaction directly rather than inferring it from stated threshold
  values.
- When a fix's fail-before/pass-after check on the real board reports 0 →
  0 — build an isolated fixture engineered to distinguish "still broken"
  from "correctly finding nothing here" before calling the fix verified.

## Examples

```cpp
// pcbnew/pcbexpr_functions.cpp -- what insideCourtyard's argument actually does
RegisterFunc( wxT( "intersectsCourtyard('x')" ), intersectsCourtyardFunc, true );
// arg->AsString() is used as a SELECTOR matched via wxString::Matches() --
// there is no path that treats it as a resolved property VALUE from the
// other matched item. A.insideCourtyard(B.Reference) parses, B.Reference
// correctly computes a real reference string, and it is never consulted.
```

```
# The audit technique: override every rule's own condition at 999mm,
# run the real board, count matches per rule (13 rules, real 168-footprint
# board, ~20s each):

Rule 4  "HV to LV"                A.NetClass=='HighVoltage' && ...   -> 498 matches
Rule 6  "GateDrive near HV"        A.NetClass=='GateDrive' && ...     -> 115 matches
Rule 10 "Default routing"          A.Type=='Track' || ...             ->  499 matches
Rule 5  "HV internal same fp"      A.insideCourtyard(B.Reference)     ->    0 matches
Rule 7  "Power internal same fp"   A.insideCourtyard(B.Reference)     ->    0 matches
Rule 1  "Same footprint pads"      A.Footprint == B.Footprint         ->    0 matches
Rule 1a "Fine pitch IC pads"       A.Footprint == B.Footprint         ->    0 matches
#        ^ NetClass/Type conditions all bind; Footprint/insideCourtyard don't, ever.
```

```
# WRONG fix and shape rejected: patching the argument, keeping the function
A.insideCourtyard(B.Reference)   # never binds regardless of argument shape

# RIGHT: drop the courtyard-geometry indirection for the thing actually meant
A.Reference == B.Reference       # confirmed to bind: 0/0 (base) -> 0/1 (fixed)
                                  # at the 1.5mm -> 2.0mm threshold crossing
                                  # a 1.95mm-gap fixture, in isolation
```
