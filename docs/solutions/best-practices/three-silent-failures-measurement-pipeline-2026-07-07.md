# Three silent failures in a measurement pipeline

## Context

The netclass-aware clearance experiment required kicad-cli DRC as the truth gate. Three separate issues prevented kicad-cli 9.0.7 from loading either the input board or the generated output PCB. Each failure was silent — kicad-cli exits code 3 with "Failed to load board" and produces no JSON output, so a naive DRC wrapper returns 0 errors.

## The Three Fixes

### 1. Board format: KiCad 5 → KiCad 9

The temper PCB used KiCad-5-era syntax rejected by kicad-cli 9.0.7:

| Issue | Before (KiCad 5) | After (KiCad 9) |
|-------|-----------------|-----------------|
| Bare properties | `(property "Reference" "R1")` | `(property "Reference" "R1" (at 0 0 0) (layer "F.SilkS") (effects (font (size 1 1) (thickness 0.15))) hide)` |
| gr_rect width | `(gr_rect ... (layer "Edge.Cuts") (width 0.15))` | `(gr_rect ... (layer "Edge.Cuts") (stroke (width 0.15)))` |
| Semicolon comments | `; Net definitions` | Remove — bare `;` lines break the parser |

### 2. net_class s-expression: missing description string

The generated `(net_class ...)` form was missing the description string required by KiCad 9:

```python
# WRONG — kicad-cli 9 rejects this:
f"(net_class \"{name}\" (clearance {c}) (trace_width {w}) ...)"

# RIGHT — description string after class name:
f"(net_class \"{name}\" \"Auto-generated from netclass_rules.yaml\" (clearance {c}) (trace_width {w}) ...)"
```

The plan cited `ESP32-POE_ESP32-PoE_Rev_K.kicad_pcb` as a reference, but the description string requirement wasn't extracted during planning. A round-trip test (write netclass form → kicad-cli load → pass) would have caught this.

### 3. Netlist pin iteration: tuples vs Pin objects

`netlist.nets[i].pins[j]` is a `tuple` from the KiCad parser — not a `Pin` object with a `.component` attribute. `getattr(tuple, 'component', None)` returns `None` for every pin, so the constraint generator classified 0 components and produced 0 constraints:

```python
# WRONG — net.pins[i] is a tuple, has no .component
for net in netlist.nets:
    for pin in net.pins:            # pin is a tuple
        if pin.component == comp_ref:  # AttributeError, silently caught
            ...

# RIGHT — component.pins[i] is a Pin object with .net
for pin in component.pins:          # pin is a Pin object
    net_name = pin.net
    ...
```

## Why This Matters

**Three independent failures, one compound false confidence.** The DRC wrapper returned 0 because kicad-cli failed silently. The constraint generator returned 0 because tuples have no `.component`. The netclass forms broke kicad-cli on the output PCB. Each bug alone would produce a wrong result; together they produced a completely disconnected measurement.

**The "it loaded in the reference board, therefore my board must load" assumption is wrong.** The reference board (ESP32-POE) was generated by KiCad itself with correct syntax. A hand-authored or placer-generated board inherits whatever format the generator produces. The format contract must be verified — not assumed from a different board.

## Prevention

1. **Round-trip test for any generated format:** write file → external tool loads it → verify exit code 0. Not "it looks right" — "the tool accepts it."
2. **Assert on classifications, not just final output:** `assert len(constraints) > 0` before claiming "separation works." Silent empty results are the most dangerous.
3. **Check subprocess exit codes:** `run_drc()` must check `returncode != 0` and return a sentinel, not 0.
4. **Verify attribute access on parsed structures:** when iterating `list[tuple]` vs `list[Pin]`, a `.component` access that silently returns `None` via `getattr(default=None)` is a bug magnet. Prefer attribute access that raises `AttributeError` on wrong types, or type-check at the parse boundary.
