# Fabricated-MPN Audit and Gate — 2026-07-27

**Scope:** every MPN in `elec/src/*.ato` (the canonical, machine-readable source of
truth) and `docs/hardware/BOM.md` (the derived prose BOM). Four fabricated parts
had already been found by accident, each while looking for something else:

1. `EKZE251ELL332MM40S` (bus capacitor) — did not exist at any distributor.
2. `DE2E3KH221MA3B` (X2 safety cap) — MPN unfindable *and* the value was wrong
   by 1000x (Murata's `221` suffix decodes to 220 pF; the BOM called it
   220 nF). Real part substituted: `B32922C3224M289`.
3. A third case, already recorded in `docs/evidence/2026-07-26-bom-availability-sweep.md`.
4. `ERA-3AEB6132V` / 61.3 kOhm (`modules.ato:1621-1622` at the time it was found,
   `modules.ato:1591` in the current tree) — 61.3 kOhm is not an E96 *or* E192
   value (neighbours 60.4, 61.2, 61.9), and the MPN is in neither DigiKey's
   nor Mouser's catalogue. Value and MPN agreed with *each other* perfectly;
   only reality disagreed.

This pass audits everything else, and builds an offline, fail-closed CI gate
so this error class cannot recur silently.

---

## Falsifier (stated before implementation)

> If the gate is given a reconstruction of the known case-4 fabrication
> (`ERA-3AEB6132V`, declared 61.3 kOhm +/-0.1%) and does **not** report an
> E-series violation naming 60.4/61.2/61.9 kOhm as the nearest legal E192
> neighbours — whether by silently passing it, crashing, or miscategorising
> it as "unchecked" — the gate has failed its one job and must not ship.

**Result: the falsifier did not fire.** `scripts/tests/test_mpn_fabrication_gate.py::test_falsifier_case4_reconstruction_fires`
reconstructs exactly this fixture and asserts the violation, the `eseries`
classification, and the three named neighbours (60.4/61.2/61.9 kOhm). It
passes. The same reconstruction against the *real* MPN string
(`decode_mpn("ERA-3AEB6132V")` → 61300.0 ohm) is exercised end-to-end by
`test_gate_fails_on_real_tree_today`, which runs the shipped gate binary
against today's `elec/src/*.ato` and asserts `r_low_top` / `ERA-3AEB6132V`
appear in its output.

A second falsifier was checked for the anti-vacuity requirement: *if the
gate is pointed at zero `.ato` files, or at a real file with zero
resistor/capacitor declarations, and it exits 0, that's a vacuous pass and a
bug.* This also did not fire — both paths exit 5 (tool error), never 0. See
Gate Proofs below.

## Triage method

1. **Offline first.** Every `<ref>.value = <num><unit> [+/- tol%]` /
   `<ref>.mpn = "<mpn>"` pair in `elec/src/*.ato` was parsed (120 pairs).
   Each declared value was checked against the E-series appropriate to its
   tolerance (E6/E12/E24/E48/E96/E192, generated by the standard IEC 60063
   rounding construction and cross-checked against the case-4 anchor).
   Each MPN was decoded, where its manufacturer-prefix family is
   recognised, and cross-checked against the declared value.
2. **Prioritise by consequence.** Safety-critical/precision items (anything
   mains-facing, in a protection-threshold path, or specified tighter than
   1%) were triaged first; then actives; then commodity passives — per the
   task brief.
3. **Network verification only where offline signals were suspicious or the
   role was safety-critical.** 9 MPNs were freshly checked against DigiKey
   (direct product-page fetches, not search snippets) this session,
   targeted at the E-series/decode failures in safety-critical or
   precision roles, plus the highest-consequence "found by accident"
   candidate (the OCP-01 reference divider). The remaining ~144 commodity
   passives were left offline-only, consistent with the existing
   `2026-07-26-bom-availability-sweep.md`'s own explicit sampling rationale
   — exhaustive live lookups on ~180 MPNs was called out in the task brief
   as certain to exhaust budget and stall.
4. **Did not redo the 38 MPNs `2026-07-26-bom-availability-sweep.md` already
   checked.** That document is treated as ground truth for those 38; this
   audit's new network checks are disjoint from it (listed below).

## Findings, ranked by consequence

### 🔴 SAFETY-CRITICAL + SUSPECT-FABRICATED (flagged loudly, separately)

**`R_OCP_REF_T` / `r_ref_top` in `OCPComparator` (OCP-01, the primary
over-current protection comparator, 50 A trip) — `elec/src/modules.ato:1695`,
also `docs/hardware/BOM.md:337`.**

- Declared: `3200ohm +/- 1%` (3.2 kOhm).
- MPN: `RC0603FR-073K2L`, which decodes (Yageo R/K/M convention) to exactly
  3.2 kOhm — internally consistent, exactly the case-4 signature.
- **3.2 kOhm is not an E96 value.** Nearest E96 neighbours: 3.16 kOhm,
  3.24 kOhm, 3.09 kOhm.
- **Direct DigiKey search (`digikey.com/en/products/result?keywords=RC0603FR-073K2L`,
  fetched 2026-07-27): zero results.** DigiKey *does* carry the immediate
  neighbouring codes in this exact family — `RC0603FR-0733K2L` (33.2 kOhm),
  `RC0603FR-0773K2L` (73.2 kOhm), `RC0603FR-073K3L` (3.3 kOhm),
  `RC0603FR-073K6L` (3.6 kOhm), even the bare round `RC0603FR-073KL` (3 kOhm)
  — but nothing at `073K2L`. WebSearch corroborates: no distributor hit at
  all, anywhere.
- **Corroborating internal evidence:** every structurally analogous
  reference-divider "top" resistor elsewhere in this file uses a genuine
  E96 value for the same role — `CoilThermalComparator.r_ref_top` =
  `RC0603FR-073K16L` (3.16 kOhm), `SecondaryOCPComparator.r_ref_top` =
  `RC0603FR-073K74L` (3.74 kOhm), `ThermalComparator.r_ref_top` =
  `RC0603FR-079K09L` (9.09 kOhm) — all E96 members, all decode-clean. OCP-01
  is the one outlier.
- **This is not a documentation typo isolated to one file**: `BOM.md §5.5`
  independently states the same MPN and the same "3.2kΩ 1%" note, added
  2026-07-26 — i.e., this was carried into the BOM as a real design
  decision, not just a stray `.ato` comment.
- **UNVERIFIED, not certain**: absence from a DigiKey keyword search is
  strong evidence (the same standard used to call case 2 and case 4
  fabricated) but not absolute proof of non-existence everywhere. Mouser
  fetches for this MPN timed out repeatedly and could not be completed this
  session — see UNVERIFIED list.
- **Why this ranks above even the UVL-02 finding below**: this is the
  primary over-current protection for a 1800 W mains induction cooktop. If
  the part cannot be procured at all, the build stalls at the safety path;
  if someone substitutes a "close enough" real part without noticing the
  E96 gap, the 50 A trip threshold silently moves.

### Highest real-world consequence (not fabricated — a real MPN, wrong declared value)

**`r_div_bot` in `LogicUVLOComparator` (UVL-02 candidate) —
`elec/src/modules.ato:2415-2417`.**

```
r_div_bot = new Resistor
r_div_bot.value = 100kohm +/- 1%
r_div_bot.mpn = "RC0603FR-0710KL"
```

`RC0603FR-0710KL` decodes to **10 kOhm** — a real, extremely common Yageo
part (used correctly as a literal 10k in ~15 other places in this same
file, already confirmed real in the 2026-07-26 sweep). The *declared value*
on the same three lines says **100 kOhm**.

This is not a fabrication — both 10k and 100k are real E96 values and
`RC0603FR-0710KL` is a real part. It is a **value/MPN disagreement**, the
same defect class case 4 taught us to look for, just without the
"nonstandard value" tell (both numbers are individually unremarkable,
which is exactly why nothing upstream caught it).

**Why it is the single highest-consequence finding in this audit:** the
module's own docstring gives an extensive, worked derivation — Ohm's-law
divider equations, nominal trip/recovery voltages, and a swept worst-case
corner analysis — *entirely conditioned on R_div_bot = 100 kOhm*:

> "With R_div_top=698k, R_div_bot=100k, R_hyst=3.74M (all E96 1%): VCC_trip
> = 2.715 V (nominal) ... worst-case trip (max) = 2.800 V < 2.9V ceiling
> (100mV margin)"

If the board is built to the MPN as specified (10 kOhm) rather than the
documented value (100 kOhm), the actual trip point recalculates to roughly
**24 V** on a 3.3 V logic rail — i.e., the comparator can never trip at all.
UVL-02 protects the board's own 3.3 V logic supply against brownout; a
10 kOhm part in this position would silently and completely defeat that
protection, and nothing downstream would notice until the rail actually
browned out with no lockout. (This module's fault output is *also* not
wired into the interlock's SET aggregation per its own docstring — a
separate, already-documented gap — so this divider is currently only
watched via a bench test point regardless; that does not reduce the
severity of the value/MPN drift itself.)

**Recommendation (not applied — see hard constraints): do not silently
"fix" this by editing either line.** Given every sibling divider in the
file consistently uses the dedicated non-10k MPN for its "…_bot" leg only
when the design genuinely wants a non-10k value, and this module's own
worked math needs exactly 100 kOhm, the likely correct fix is the MPN
(→ `RC0603FR-07100KL`, the exact part already used for `r_fb_top` and
`r_window_ok_pulldown` elsewhere in this file) — but this needs a human
decision, not an audit-pass edit.

**The gate fails on today's tree**, as required — 5 unresolved findings,
including the already-known case 4 (proving it still catches what it's
named for) and 4 new ones.

Proven anti-vacuity behavior (`scripts/tests/test_mpn_fabrication_gate.py`):

- `--ato-glob` matching zero files → exit 5, stderr names the tool-error
  reason. Never exit 0.
- A real `.ato` file with zero `.value`/`.mpn` pairs (`elec/src/interfaces.ato`,
  which only declares interfaces) → exit 5. "0 parts inspected, 0
  violations" is impossible to reach as an exit-0 state; it is a hard
  failure.
- An allowlist file that exists but has malformed YAML, or is missing a
  required field (`file`/`ref`/`mpn`/`checks`/`reason`) on any entry →
  `load_allowlist()` returns `None` and the CLI exits 5. A genuinely
  *absent* allowlist file is fine (0 entries) — only a present-but-broken
  one fails closed, so a typo can't silently disable every exception at
  once in either direction.
- The allowlist is scoped per `(file, ref, mpn, check-kind)` — an entry
  naming only `eseries` does not suppress an unrelated `decode` finding on
  the same line, and an entry for one `ref` does not suppress a finding on
  a different `ref` sharing the same MPN string.

16/16 tests pass (`uv run pytest scripts/tests/test_mpn_fabrication_gate.py -v`).
