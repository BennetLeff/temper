# `ac_l` — the generated schematic marks the mains fuse's line pin `no_connect`

**Date:** 2026-08-24
**Base:** `origin/main` @ `03d0f3697`
**Gate:** `ERC endpoint_off_grid consequence gate (pcb/temper.kicad_sch)`, the
`Cross-Source Consistency Gates` failure triaged in
[`2026-08-24-trunk-red-triage.md`](./2026-08-24-trunk-red-triage.md) §1.1.

## Bottom line

The gate is right, and the cause is one line of generator policy.

```
('F1', '1') [HV/mains]: atopile net 'ac_l' has 1 members;
  schematic net of that name has 0 members;
  missing_in_schematic=[('F1', '1')] extra_in_schematic=[]
```

`scripts/gen_schematics.py` represents **every** single-node net as a KiCad
`no_connect` marker instead of a label. There are 29 such nets. For 28 of them
that is correct. For `ac_l` it is not: `no_connect` is an assertion that a pin
is *intentionally* unconnected, and `ac_l` is the conductor by which mains Line
reaches the board.

So the committed schematic carries an X on the mains fuse's input pin, and
`docs/CONNECTORS_AND_WIRING.md` says a 16 A/250 V IEC C20 inlet lands there.

**This is a schematic-representation defect, not a board defect.** No copper is
wrong. What is wrong is that the drawing asserts something about the mains
input that the design does not mean, and ERC has been agreeing with the drawing.

## 1. The evidence, in the order I got it

### 1.1 `ac_l` is a one-node net in the source

`elec/build/default.net`, generated by atopile from `elec/src/*.ato`:

```
(net (code "12") (name "ac_l")
  (node (ref "F1") (pin "1") (pintype "stereo")))
```

One node. Compare its neighbour, and the fuse's other pin:

```
(net (code "13") (name "ac_n")
  (node (ref "L1") (pin "2")) (node (ref "RV1") (pin "2")) (node (ref "C1") (pin "2")))
(net (code "15") (name "w1_1")
  (node (ref "L1") (pin "1")) (node (ref "C1") (pin "1"))
  (node (ref "RV1") (pin "1")) (node (ref "F1") (pin "2")))
```

`elec/src/modules.ato:881` is where it comes from: `ac_l ~ fuse.p1`, with
`ac_l` declared `required = true` at `:647-648`.

### 1.2 One node is correct here — the inlet is off-board

`docs/CONNECTORS_AND_WIRING.md:13`:

| | | | | | | |
|---|---|---|---|---|---|---|
| **J_IN** | AC Mains Input | IEC C20 Inlet | Schurter 4798.9000 (Panel) | IEC C19 Cord | 3 | 16A/250V |

and §2.1: *"Panel Mount, Quick Connect or Solder terminals — **L**: Line (Hot) —
Black/Brown Wire (14 AWG)."*

The inlet is a **panel-mount** part, so it is legitimately absent from the PCB
netlist. Confirmed independently: the design's only two connectors are `J1`
(JST XH 4-pin, RTD sensor) and `J2` (2-pin header, fan). There is no PCB-side
mains inlet, and there is not supposed to be.

**So `ac_l` having one node is correct. What follows from it is not.**

### 1.3 The schematic gives F1 pin 1 a `no_connect`

`pcb/power_input.kicad_sch`, F1 at `(90.80 110.80)`:

```
(symbol (lib_id "0034.3129") (at 90.80 110.80 0) ...
  (property "Reference" "F1" ...)
  (pin "1" ...) (pin "2" ...))
(no_connect (at 75.56 110.80) ...)          <- pin 1 side, 15.24 mm left
(label "w1_1" (at 106.04 110.80 0) ...)     <- pin 2 side, 15.24 mm right
```

Pin 2 gets its net label. Pin 1 gets an X.

`grep -r "ac_l" pcb/*.kicad_sch` returns **nothing**, across all eight sheets.
The net does not appear in the drawing in any form.

### 1.4 It is systematic, and the control is clean

Every net with one node loses its label; every net with two or more keeps one
label per node:

| net | nodes | labels in `pcb/*.kicad_sch` |
|---|---:|---:|
| `ac_l` | 1 | **0** |
| `usb_dp`, `usb_dn`, `nc3`, `gpio18`, `tx`, `rx`, `io13`, `a3`, `b3` | 1 each | **0** each |
| `ac_n` | 3 | 3 |
| `w1_1` | 4 | 4 |
| `RELAY_CTRL` | 6 | 6 |
| `PWR_RTN` | 20 | 20 |

### 1.5 The policy is explicit in the generator, and deliberate

`scripts/gen_schematics.py:751-755` — only multi-node pins are eligible for a
label:

```python
# Build a set of (ref, pin) connected to multi-node nets
connected_pins: set[tuple[str, str]] = set()
for net in netlist.nets.values():
    if net.pin_count >= 2:
        for ref, pin in net.nodes:
            connected_pins.add((ref, pin))
```

and `:1034-1036`, inside `oracle_verify()`:

```python
for net_name, pins in src_by_net.items():
    if len(pins) <= 1:
        continue  # single-node nets -> no_connect markers
```

This is not an accident. It is a stated design decision, and the oracle was
written to match it.

## 2. Why nothing caught it: the oracle excludes exactly this class

`oracle_verify()` is the generator's own correctness check — it re-exports a
netlist from the generated schematics and compares connectivity against the
source. §1.5's second excerpt is the reason it cannot see this defect: **the
single-node nets are skipped before the comparison runs.**

So the oracle can prove that every multi-node net survives generation, and can
prove nothing whatever about the 29 single-node ones. The generator could drop,
rename, or mis-mark any of them and the oracle would stay green. It did, and it
was.

That is the same shape as the WASM tier's freshness check
(`docs/evidence/2026-08-24-wasm-tier-phase5-verdict.md` §6.2), which compares
deployed against CI-built and is therefore structurally blind to a stale
registry both sides share. A verifier that excludes a class cannot report on it,
and its greenness will be read as covering it.

## 3. Which of the 29 are actually wrong

I classified all of them. **One is wrong. The other 28 are defensible.**

| class | count | pins | `no_connect` correct? |
|---|---:|---|---|
| ESP32-S3 unused pins | 16 | `U27` — `usb_dp/dn`, `tx`, `rx`, `gpio18/21/35/36/37`, `io13/40/41/42/45/46/48` | **Yes** |
| Explicit NC pins | 2 | `nc_7` (`U6.7`), `nc3` (`U8.20`) | **Yes** |
| Spare logic outputs | 5 | `safety.fault_or-y3`, `safety.fault_any_or-y3`, `safety.fault_or3-y3`, `rtd_pan.rail_monitor-outb`, `safety.uvlo_logic.mon-outb` | **Yes** |
| Spare logic **inputs** | 3 | `a3`, `b3`, `c3` (`U24.11/12/13`) | Yes for the drawing — but see below |
| Spare relay NO contacts | 2 | `discharge.k_dis1-no` (`K2.3`), `discharge.k_dis2-no` (`K3.3`) | Probably — the `-nc` halves are in use |
| **Mains line landing** | **1** | **`ac_l` (`F1.1`)** | **No** |

Two asides, neither part of this finding and neither a schematic question:

- `a3`/`b3`/`c3` are *inputs* of a spare gate on `U24`. Floating CMOS inputs are
  a hardware concern independent of how they are drawn; a `no_connect` is an
  honest drawing of the current design, which is what makes it worth noticing.
- `discharge.k_dis1-no`/`k_dis2-no` are the unused halves of relays whose `-nc`
  contacts are wired (`R14`/`R7`, `R15`/`R9`). Fine electrically; worth being a
  deliberate choice rather than a default on a discharge path.

## 4. The fix I recommend, and the decision it needs

The generator needs to distinguish two things it currently conflates:

- **"this pin is intentionally unconnected"** → `no_connect`. Right for 28.
- **"this net leaves the board by wire"** → a label. Right for `ac_l`.

Nothing in the netlist expresses that difference today, so it has to be
declared. Cheapest form that stays reviewable: an explicit, commented list of
wire-landing nets — in `elec/src/` as an attribute, or as a small config the
generator reads — seeded with `ac_l` and cross-referenced to
`docs/CONNECTORS_AND_WIRING.md`'s J_IN row. The generator emits a label for
those and a `no_connect` for everything else.

**And `oracle_verify()` should stop skipping single-node nets.** Once the two
cases are distinguishable it can assert the right one for each, which is what
turns §2's blind spot into coverage. That is the durable half of this fix; the
label itself only repairs today's instance.

## 5. Why I did not apply it

`kicad-cli` on this machine cannot run schematic operations:

```
Error: Failed to load shared library '.../_eeschema.kiface':
  libwx_gtk3u_webview-3.2.so.0: cannot open shared object file
```

So I could not regenerate the schematic, could not re-run ERC, and could not run
`oracle_verify()` — which itself shells out to `kicad-cli sch export netlist`.
A fix to how a mains conductor is represented, shipped without being able to run
the gate it is meant to clear, is not a fix; it is a guess with a commit message.
The finding is complete and reproducible without it (§6), and the change is
small once someone can verify it.

There is also a policy question in §4 that is not mine to settle: the list of
wire-landing nets is a statement about how the product is assembled.

## 6. Reproducing

```bash
# 1.1 — one node
grep -A2 '(name "ac_l")' elec/build/default.net

# 1.3 — the marker, and the absent label
sed -n '630,655p' pcb/power_input.kicad_sch
grep -rc "ac_l" pcb/*.kicad_sch            # -> 0 on every sheet

# 1.4 — the control
for n in ac_l usb_dp gpio18; do echo -n "$n "; grep -rho "\"$n\"" pcb/*.kicad_sch | wc -l; done
for n in ac_n w1_1 PWR_RTN; do echo -n "$n "; grep -rho "\"$n\"" pcb/*.kicad_sch | wc -l; done

# 1.5 — the policy
sed -n '751,755p;1034,1036p' scripts/gen_schematics.py

# 3 — every single-node net and its pin
python3 - <<'PY'
import re
s=open('elec/build/default.net').read()
for c,n,b in re.findall(r'\(net \(code "(\d+)"\) \(name "([^"]+)"\)((?:\s*\(node [^\n]*\))*)', s):
    if b.count('(node ')==1:
        m=re.search(r'\(ref "([^"]+)"\) \(pin "([^"]+)"\)', b)
        print(f'{n:34s} {m.group(1)}.{m.group(2)}')
PY
```
