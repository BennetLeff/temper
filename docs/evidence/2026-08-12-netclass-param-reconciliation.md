# Net-class parameter reconciliation: all 5 mismatches resolved by correcting `design_rules.py`; gate is now blocking

**Verdict up front.** All 5 field mismatches `scripts/check_netclass_class_param_correspondence.py` reports on `origin/main` are resolved, in every case by correcting `design_rules.py`'s `TEMPER_NET_CLASSES` (and its duplicate, `packages/temper-placer/configs/netclass_rules.yaml`) to match `pcb/temper.kicad_pro`, which was correct in every case. `pcb/temper.kicad_pro` and `pcb/temper.kicad_pcb` were not touched. Measured: kicad-cli DRC's `clearance` and `track_width` violation counts on the real, committed board are **unchanged** (386 and 199 respectively, before and after) — neither correction touches a value kicad-cli's DRC actually derives a rule from. The gate now passes clean (5 → 0 mismatches) and `continue-on-error: true` has been removed from its CI step. One narrower question — whether `HighVoltage`'s now-2.0mm same-class clearance is itself IEC-adequate for a specific no-creepage-backstop case — is **not** resolved by this PR and is flagged for a human below; it does not block the gate because it is a value-adequacy question, not a correspondence one.

## HighVoltage.clearance: 2.0mm, not 6.0mm

### Grounding

- `pcb/temper.kicad_pro:219` (`"clearance": 2.0` in the `HighVoltage` block, `"name": "HighVoltage"` at line 226) has carried 2.0mm **since the file's introduction** — `git blame -L219,219 pcb/temper.kicad_pro` attributes the line to `651927a8e2` (2025-12-15), never touched since.
- `scripts/generate_kicad_dru.py:55-63` derives `HV_INTERNAL_CLEARANCE_MM = 2.0` from a cited IEC 60335-1 clause chain (verified directly, not quoted secondhand): clause 29.1 rated impulse voltage 1500V (120V nominal, OVC II, Table 15) → Table 16 basic clearance 0.5mm at that step → clause 29.1.3 "next higher step" for reinforced → 1.5mm → clause 29.1's own +0.5mm soldered-construction adder → **2.0mm**. This constant is what RULE 5 (`generate_kicad_dru.py:820`, `"HV internal same footprint"`) actually emits into the generated `.kicad_dru` for same-class `HighVoltage` pairs.
- `elec/src/constraints.ato:31-37` — the project's original, hand-authored SSOT (atopile) — declares `HighVoltage` with **two separate fields**: `clearance = 2.0mm` (line 33) and `air_clearance = 6.0mm` (line 37). `pcb/temper.kicad_pro`'s single clearance value matches `.ato`'s `clearance` field exactly; `design_rules.py`'s pre-fix 6.0mm matched `.ato`'s *different*, separately-named `air_clearance` field exactly. Both single-clearance-field tables (`design_rules.py`, `netclass_rules.yaml`) carried the same 6.0mm, consistent with the same conflation happening in both files at once (git history: `design_rules.py`'s `HighVoltage.clearance` started at 2.0mm, matching `kicad_pro`, at commit `d7aec3fb8`; raised to 6.0mm at `cb3174510` (2026-06-28), whose own commit message justifies the raise by citing a **cross-domain** (`HighVoltage`-to-`ACMains`) violation, not this class's own same-class figure).
- 6.0mm's citation, still attached to `netclass_rules.yaml`'s pre-fix entry (`because: "IEC 60335-1 Table 16 working isolation at 400V"`), does not hold up: Table 16 is indexed by *rated impulse voltage*, not working voltage, and its rows are 330/500/800/1500/2500/4000/6000/8000/10000V — 400V is not a row, and 6.0mm is not one of its values.

### Structural fact that makes the blast radius zero

`TEMPER_NET_CLASSES["HighVoltage"].clearance` is **never read** by `scripts/generate_kicad_dru.py`. Verified directly: `grep -n "HV_INTERNAL_CLEARANCE_MM" scripts/generate_kicad_dru.py` shows it used only at its own definition (line 63) and at RULE 5's emission (line 820) — a standalone constant, not derived from `TEMPER_NET_CLASSES`. The only field of `TEMPER_NET_CLASSES` that `generate_kicad_dru.py` consumes per-class is `.trace_width` (the "TRACE WIDTH RULES" loop, `generate_kicad_dru.py:1024-1037`, emitting one `(rule "<class> trace width" ... (constraint track_width (min ...)))` per class in `class_order`). So correcting `TEMPER_NET_CLASSES["HighVoltage"].clearance` cannot change a single kicad-cli DRC number — there is no code path from that value to the generated `.kicad_dru`, or to `pcb/temper.kicad_pro`'s own (unchanged) netclass table.

### The one open question this PR does not close

Whether 2.0mm is itself IEC 60664-1-adequate for the case it silently governs — **same-domain, different-potential `HighVoltage`-to-`HighVoltage` pairs on different components**, which get no custom `.kicad_dru` rule at all (RULE 5 requires `A.Reference == B.Reference`; RULE 2/3/4/4a/4b/6a/6b all require different netclasses) and therefore **no creepage backstop**, only this one clearance figure. `docs/specs/NET_CLASS_SPECIFICATION.md` (REQ-ELEC-01, §3.3) independently lists `HighVoltage`'s own "Clearance: 2.0mm (80 mil) minimum" (matching `HV_INTERNAL_CLEARANCE_MM`) but its adjacent "IEC 60335 Requirements" bullet — "Minimum clearance: 4mm through air" — is scoped to "Reinforced insulation to LV circuits," i.e. the cross-domain `HighVoltage`-to-LV case, not the same-class case this question is about; it does not resolve it either way. `scripts/generate_kicad_dru.py:475-476`'s own comment on the adjacent HV-to-LV rule ("NOTE: IEC 60664-1 at 400V working voltage may require 3.0mm+ clearance — verify before HV bring-up") shows the repo's own authors have not closed the analogous cross-domain question, let alone this narrower same-class one. **No document in this repository resolves this**, and it is not fabricated here. A human with the IEC 60664-1 text in hand needs to determine whether the rated-impulse-voltage derivation behind `HV_INTERNAL_CLEARANCE_MM` is the right methodology for this specific pairing, or whether a peak-working-voltage check independently applies (which `HIGH_VOLTAGE_CLEARANCE_SPEC.md`-style OVC III/PD2 tables would put closer to 2.5mm+ — a number between the two contested figures, matching neither one's original rationale). This is a value-adequacy question, separate from the correspondence question this PR's gate checks, and does not block it.

## Power: all four fields, 0.5/1.0/1.0/0.5mm, not 0.25/0.5/0.8/0.4mm

### Grounding

- `pcb/temper.kicad_pro:201,211-213` (`Power` block, `"name": "Power"` at line 208): `clearance: 0.5`, `track_width: 1.0`, `via_diameter: 1.0`, `via_drill: 0.5`. Its own `description` field reads *"LV power rails: +3.3V, +5V, +15V. 3A continuous."*
- `elec/src/constraints.ato:64-67` (`module Power`, the project's original SSOT): `trace_width = 1.0mm`, `clearance = 0.5mm`. (`.ato` has no `via_diameter`/`via_drill` fields for any class — vias are not modeled there.) These two fields match `pcb/temper.kicad_pro` exactly.
- `docs/specs/NET_CLASS_SPECIFICATION.md` (REQ-ELEC-01, "Status: Implemented"), independently of `.ato`: the summary table (line 17) and §3.2 "Power (Low Voltage Rails)" (lines 49-57) both give **Trace Width: 1.0mm, Clearance: 0.5mm, Via: 1.0mm pad / 0.5mm drill, Current: 3A** — all four fields, matching `pcb/temper.kicad_pro` exactly, independently of `.ato` (which doesn't cover via sizing at all).
- Two independent primary sources (the compiled-netlist SSOT for 2 of 4 fields, and a formal, dated, "Implemented" spec document for all 4) agree with `pcb/temper.kicad_pro` and disagree with `design_rules.py`/`netclass_rules.yaml`'s pre-fix values on every field.

### The field-mixup pattern, confirmed

`design_rules.py`'s pre-fix `Power` block (`trace_width=0.5, clearance=0.25, via_diameter=0.8, via_drill=0.4`, `packages/temper-placer/src/temper_placer/core/design_rules.py:100-110` before this PR) is **byte-for-byte identical** to its own `HighCurrent` class in the same file (`trace_width=0.5, clearance=0.25, via_diameter=0.8, via_drill=0.4`, then at lines 191-201) — every one of the four scalar fields, differing only in the unrelated `via_template` (`Via2x2` vs. `Via4x4`) and `dru_priority`. `netclass_rules.yaml`'s pre-fix `Power` block (lines 75-79) carried the identical four numbers. This is the same failure mode the task's own framing names for `HighVoltage`: a neighbouring row's values ended up in the wrong class, not an independent `Power` derivation — `HighCurrent` is a real, distinct class (`packages/temper-placer/src/temper_placer/core/design_rules.py`'s `TEMPER_NET_ASSIGNMENTS` maps it to different nets than `Power`) whose own values were never in dispute and are untouched by this PR.

### Blast radius, measured

`TEMPER_NET_CLASSES["Power"].trace_width` **is** consumed by `scripts/generate_kicad_dru.py`'s per-class "TRACE WIDTH RULES" loop (`generate_kicad_dru.py:1013-1037`), which emits `(rule "Power trace width" (condition "A.NetClass == 'Power' && A.Type=='Track'") (constraint track_width (min <value>)))` into the generated `.kicad_dru`. Raising this from 0.5mm to 1.0mm is therefore not structurally guaranteed to be a no-op the way `HighVoltage.clearance` was — it needed a real measurement, not just a code-path argument. `.clearance`, `.via_diameter`, and `.via_drill` are **not** consumed anywhere in `generate_kicad_dru.py` (confirmed: no `nc.clearance`/`nc.via_diameter`/`nc.via_drill` reference in that script outside the static, class-independent hole-clearance rules at the file's end) — those three fields have no DRC-generation code path at all, only the Python placer/router side (`packages/temper-placer/src/temper_placer/router_v6/constraints_design_rules.py:223,293,309` builds its own per-netclass tables from them for `router_v6`'s routing-budget calculations, and `netclass_constraints.py:118` uses `.clearance` for CP-SAT cross-class component-separation constraints).

Measured live, `scripts/ci_check_drc.py --backend kicad-cli`'s exact protocol (regenerate `pcb/temper.kicad_dru` from the current `design_rules.py`, then `run_drc` against the real, unmodified `pcb/temper.kicad_pcb`):

| | `clearance` | `track_width` | total errors |
|---|---:|---:|---:|
| before (base commit, `design_rules.py` unmodified — verified via `git stash`) | 386 | 199 | 1264 |
| after (this PR's `design_rules.py`) | 386 | 199 | 1264, 1263, 1264 (3 samples) |

**Zero measured change** in `clearance` or `track_width` across 3 post-fix samples (total errors varies by at most 1, consistent with `drc_ceiling.json`'s already-documented `creepage` nondeterminism band — `clearance` and `track_width` are the two deterministic categories here and neither moved). The reason: `pcb/temper.kicad_pro`'s own `Power` netclass `track_width: 1.0` (unchanged, always correct) already governs the board's actual enforced minimum; the generated `.kicad_dru` "Power trace width" rule going from `min 0.5mm` to `min 1.0mm` only tightens a rule that was already redundant with (and looser than) the netclass-level one kicad-cli was already enforcing. `power_pcb_dataset/drc_ceiling.json`'s ceiling (1266 total, 386 clearance, 199 track_width) is not breached; the board still measures within it before and after.

### Placement/routing feasibility (Python-side fields)

`.clearance`/`.via_diameter`/`.via_drill` feed `router_v6` routing-corridor budgets and CP-SAT cross-class separation constraints, not kicad-cli DRC. A full CP-SAT solve against the real 169-component board is not a tractable feasibility oracle in this repo today (established in `docs/evidence/2026-08-12-gate-vacuity-structural-prevention.md`'s antecedent work and reconfirmed by this session: `packages/temper-placer/tests/pcl/test_e2e_netclass_ssot.py` is itself marked `@pytest.mark.slow @pytest.mark.integration`), so feasibility was checked the way this repo's own test suite already encodes it: the full `core`/`io`/`pcl`/`router_v6`/`placer` unit/property/regression suite (12,435 collected tests) was run before and after. Excluding 4 test files that fail to *collect* in this environment regardless of this change (`ModuleNotFoundError: No module named 'temper_constraints'` — the `temper-constraints` pyo3 crate is not built in this worktree; confirmed pre-existing by running the same imports against the unmodified base commit), the run produced 22 failures. **All 22 were independently confirmed pre-existing** by re-running the identical test selection against the base commit via `git stash` (temporarily reverting this PR's `design_rules.py`/`netclass_rules.yaml` changes): 20 fail identically with the same `ModuleNotFoundError: No module named 'temper_constraints'` (missing rust extension), and 2 (`test_physics_gate.py::test_creepage_clean_*`) fail identically with `"No resolvable project ... call copy_kicad_project_sidecar"` (a pre-existing kicad-cli project-sidecar setup gap in this test, unrelated to netclass values). None of the 22 reference `Power` or `HighVoltage` clearance/trace/via values in their failure output. 8 additional tests in `test_design_rules.py`, `test_netclass_loader.py`, `test_e2e_netclass_ssot.py`, and `test_phase1_anti_false_zero.py` asserted the pre-fix (wrong) values as expected results — these were updated in this PR to assert the corrected values, each with a comment citing this document.
