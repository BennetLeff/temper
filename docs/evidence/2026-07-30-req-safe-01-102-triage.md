## 2. Overlap with the measurement tool's 60

### 2.1 Method

`scripts/measure_cross_domain_creepage.py --min-creepage-mm 8.0` re-run
against the identical tree (`elec/build/default.net` rebuilt via `make
netlist` first): **60 violations, unchanged from the prior session's
figure**, confirming this control tool is unaffected by anything in this
task. Both this tool and REQ-SAFE-01's fixture load domain membership from
the exact same `elec/domain_manifest.yaml` (`load_manifest()` in the tool
reads `domains.HV.nets`/`domains.SELV.nets` directly, same file, same exact
literal net-name matching rule).

Component-pair grouping (collapsing the tool's 60 pad-level records to
component-pair groups, matching REQ-SAFE-01's own unit of grouping):
**28 distinct component-pair/intra groups** (23 inter-component + 5
intra-footprint: C6, K2, K3, U3, U7).

### 2.2 The overlap number

**All 28 of the tool's groups are a subset of REQ-SAFE-01's 57.** Set
intersection computed directly (not estimated): `overlap = 28`,
`only_in_tool = 0`, `only_in_REQ-SAFE-01 = 29`. In other words: **the tool
undercounts relative to REQ-SAFE-01, and does so by exactly the 29-group
gap this section explains -- it never disagrees on a case it does examine.**

So the honest framing is: **you have 57 problems, of which 28 (49%) are
already visible in the 60-pad-pair view (just consolidated -- e.g. the
tool's 20 U7 self-pair records collapse to REQ-SAFE-01's single U7 intra
group), and 29 (51%) are additional, each with a specific, checked reason
below** -- not 102 independent findings and not merely "the same 60
findings restated."

### 2.3 Why the 29 are new: two distinct, fully-explained causes

**(a) 19 groups: pure threshold difference, not a new physical finding.**
17 inter-component pairs (C6-R23, C17-C30, C17-R1, C22-C28, C22-C9, C22-Q2,
C23-U17, C23-U27, C30-F1, D2-R70, D2-TP1, D4-U6, F1-TP1, R2-U6, R44-R5,
R59-RT1, R67-U7) plus 2 intra-footprint groups (K1, T1) that clear the
tool's 8.0mm bar but not REQ-SAFE-01's REINFORCED 10.0mm creepage minimum
(and, for the intra pair, are checked at all only because REQ-SAFE-01 also
enumerates intra-footprint crossings, which the tool's self-pair sweep
happens to already catch for these two at a looser bar too -- see SS1.2 for
K1=8.000mm, T1=9.100mm). Every one of these 19 groups' tightest measured
distance sits strictly between 8.0mm and 10.0mm (confirmed by direct
inspection against `pair_table_final.json`: range 8.255mm-9.844mm for the
17 inter pairs, 8.000mm and 9.100mm for K1/T1). These pairs are real, but
they are not something the 8.0mm tool got wrong -- they are outside the
question it was asked. (`T1<->U27`, a *different*, separate group at
7.850mm, is NOT one of these 19 -- it already clears the tool's 8.0mm bar
and is part of the 28-group overlap in SS2.2, not this new-29 set.)

**(b) 10 groups, all involving C27: a real, separate PCB defect.** Checked
directly against `placement["components"]` (built from the compiled
netlist, `elec/build/default.net`) vs. each component's own `pads[].net`
(built from `pcb/temper.kicad_pcb`'s own per-pad net annotation):

```
C27: component-level domain (from compiled netlist join) = DC_BUS
     nets = ['SW_NODE', 'tank.c_tank1-p2']   (both declared HV in the manifest)
     C27's own PCB PAD net annotations       = ['I_SENSE', 'gnd']
     -> neither pad annotation matches DC_BUS -> pads_in_domain() has no
        match -> REQ-SAFE-01's documented, conservative fallback ("Using
        every pad is the conservative choice" -- _copper.py's own
        pads_in_domain docstring) treats BOTH of C27's pads as DC_BUS
        copper for this check.
```

Every other component checked in the 27-group-minus-C27 "only in
REQ-SAFE-01" set (D1, R66, C15, R25, TP2, C35, C34, R29, C18, U22 on the
SELV side; C6, R23, U27, C23, C17, C30, R59, RT1, D2, R70, U17, R67, U7,
TP1, F1, R5, R44, U6, R2, D4, C22, Q2, C9, R1 elsewhere) has consistent
component-level and pad-level domain classification -- checked pair by
pair, not assumed. **C27 is the only component on the board where this
triage found the fallback was live.**

C27's two physical pads are real, fixed copper at their real PCB positions
regardless of what net name is written next to them, so the geometric
distances reported are trustworthy -- the ambiguity is only about WHICH
domain the fallback should have picked, and here it picked correctly:
both of C27's actual schematic nets (`SW_NODE`, `tank.c_tank1-p2`) ARE
declared HV, so treating both physical pads as HV copper is the right
answer, not merely the safe one. What this means in practice: **C27's PCB
pad-net annotations are stale relative to the current compiled netlist**
(most likely dating to before the tank bank changed from 2 to 3 capacitors,
per `elec/domain_manifest.yaml`'s own comment on `tank.c_tank1-p2`: "the
tank bank went 2 x 150nF -> 3 x 100nF; same 300nF total, same two nets, one
more component on each"). This is a genuine, if secondary, finding: any
OTHER tool that trusts the `.kicad_pcb` file's own per-pad net field for
domain classification (as `measure_cross_domain_creepage.py` and
`check_isolation_keepout.py` both explicitly do, by design) will silently
miss C27's real HV-to-SELV proximity. **Not fixed here** -- fixing a stale
pad-net annotation is a `pcb/` copper/net edit, outside this task's
footprint-documentation-only scope and outside its explicit hard
constraint against touching domain classification or netlist-affecting
geometry. Flagged for a follow-up task.

## 3. REQ-SAFE-01 measures pads only, not tracks or zones (and does not read F.Fab/F.CrtYd)

This task's brief describes REQ-SAFE-01 as measuring "copper items --
tracks, zones, pads." Read directly against the implementation
(`temper_placer/requirements/validators/clearance.py`, `_copper.py`,
`_geometry.py`, and `tests/requirements/safety/_real_board_fixture.py`):
**it does not.** `grep -rn "track\|zone\|Zone\|Track"` across every file in
`requirements/validators/` and the real-board fixture returns zero hits, and
a second grep for `"F.Fab\|CrtYd\|Fab\b"` across the same files also returns
zero hits -- the validator has no body-outline consumption either, which is
why SS5.1's RT1 footprint edit could not and did not move the 102 count.
The entire measurement is `_CopperModel`, built exclusively from each
placement component's `pads` list (`_component_pads()`); there is no code
path anywhere in this validator that reads a `kicad_pcb` `segment`,
`arc`, or `zone` element. This matters for the remedy triage in SS4: a
"routing" remedy (move a track or pull back a zone) cannot be verified --
or falsified -- against this checker at all, because the checker is
structurally blind to tracks and zones. Every one of the 102 violations is
therefore, by construction, a component-pad-to-component-pad finding; none
can be resolved by a copper-routing change alone, regardless of how the
routing looks. (Whether the requirement's real-world INTENT should also
cover track/zone copper is a separate, legitimate question -- this section
reports what the code that produced 0 -> 102 actually does, not what its
name implies it should do.)

## 4. Remedy triage: classification rule and results

### 4.1 Rule

- **`part`** for every intra-footprint group (7: C6, K1, K2, K3, T1, U3,
  U7) -- by definition unfixable by moving anything; the remedy is a
  different footprint, a different part, or (unverified by any tool in this
  repo) a milled isolation slot.
- **`routing`**: not used for any of the 102 -- see SS3. Stated explicitly
  rather than silently omitted, so this is a checked absence, not an
  oversight.
- For the 50 inter-component groups: **`local placement` if the group's
  worst shortfall is <=2.5mm, else `floorplan`.** This is a stated
  heuristic, not a placement simulation -- it was not verified by actually
  moving any part and re-measuring (this task's hard constraint forbids
  applying unverified placement/routing changes). The 2.5mm cutoff is a
  judgment call: on a board this dense, a few mm is roughly the available
  local slack around a small passive before it collides with its OWN
  domain's next neighbour; shortfalls beyond that consistently correspond,
  in the data, to a small number of "hub" components (R30, C27, C17, C22 --
  9, 10, 7, 8 violating neighbours respectively) whose entire local
  neighbourhood is crowded, not just their one worst pairing -- see SS1.3.
  Where available, the SS1.2 `body` column (pad-pair line-of-sight crossing
  under a component's own moulded body, from a 10.0mm tool re-run) is
  reported alongside as corroborating context, not as an input to this
  rule.

### 4.2 Results

Group-level (57 groups): **floorplan 28, local placement 22, part 7,
routing 0.**
Record-level (102 records): **floorplan 67, local placement 22, part 13,
routing 0.**

**28 of 57 groups (49%; 67 of 102 records, 66%) genuinely require the
deferred floorplan work** -- moving the HV resonant-tank region (R30, C27)
and/or the gate-driver secondary-side region (C17, C22, U7's neighbourhood)
relative to the surrounding SELV cluster. This triage does not attempt
that relocation (explicitly out of scope) and does not reclassify any of
these 28 to a cheaper category to shrink the count.

**22 groups (39%; 22 records, 22%) are plausible local-placement fixes** --
small shortfalls (<=2.5mm) against a low-fan-out SELV neighbour, most
involving a single small passive (C37, C28, C9, C30, TP1, D2, D4, Q2, R2,
R5, R44, R23, U17, U22, U27, R59/RT1, C23, C6/R23, R67, R70) that plausibly
has room to move without immediately colliding with a different neighbour.
**Not independently verified by re-placing and re-measuring** -- flagged as
a heuristic classification per SS4.1, not a confirmed fix.

**7 groups (12%; 13 records, 13%) need a different part** -- the 7
intra-footprint crossings. Consistent with, and a superset of, the 5
(C6/K2/K3/U3/U7) already known from prior sessions; K1 and T1 are added at
the tighter 10.0mm reinforced-creepage bar this task's corrected geometry
now exposes.

## 5. The three footprint-dimension unknowns

### 5.1 RT1 -- RESOLVED

**Real body:** Ametherm SL32-10015, D31.0mm max x T6.0mm max (disc
diameter x thickness), fetched and read directly from
`https://www.ametherm.com/datasheetspdf/SL3210015.pdf` (revision "a",
11/11/2008) -- not taken from a search-result summary alone; the raw PDF
table was read directly (`D: 31.0 max`, `T: 6.0 max`, `Lead Diameter: 1.0
nom`, `S: 7.8 nom`). This footprint's own name
(`R_Disc_D15.0mm_W7.0mm_P7.5mm`, a hand-made "stub", confirmed absent from
the real, installed KiCad `Resistor_THT.pretty` library) understated the
disc diameter by more than 2x.

**What was added:** `pcb/temper.kicad_pcb`'s RT1 footprint gained an
F.Fab and F.CrtYd rectangle, D(31.0mm, X-axis) x T(6.0mm, Y-axis), centred
on the existing pad-pitch midpoint (3.75, 0mm) -- i.e. the standard "disc
mounted with its flat face perpendicular to the board" silhouette real
2-lead radial disc parts use, verified by directly reading the installed
KiCad 10 library's `Varistor.pretty/RV_Disc_D15.5mm_W5.2mm_P7.5mm.kicad_mod`
(the same convention already used by this board's own RV1), which uses an
identical D x T rectangle, not a full-diameter circle. F.CrtYd adds the
same 0.25mm margin that library footprint uses.

**What was deliberately NOT changed:** the footprint's own name/`Footprint`
property (`Resistor_THT:R_Disc_D15.0mm_W7.0mm_P7.5mm`, still says D15.0mm),
the pad positions, or the pad pitch (board: 7.5mm; datasheet nominal:
7.8mm). Renaming the footprint or correcting the pad pitch to 7.8mm is a
part-selection/re-footprinting decision with net/routing consequences,
outside this task's documentation-layer-only scope, and is flagged here
rather than done silently.

**Verification:** `elec/build/default.net` sha256 identical before/after
(`3d677168b07478c070e3ebef4f596884393e20aab6648e82e7db0f4c056858ab`,

### 5.2 F1 -- LEFT UNKNOWN (confirmed, not merely repeated)

The task brief's framing -- "the cited part number is the fuse cartridge,
not any specific holder, so no body dimension can be derived from it" --
was independently verified, not just trusted, against this repo's own
source:

- `elec/src/components.ato`'s `Fuse` component docstring: "Bare 5x20mm fuse
  LINK ONLY -- not a holder+fuse assembly."
- `elec/src/modules.ato` (`fuse.mpn = "0034.3129"`): confirms the schematic
  component IS the bare Schurter FST 5x20 fuse link, and separately
  documents a known, still-open "HOLDER GAP" -- no PCB-mount fuseholder is
  instantiated anywhere in the 155-part BOM. `BOM.md` Section 1.2 names the
  INTENDED holder as Schurter FUP 0031.2510, but modules.ato's own comment
  already flags that this part's real drilling diagram (~30.48mm primary
  pin spacing plus a third orientation pin, per the Schurter FUP datasheet)
  does NOT match the current PCB footprint stub
  (`Fuse:Fuse_Holder_5x20mm`, 2-pin THT, 22.5mm pitch).
- Independently confirmed via the real Schurter FUP 0031.2510 datasheet
  (web search, `schurter.com/en/part/0031.2510` and RS/Digikey listings):
  this is a "Shock-Safe Fuseholder" with a slotted bayonet cap, external
  depth ~54.8mm, head diameter ~19mm -- an entirely different mechanical
  form factor from a simple 2-pad through-hole clip.

**Why this blocks adding F.Fab/F.CrtYd, not just naming the MPN:** even if
a body outline were drawn for the FUP 0031.2510, it would have to be
anchored to pads that do not exist on this board (the FUP is a 3-pin,
~30.48mm-pitch part; F1's real pads here are 2-pin, 22.5mm pitch). Drawing
a courtyard for a part whose real footprint has already been documented
(by this repo's own source comments) as NOT matching the board's actual
copper would misrepresent creepage geometry, not clarify it -- worse than
leaving it unknown. **Left unknown.** The correct fix is the one
`modules.ato` already names and defers: re-footprint F1 for the FUP
0031.2510's real pad-out before fab, a decision with net/routing
consequences outside this task's scope.

### 5.3 R30 -- LEFT UNKNOWN (confirmed: no manufactured part exists to have a datasheet)

R30's footprint (`lib:LitzPad_15A`, `generator hand-built`) is not a
purchased component -- it is a custom-designed pair of 8.0mm-diameter
through-hole pads for hand-terminating litz wire to the resonant tank, and
its own `descr` already says so: "generic high-current PTH pad spec; low
confidence -- no part-specific datasheet exists for this custom coil
terminal." Checked, not merely repeated: there is no Litz-pad manufacturer
or part number anywhere in `elec/src/*.ato`'s `tank.inductor_conn`
declaration to look up. **Left unknown** -- there is no "real body" to
establish a dimension for; the part IS bare copper with no moulded
enclosure, so an F.Fab/F.CrtYd outline for it would have to be invented
rather than sourced, which this task's hard constraint explicitly forbids.
This is the same pre-documented gap the task brief names, reconfirmed.
