# Why the HighVoltage clearance gap keeps happening, and what actually stops it

**Verdict up front.** PR #1023 and PR #1025 both claimed to sync
`pcb/temper.kicad_pro` against `design_rules.py`. Both only ever touched
`netclass_assignments` -- which NET maps to which CLASS -- and never
compared a CLASS's own parameter values (clearance, trace width, via
diameter, via drill). `HighVoltage.clearance` disagrees right now (6.0mm
`design_rules.py` vs. 2.0mm `pcb/temper.kicad_pro`) because **no gate,
script, or test in this repo has ever compared that field between those
two files** -- not because a real check regressed. This is a fresh
instance of a class this repo has now found 24 other times
(`docs/evidence/2026-08-11-gate-vacuity-audit.md`), and it fits a
specific, previously-undercounted sub-shape of that taxonomy: *the
compared property is presence/name, never value*. A new gate closing this
specific gap is added and proven to fail on the current tree (Part 1).
The structural fix the task asked me to evaluate -- mutation-test every
correspondence gate -- **already exists in this repo, already works, and
is not a proposal**: `scripts/gate_mutate.py` + `scripts/check_gate_mutations.py`
(R42) is real, CI-blocking machinery that mutates a gate's own committed
logic and requires a canary to notice. It is extended in this PR to cover
the new gate (Part 2, demonstrated, not just described) and, in the
process, caught two authoring bugs in that extension live -- itself a
second, unplanned proof that the mechanism works. But R42 has a hard
limit that no amount of scaling fixes: **it can only keep an *existing*
comparison honest. It cannot discover that a comparison was never
written.** That is what caught this defect, and it is not mechanizable.

## Part 1: what #1023/#1025 actually synced, and why nothing caught the rest

### The claim vs. the diff

Both PRs' titles and commit messages describe reconciling `pcb/temper.kicad_pro`
against `design_rules.py`. Read against their actual diffs, both are
narrower than that:

```
$ git show 8e92559e2 -- pcb/temper.kicad_pro | grep -c '"clearance"'
0
$ git show 28de4543d -- pcb/temper.kicad_pro | grep -c '"clearance"'
0
```

`8e92559e2` (#1023) adds four missing/case-corrected entries to
`net_settings.netclass_assignments` (`ac_l`, `ac_n`, `+170V_BUS`,
`SW_NODE` -> their correct classes). `28de4543d` (#1025) adds 23 more,
generated by a new script. Neither diff touches
`net_settings.classes[]` -- the block that carries each class's own
`clearance`/`track_width`/`via_diameter`/`via_drill` figures. Confirmed
directly: `pcb/temper.kicad_pro:219` still reads
`"clearance": 2.0` for `HighVoltage`, unchanged by either commit, while
`packages/temper-placer/src/temper_placer/core/design_rules.py:78` has
carried `clearance=6.0` for the same class since before both PRs.

**These are two different sections of the same file, and only one of
them has ever been checked against `design_rules.py`:**

- `net_settings.netclass_assignments` (net name -> class name): fixed by
  #1023, generalized by #1025's `scripts/sync_kicad_netclass_assignments.py`.
- `net_settings.classes[]` (class name -> clearance/width/via figures):
  touched by no PR, checked by no gate, until this one.

### Why nothing caught it: three independent near-misses, not one bug

**1. `scripts/sync_kicad_netclass_assignments.py` only ever reads class
*names*.** Its `load_declared_classes` (`scripts/sync_kicad_netclass_assignments.py:94-97`):

```python
def load_declared_classes(kicad_pro_text: str) -> set[str]:
    data = json.loads(kicad_pro_text)
    classes = data.get("net_settings", {}).get("classes", [])
    return {c["name"] for c in classes if "name" in c}
```

This is a `set[str]` of names, used only to decide whether a target class
is "real" (`compare_target_assignments`, line 105-117) before writing an
assignment. The script's `compute_diff` (line 120-134) diffs
`netclass_assignments` dictionaries -- never the `classes[]` entries
themselves. There is structurally no code path in this file that could
ever notice `HighVoltage.clearance` disagreeing, because it never reads
that field on either side.

**2. `scripts/check_hv_netclass_coverage.py`'s PROPERTY 2 checks rule
*existence*, not rule *value*.** Its own docstring is explicit about this
scope boundary (`scripts/check_hv_netclass_coverage.py:62-71`): "every
class this project declares as a real, intentional netclass must have at
least one rule ... that POSITIVELY matches that class by name." A class
with a *wrong* clearance rule is exactly as "covered" as one with the
*right* clearance rule -- both have "a rule of any kind." Finding 9 of
the gate-vacuity audit (`docs/evidence/2026-08-11-gate-vacuity-audit.md:603-677`)
independently proved this same blind spot for `HighVoltageIsolated`'s
missing trace-width rule and named the general risk explicitly: *"a gate
named 'netclass coverage' that measures rule existence would hide an
omitted clearance rule just as completely."* My defect is exactly that
prediction landing for real, on a different class, in the value dimension
rather than the presence dimension.

**3. `scripts/check_netclass_map_board_correspondence.py` explicitly
disclaims this pair.** Its own module docstring (line 11-13): *"PR #1023
fixed that pair, and #1025 is landing a generator with `--check` for
exactly that pair (do not duplicate it; this gate does not touch
`pcb/temper.kicad_pro` at all)."* `docs/evidence/2026-08-11-correspondence-gates.md`
(the design doc for this gate family) repeats the same disclaimer at
line 329-336, and names the `class_order` trace-width gap (Finding 9, a
sibling of this one) as a related item it deliberately left unbuilt.
Nobody dropped the ball here -- the gate was scoped away from this pair on
purpose, twice, in writing, by two different documents, and the pair was
never picked up by anything else.

### A fourth, freshly-found near-miss: the "CI tripwire" that was never wired

`sync_kicad_netclass_assignments.py`'s own docstring claims (line 19):
*"the two tables cannot independently drift again as long as this script
(or its `--check` mode, wired into CI) is run."* `scripts/manifest.yaml`'s
entry for it (added the same PR, `#1025`) states `disposition: ci-gate`
and *"--check mode is the CI tripwire against future drift."*

```
$ grep -rn "sync_kicad_netclass_assignments" .github/workflows/*.yml
(no output)
```

It is not invoked anywhere in CI. It has a real, passing pytest suite
(`scripts/tests/test_sync_kicad_netclass_assignments.py`, including a
`TestCLI` class that runs `--check` via `subprocess` against the real
`pcb/temper.kicad_pro`) -- but a test suite that exercises a script's CLI
is not the same claim as that CLI running as a gate in the pipeline that
blocks merges, and nothing does the latter.

This is the exact mechanism the audit's Finding 12
(`docs/evidence/2026-08-11-gate-vacuity-audit.md:771-808`) already named
for seven other scripts ("`disposition: ci-gate` is read by nothing").
`sync_kicad_netclass_assignments.py` is an eighth instance -- and it is
informative *why* the audit's own reachability scan missed it: Finding
12's methodology explicitly counts a script as "reachable" if *"a
`scripts/tests/test_<name>.py` exists under the pytest sweep"* (line
785-787). `test_sync_kicad_netclass_assignments.py` exists, so the
audit's generous heuristic would have credited this script as wired even
though it never runs as a gate. **The audit's own detection method
conflates "has unit tests" with "is invoked as a CI gate"** -- a real
gap in Finding 12's methodology, not just an omission from its list. (The
audit doc's own words apply here without irony: *"An audit of vacuous
gates is not exempt from being vacuous."*)

### The fix (Part 1 deliverable)

`scripts/check_netclass_class_param_correspondence.py` (new): for every
class name declared in **both** `TEMPER_NET_CLASSES` and
`pcb/temper.kicad_pro`'s `net_settings.classes`, compares all four scalar
routing fields (`clearance`, `trace_width`/`track_width`, `via_diameter`,
`via_drill`) and fails on any disagreement. Fail-closed contract matches
the gate family (`GateError` on missing/malformed/empty inputs, exit 5;
zero shared classes is a vacuous run, exit 5, never a clean pass).
`run()` accepts injectable `net_classes`/`kicad_pro_classes`, mirroring
`check_hv_netclass_coverage.py`'s own convention so tests never depend on
live repo state.

**Run against the real, current tree:**

```

=== FIELD MISMATCHES: 5 ===
  VIOLATION netclass 'HighVoltage' field 'clearance': design_rules.py=6.0 kicad_pro=2.0
  VIOLATION netclass 'Power' field 'clearance': design_rules.py=0.25 kicad_pro=0.5
  VIOLATION netclass 'Power' field 'trace_width': design_rules.py=0.5 kicad_pro=1.0
  VIOLATION netclass 'Power' field 'via_diameter': design_rules.py=0.8 kicad_pro=1.0
  VIOLATION netclass 'Power' field 'via_drill': design_rules.py=0.4 kicad_pro=0.5

FAILED -- 5 field mismatch(es)
$ echo $?
3
```

**This gate genuinely fails on the current tree.** It was not landed
passing and then broken; it was written to test this exact hypothesis,
and it caught five real disagreements on the first run, not just the one
the task named. **The other four (all on `Power`) are undiscussed by this
PR and not fixed here** -- listed above in full, per the task's
instruction not to hide what a gate reveals beyond its original target.
Which side is correct for any of the five, including `HighVoltage`, is
explicitly out of scope (owned by a parallel agent for the value
question); this gate is value-agnostic by construction -- it asserts
disagreement is a defect, never which side is right.

**Wiring:** `.github/workflows/python-tests.yml`'s `consistency-gates`
job, "Gate 6", alongside Gates 1-5 (three from
`docs/evidence/2026-08-11-correspondence-gates.md`, plus the PD2 and
corpus-fixture-divergence gates added after that doc). **Advisory**
(`continue-on-error: true`), matching that family's established
convention for a gate whose real motivating inputs are genuinely broken
today (Gates 1 and 2 there are advisory for the identical reason). A
named path to blocking is recorded directly in the workflow comment:
reconcile the five values (or re-derive one table from the other, the way
`sync_kicad_netclass_assignments.py` already does for
`netclass_assignments`), confirm the step exits 0, remove
`continue-on-error`. `scripts/manifest.yaml` gets a real entry
(`disposition: ci-gate`) that is, unlike the one three sections above,
actually reachable from a live workflow step -- checked directly, not
assumed.

19 unit tests (`scripts/tests/test_check_netclass_class_param_correspondence.py`):
mutation falsifiers (single-field mismatch, multi-field mismatch on one
class, missing kicad_pro field flagged against `None`, fixing the
mismatch clears the violation), anti-vacuity (six degenerate-input cases,
all fail closed), helper units, and a `TestRealRepoIntegration` test that
pins today's verdict as `violation` with `("HighVoltage", "clearance")`
in the reported set -- a future PR that reconciles the values must touch
this test too, not silently go green underneath an unchanged assertion.

**Reading across the table:** most instances are genuinely different bugs
in different files, but two mechanisms recur enough to call load-bearing:
(a) a "coverage"/"presence" check standing in for a "correctness"/"value"
check, and (b) a script or PR claiming CI enforcement that was never
wired. Neither has one root cause across all instances -- they are
independent authoring decisions in independent files -- but both are
instances of the same higher-level pattern: **the checked claim is
narrower than the plain-English claim next to it** (a docstring, a PR
title, a `disposition:` field), and nothing ever verifies the two agree.

### The structural fix: does R42 (mutation-testing gates) already exist, does it generalize, and did it stall?

**It exists, it is not a proposal, and it did not stall.**
`docs/plans/2026-08-02-035-feat-gate-mutation-testing-plan.md` (R42) specified
exactly the mechanism the task asks me to evaluate: weaken a gate's own
logic along declarative axes and require a canary to notice. It shipped:

- `scripts/gate_mutate.py` (538 lines): seven AST-transform axes
  (`guard-strip`, `condition-invert`, `scope-remove`, `violation-discard`,
  `comparison-flip`, `threshold-set`, `return-stub`), applied only to an
  in-memory/tempfile copy -- the committed gate file is provably
  byte-identical after every run (`committed_bytes_unchanged`, exercised
  in CI every time).
- `scripts/check_gate_mutations.py` (~460 lines): for each `(gate,
  mutation, canary)` triple in `ci-corpus/mutations.yaml`, runs the
  canary's `pristine`/`seed` functions against the real gate (must match
  expected outcomes) and then the mutated gate (must flip for the
  mutation to count KILLED).
- Wired into `.github/workflows/python-tests.yml`'s
  `board-provenance-requirements-gates` job, **never
  `continue-on-error`** -- a real, merge-blocking check.

One plan (`docs/plans/2026-08-07-002-feat-wasm-tier-phase2-4-plan.md`,
written 2026-08-07) claimed *"nothing has been built."* That claim was
already false the same day it was written -- the first sweep
(`docs/evidence/2026-08-07-gate-mutation-sweep.md`) landed 19/19 KILLED
that same date. A later session (`docs/evidence/2026-08-11-phase3-mutation-state-of-play.md`)
corrected the stale claim and, separately, found and fixed a real
regression: the sweep had silently drifted to 18/19 between 2026-08-07
and 2026-08-11 (an AST-locator index drifted when unrelated code changed
shape, plus a genuine gate hardening broke a canary fixture's
placeholder commit hash) -- fixed by re-locating the index and using a
real, resolvable commit SHA in the fixture, not by weakening either
assertion. This is the same "a plan claiming a gap that had already
closed, sitting next to a real gap that had silently reopened" pattern
this task's own brief warns about, playing out in the mutation-testing
machinery's own history -- and it was caught by treating code as ground
truth over plan prose, exactly as this task instructs.

**Does it generalize? Demonstrated, not proposed, in this PR.** The new
Part 1 gate is dependency-injectable by construction
(`net_classes`/`kicad_pro_classes` overrides, mirroring
`check_hv_netclass_coverage.py`), so extending R42 to it cost one new
canary module (`ci-corpus/canaries/check_netclass_class_param_correspondence.py`,
~90 lines: `pristine_agree`/`seed_mismatch`) and three new manifest
triples (`comparison-flip` on the field-equality check,
`condition-invert` on the final verdict guard, `return-stub` forcing an
always-clean `run()`) -- the same shape as the existing
`check_hv_netclass_coverage.py` entries, deliberately. Full sweep after
the extension:

```
$ uv run python scripts/check_gate_mutations.py
...
OVERALL: 22 killed, 0 survived, 0 unverified, 0 equivalent, 0 not_applicable -- mutation score 1.0000
```

(was 19/19 across 7 gates before this PR; the 3 new triples, all on the
new eighth gate, are this PR's own.)

**This extension caught two real authoring bugs live, which is itself
evidence the mechanism works rather than merely asserting it does:**

1. The first `condition-invert` registration used `index: 3` for `run()`'s
   final `if report.mismatches:` guard, by lexical (top-to-bottom) order.
   The sweep reported `NOT_APPLICABLE`: `gate_mutate.py`'s `_scope_node`
   + `ast.walk` traverse breadth-first, not lexically, so the correct
   index was `1`. This is not a hypothetical risk -- it is the *exact*
   mechanism that caused the real regression in
   `measurement-invert-freshness-guard` described above (an unrelated
   code change shifted an AST occurrence index). The drift guard did its
   job (reported `NOT_APPLICABLE`, mutated nothing) rather than silently
   patching the wrong line.
2. The first `comparison-flip` canary used a coarse `"clean"`/`"violation"`
   oracle. Flipping `!=` to `==` in `compare_class_params` does not flip
   the overall verdict on the seed fixture -- it just makes the *wrong*
   three fields (the agreeing ones) get flagged instead of the one real
   mismatch, so `report.mismatches` stays non-empty either way and the
   coarse state string is identical before and after. The sweep correctly
   reported this mutation **SURVIVED** -- a real, demonstrated blind spot
   in my own first-draft canary, not a hypothetical one. Fixed by making
   the canary return `f"violation:{sorted(field_names)}"` instead of the
   bare state, mirroring `check_hv_netclass_coverage.py`'s own
   `seed_unassigned_hv_net` docstring, which independently documents the
   identical reason ("a coarse state-only oracle cannot tell 'correctly
   flagged X' apart from 'wrongly flagged Y instead'"). After the fix, the
   sweep reports this triple KILLED.

Both fixes are committed in this PR alongside the new gate; both are the
kind of gap a plan document asserting "mutation testing generalizes" could
easily leave unstated. Demonstrating it against a gate authored in the
same PR, and hitting two real snags in the process, is stronger evidence
than describing the mechanism abstractly would have been.

### Cost, coverage, and what it structurally cannot catch

**Cost, measured, not estimated.** For a freshly-authored gate that
already follows this repo's dependency-injection convention (which every
correspondence gate examined in this PR and its precedents already does),
extending R42 costs: one canary module (~90 lines, most of it comment),
2-3 manifest entries (~15 lines each, mostly description prose per the
plan's own KTD1 "human-reviewable" requirement), and iterating on 1-2
authoring mistakes the sweep itself surfaces (as happened here). That is
on the order of an hour of focused work when `run()` is already
injectable. For a gate that is **not** already injectable -- most of the
CLI-only `scripts/check_*.py` files that always hit the real filesystem
or subprocess a real tool -- the cost is higher: either retrofit the gate
itself with injection points (a real code change to previously-working
logic, with its own regression risk) or build a heavier tempdir/subprocess
canary, as several of the 8 gates R42 already covers do
(`check_isolation_keepout.py`, `check_measurement_provenance.py`).

**Coverage today: 8 of 94 scripts currently declared `disposition: ci-gate`
in `scripts/manifest.yaml` (measured directly: `grep -c "disposition:
ci-gate" scripts/manifest.yaml` -> 94; the audit measured 86 a day
earlier, so the manifest has grown ~8 entries in the interim -- the
denominator is a moving target, and R42's numerator has grown by exactly
one gate over the same window), after 10 calendar days of dedicated
effort across four plan units (2026-08-02 plan -> 2026-08-07 first sweep
-> 2026-08-11 CI wiring and regression fix -> 2026-08-12, this PR's
extension). At roughly 8.5%, whichever denominator is used.** The plan's own "Assumptions" section scoped this
deliberately: *"Advisory gates (`continue-on-error`) are outside the
must-bite requirement in the first release"* -- meaning Gates 1, 2, and
the PD2 gate (all advisory, all genuinely violating today) are not even
eligible for R42's blocking guarantee as currently scoped, and neither,
strictly, is this PR's own new Gate 6 (added anyway, as a demonstration,
not because the plan requires it). Extrapolating the measured per-gate
cost linearly across the remaining ~78 `ci-gate` scripts is a multi-week
undertaking, not a cheap blanket rollout -- this is a real, load-bearing
limit on "does it scale to 115," not a hedge.

**What R42 structurally cannot catch, regardless of scale:** it mutates
an *existing* comparison and checks that a canary notices the mutation.
It has no operation for "this comparison was never written." Nothing
about `sync_kicad_netclass_assignments.py`'s `load_declared_classes`
reading only `{c["name"] for c in classes}` is a *weakening* of previously
correct logic -- it is, and was from the start, a deliberate scope
decision to compare names only. A mutation axis can invert a `!=`, strip
a `raise`, or stub a `return`; none of the seven axes has any way to
notice that a function which was always going to only read `.name` never
grew a second code path to read `.clearance`. **This is not a gap in
R42's seven axes -- it is a gap in what mutation testing as a category
can express.** Mutation testing proves an existing check is not
*accidentally* defeatable by a small code change. It cannot prove a check
covers the right *property* in the first place, because "compare
clearance too" is not a perturbation of the code that exists; it is code
that does not exist yet. Only the human/agent-driven audit -- reading a
gate's docstring against its actual field accesses, as both
`docs/evidence/2026-08-11-gate-vacuity-audit.md` and Part 1 of this
document did -- found that gap. R42 could not have found it, at any
coverage percentage, because there was nothing registered to mutate.

The two mechanisms are complementary, not substitutable, and the record
in this repo already shows both being necessary: the audit found 24 real
findings that no mutation sweep flagged (none of them are mutations of
comparisons that already existed correctly); R42, once wired, has held
its own 7-gate scope at a 1.0000 mutation score since 2026-08-11 and, in
this PR, caught two real authoring bugs the instant an eighth gate's
triples were added -- something a docstring-reading audit pass would have
had no mechanical way to force.

### Assessment: is mutation-testing the real fix, or the obvious one?

**Both, for different halves of the problem.** For gates that already
exist and already compare the right things: yes, unambiguously the real
fix, already proven in this repo (constraint_mutation_gate.py / R32's
Finding 8, closed; R42 / this PR's own 3-triple extension, closed) rather
than merely plausible. For gates that were never written, or that compare
the wrong pair of fields by design (this document's entire Part 1): no
amount of mutation-testing machinery would have found it, because there
was no comparison to mutate. The honest recommendation, given the
measured 9%-after-10-days coverage curve: require every **newly authored**
correspondence gate to ship with dependency-injectable `run()`, a canary
module, and 2-3 R42 triples on day one (now demonstrated cheap, ~1 hour,
