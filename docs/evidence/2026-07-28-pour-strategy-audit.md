# Copper-pour strategy audit: 96 zones, provenance, classification, and the falsifier

**Date:** 2026-07-28
**Base commit:** `60d441f2` (`docs/methodology-loop-discipline`) — "fix(placer): revert the
outer-layer half of the stackup fix, keep the phantom-layer half"
**Scope:** `pcb/temper.kicad_pcb`'s 96 committed zones; whether they are the binding
constraint on routing completion; a stackup/pour-rule recommendation.

## FALSIFIER — stated up front, per instructions

> *"Unnecessary pours are consuming the outer layers, and removing them raises
> routing completion materially above 38.54%. If completion does not move, the
> pours were not the binding constraint and the 'board is genuinely too tight'
> conclusion stands."*

**The falsifier did NOT fire.** Deleting the zones this audit classifies `DELETE`
(18 of 96: `GATE_HS`, `GATE_LS`, `PWM_HS`, `PWM_LS`, `V_BUS_SENSE`, `SW_NODE`) leaves
completion at **exactly 38.54% (59/96 unrouted)** — bit-for-bit identical to the
committed board. Going further and deleting **all 96 zones** (a diagnostic-only
experiment, explicitly not a recommendation — see Task 2) makes completion **worse**
(13.54%, 83/96 unrouted), not better — and relocating the KEEP-verdict pours to an
inner layer instead of deleting them (a second diagnostic, also not a recommendation)
lands on that exact same worse number. The mechanism explaining all three results is
in Task 0/Task 2 below. **The board is not simply "genuinely too tight" either** —
the real finding is more specific than the falsifier's binary offered: routing
completion today is capped by which of the 4 physical layers the router considers
available *and* how hospitable that layer is to the router once open (component
density, the forced-segment fail-closed gate), and pour deletion or relocation alone
changes neither in a way that helps, without further work this audit did not attempt
(Task 3).

## Task 0 — provenance: BOTH committed and generated, and that matters

The 96 zones are **generated by the router's pour emitter and then committed as a
snapshot into the board artifact.** Both halves of the provenance question are true
simultaneously:

1. **Generated at route time.** `route_pcb(..., enable_zone_pours=True)` calls
   `_emit_zone_pours()` (`packages/temper-placer/src/temper_placer/router_v6/_adapter_convert.py:551`),
   which calls `_zone_layers_for_net()` (line 420) to decide, per net, whether it
   gets zone treatment, then `compute_zones_for_net()`
   (`router_v6/zone_emission.py:139`) to turn that net's pad positions into one
   convex-hull `(zone ...)` per spatial cluster, on **both** `F.Cu` and `B.Cu`
   unconditionally (`_zone_layers_for_net` returns `["F.Cu", "B.Cu"]` for any net
   whose class is `GND`, `Power`, `GateDrive`, `HighVoltage`, or `ACMains` — see
   root-cause note below).
2. **Committed as a snapshot.** `git log --oneline -- pcb/temper.kicad_pcb` shows
   commit `556ccf4f` ("feat(pcb): commit first route of temper.kicad_pcb (51/96
   nets, 53.1%)") whose own message states: *"Committed board: 2,338 segments, 48
   vias, **96 zones**, 170 footprints."* That count matches the board file today
   exactly (`grep -c '(zone (net' pcb/temper.kicad_pcb` → 96). The zones in the
   board today are the literal output of a past `route_pcb(enable_zone_pours=True)`
   run, hand-committed.

**Consequence: editing `pcb/temper.kicad_pcb`'s zones directly is not a durable
fix.** The parser (`_parse_zones.py`) reads zones straight back out of whatever
`.kicad_pcb` it's given, and the very next commit that re-runs
`route_pcb(enable_zone_pours=True)` and commits the result will regenerate the same
zone pattern from the same net-class rules — because nothing about the *generator*
would have changed. A durable fix belongs in
`_zone_layers_for_net()`/`_CONTINUITY_EXEMPT_CLASSES`/`compute_zones_for_net()`
(the generator), not in the artifact. This audit measures against **scratch copies**
of the board (per instructions) precisely because of this: measuring against edits
to the committed file would describe a state the next route immediately erases.

### Root cause found while tracing this: `routing_strategy` says one thing, the code does another

`TEMPER_NET_CLASSES` (`core/design_rules.py:310`) declares a `routing_strategy` field
per net class. Only two classes set it to `"plane_required"`:

```
ACMains:     routing_strategy="plane_required"   (line 320)
HighVoltage: routing_strategy="plane_required"   (line 334)
```

`Power`, `GateDrive`, and `GND` leave `routing_strategy` at its default, `None`
(`core/netclass_rules_gen.py:71`). But `_zone_layers_for_net()` (the actual gate that
decides which nets get pours) does not consult `routing_strategy` at all — it
hardcodes its own, broader list: `("GND", "Power", "GateDrive", "HighVoltage",
"ACMains")`. `routing_strategy` is otherwise real, plumbed, and round-trip-tested
(`config_loader.py:464,913`, `_constraint_types/clearance.py:35`,
`tests/constraint_types/test_submodule_constraints.py:56-59` — which asserts
`ACMains`'s `routing_strategy == "plane_required"` survives config loading). It is
simply never read by the pour emitter. **This is the same SSOT-drift shape the base
commit already diagnosed for the outer-layer plane heuristic**: a declared, tested
piece of design intent (only 2 of 5 classes should get plane-style pours) and the
code that actually pours copper (5 of 5 classes) disagree, silently. This is why
`GATE_HS`/`GATE_LS`/`PWM_HS`/`PWM_LS` (GateDrive) and `+3V3`/`vcc`/`+15V`/`+15V_LS`/
`V_BUS_SENSE` (Power) have pours at all — nothing in the net-class *metadata* asked
for that; the emitter's own separate, unsynchronized net-class list did.

### Why deleting the correct pours doesn't move the number

`_extract_stackup()` (`packages/temper-placer/src/temper_placer/io/_parse_board.py:264-272`,
the code `60d441f2` deliberately kept) classifies `F.Cu`/`B.Cu` as `"plane"` — and
`routing_space.py:85` (`if layer_info.layer_type not in ["signal", "mixed"]: skip`)
then **excludes any `"plane"` layer from the router's routing space entirely** — the
instant **any single zone** on that layer has a net name matching a crude substring
test (`"GND" in name or "VCC" in name or "+" in name or "PWR" in name`,
`_parse_board.py:132-137`). `+15V`, `+3V3` (both contain `"+"`), and `PWR_RTN`
(contains `"PWR"`) all match. Deleting `GATE_HS`/`GATE_LS`/`PWM_HS`/`PWM_LS`/
`V_BUS_SENSE`/`SW_NODE` — none of which match the substring test in the first
place — removes zero matches from the layer, so `F.Cu`/`B.Cu` stay `"plane"`,
excluded, unchanged. **The pours that are electrically justified to keep
(`+15V`/`+3V3`/`PWR_RTN`) are exactly the ones triggering the layer-blocking
heuristic; the ones safe to delete were never triggering it.** Deleting the
delete-verdict list was always going to be inert for this reason, independent of
whether the deletions themselves are correct (they are, per Task 1).

The all-96-zones diagnostic confirms the mechanism from the other side: with zero
zones, no `plane_assignments` entries exist, so `F.Cu`/`B.Cu` fall through to
`layer_type = "signal"` (first/last layer index, `_parse_board.py:267-269`) — all 4
layers become nominally available. Completion **drops** anyway, to 13.54%, because
`F.Cu` (loaded with 170 real footprints, courtyards, and the `GateDrive`/
`HighVoltage` classes' `required_layer` constraints forcing specific nets onto
specific outer layers regardless of congestion) is far more hostile to the router's
forced-segment fail-closed gate than the two layers that currently carry **100% of
this board's actual routed copper**: `In1.Cu` and `In2.Cu`, which have zero
footprints and zero pours today — blank, obstruction-free canvases. Opening `F.Cu`/
`B.Cu` in name without giving the router anything better to route around on them
makes things worse, not better.

**Conclusion: the falsifier is refuted. Pours are not the binding constraint, in
either direction — but "the board is genuinely too tight" is also not the right
characterization.** The real constraint is that all useful routing today happens on
2 of 4 physical layers, and no pour-deletion policy changes that by itself. What
does change it is explored in Task 3, including a fourth measurement that confirms
it.

### A fourth measurement: relocating (not deleting) the KEEP pours

To check whether Task 3's recommendation — move the current/thermal-justified
copper to an inner layer instead of leaving it (or deleting it) on the outer layers —
would actually help, a diagnostic-only scratch board was built: `PWR_RTN`,
`DC_BUS_RTN`, `ac_l`, `ac_n` (the 4 KEEP-verdict nets) each get **one** zone,
relocated to `In1.Cu`; all other 92 zones (every DELETE-verdict net) are removed.
This is not a proposed final board state (areas are unchanged, not shrunk, and the
duplicate F.Cu/B.Cu mirror per KEEP net is dropped rather than properly resized) —
it exists only to test the mechanism.

**Result: 13.54% completion, 83/96 unrouted — identical to the all-96-deleted
diagnostic above, not an improvement over baseline.**

This is a genuinely surprising result and is reported plainly rather than
massaged. Tracing why: `_parse_board.py`'s plane-detection heuristic
(`_parse_board.py:132-137`) is **not** outer-layer-specific — it scans *every*
layer's zones for the `"GND"/"VCC"/"+"/"PWR"` substring match. `PWR_RTN`'s name
contains `"PWR"`, so relocating it to `In1.Cu` makes `In1.Cu` itself match
`plane_assignments` and get excluded from the routing space exactly as `F.Cu`/
`B.Cu` did in the baseline — the blockage moved, it didn't disappear. (`ac_l`,
`ac_n`, `DC_BUS_RTN` don't match the substring test at all — only `PWR_RTN`'s
name happens to.) With `In1.Cu` now blocked and `F.Cu`/`B.Cu`/`In2.Cu` all
zone-free, the router sees 3 nominally-open, copper-free layers — which produces
**the exact same 13.54%/83-96 result as the 4-nominally-open-layers, all-zones-
deleted diagnostic.** That equality is itself informative: above 2 open layers,
this board's completion number stops being sensitive to layer *count* and becomes
governed by something else — most likely `F.Cu`'s component density (170
footprints, all on the top side) combined with the forced-segment fail-closed
gate's conservatism there, versus the two pristine inner layers that currently
carry 100% of this board's actual routed copper.

**This means Task 3's stackup recommendation is not shown, by this measurement,
to raise the completion-rate number** — it is justified on independent electrical
grounds (a 340V/47kHz half-bridge should have a real return plane; `GateDrive`/
`HighVoltage`'s `required_layer` constraints are structurally unsatisfiable
without it), not on a promise that completion goes up. Whether completion
actually improves once the outer layers hold real, correctly-classified copper
depends on separate work (placement density, fail-closed-gate behavior on
crowded layers) not exercised by this audit's pour-only experiments. Reported
honestly rather than inferred favorably.

## Task 3 — stackup and pour-rule recommendation

### There is genuinely no return/reference plane on this board today

Confirmed directly: `grep -c` for zones by layer shows 48 on `F.Cu`, 48 on `B.Cu`,
**0 on `In1.Cu`, 0 on `In2.Cu`**. `ki_board.setup.stackup` is `None` (no KiCad
stackup table was ever defined for this board — confirmed by inspection, matching
`60d441f2`'s own finding). `docs/hardware/POWER_PLANE_DESIGN.md` describes a 4-layer
stack with **L2 = solid GND plane, L3 = power islands** — none of that exists in the
actual board file. The inner layers are not "the plane, just not shown here" — they
are electrically empty. A 340V/47kHz half-bridge with zero inner-layer return
copper has no controlled return path for its switching-current loop today; every
return current is riding whatever fragment of outer-layer pour happens to be
present, which per Task 1 is itself oversized, mispositioned (`SW_NODE`), and
scheduled for partial deletion.

**Recommendation: build the inner-layer return/power planes the docs already
describe, but wired to the *current* domain-partition reality, not the stale
star-point design.**

### The stale part of the existing docs, found while checking this

`POWER_PLANE_DESIGN.md` §3.1-3.2 and `GROUNDING_EMI_STRATEGY.md` both describe a
single L2 ground plane split into `PGND`/`CGND` (/`ISOGND`) regions joined at **one
physical 10mm×10mm star-point copper bridge** ("All ground return currents must flow
through the star point"). That design is **stale**: `elec/src/main.ato:435` records
"REMOVED: the star join (`power_return ~ gnd`) that used to sit here", and
`elec/domain_manifest.yaml` confirms `gnd` and `PWR_RTN` are separate compiled nets
today, `gnd ~ pe` (bonded to protective earth) rather than to `power_return`. The
*only* declared connections from the HV domain into the SELV domain are: the 10
isolator entries `check_domain_partition.py` verifies against the compiled netlist
(the Y1 safety capacitor `power_in.y_cap_pe`, plus discrete isolator components —
transformers, optocoupler, relays — declared in `elec/domain_manifest.yaml`
`isolators:`), and 2 explicitly audited protective-impedance resistor chains
(`ovp01_comparator_divider`,
`ovp01_adc_sense_divider`, 3-resistor series each, `min_length: 3`, so no single
resistor failure removes the current-limiting function). **A single copper star-point
bridge is not this design anymore — recreating it on an inner plane would
re-introduce the exact short the isolation redesign deliberately removed.** Any
inner-layer plane must therefore be built as physically separate copper regions —
one per domain (HV: `PWR_RTN`, `DC_BUS_RTN`; SELV: `gnd`) — with the same set of
discrete-component/trace crossings as the schematic already declares, never a
plane-to-plane copper bridge.

### Concrete recommendation

1. **`In1.Cu`: HV return region.** `PWR_RTN` and `DC_BUS_RTN` each get their own
   solid pour, sized to what 22A actually needs (§Task 1: current areas are 5-14×
   larger than the doc's own 5mm-pour spec implies for this board's trace lengths) —
   not a merge of the two nets into one flood; they are separate compiled nets and
   must stay separate copper. Keep well clear of the isolation barrier: this
   codebase's own `clearance_engine.py` (`INTERNAL_LAYER_CREEPAGE_FACTOR = 0.30`)
   reduces internal-layer creepage requirements to 30% of the external figure (the
   task brief's 3.0-8.0mm BASIC-through-REINFORCED range → roughly 0.9-2.4mm
   internal), but that reduction is a floor, not a target — do not route this
   region right up to the minimum.
2. **`In2.Cu` (or a second region of `In1.Cu`, if the creepage gap fits): SELV `gnd`
   reference region**, separate copper from the HV region above, connected to it
   *only* through the already-declared isolator components and the two
   protective-impedance chains (as traces/vias into each region, never as
   plane-to-plane copper).
3. **Outer layers (`F.Cu`/`B.Cu`) become genuinely available for signal/gate-drive
   routing** once the KEEP pours move off them — this is what the Task 2 mechanism
   requires to actually help (deletion alone made things worse; relocation is the
   untested-by-deletion-alone lever). `GateDrive`'s `required_layer="F.Cu"` and
   `HighVoltage`'s `required_layer="B.Cu"` constraints (`design_rules.py:336,369`)
   can only ever be satisfied if those specific outer layers are not walled off by
   the plane heuristic — today they structurally cannot be, regardless of which
   individual zone is deleted, because *some* KEEP-worthy pour always remains.
4. **`SW_NODE` gets a from-scratch, small, direct pour** (per
   `TRACE_WIDTH_CALCULATIONS.md`: ~5mm wide, "short connection to resonant tank")
   at the actual IGBT-output-to-tank path only. The gate-bias components currently
   stitched into its 40%-of-board hull (`D5`/`neg_bias_zener`, `R24`/`rgs`) need
   ordinary short traces, not zone geometry — connecting them via a zone is what
   produced the oversized hull in the first place (Task 1).
5. **Fix the generator, not just the artifact** (Task 0): make
   `_zone_layers_for_net()` consult `NetClassRules.routing_strategy` instead of its
   own hardcoded 5-class list, so only `ACMains`/`HighVoltage` (the classes that
   actually declare `"plane_required"`) get automatic zone treatment; `Power`/
   `GateDrive`/`GND` should route as traces by default, matching
   `TRACE_WIDTH_CALCULATIONS.md` for every one of those classes. This is the durable
   fix — editing `pcb/temper.kicad_pcb`'s zones without this change is undone by the
   next committed route.

None of the above was implemented in this pass — this is an audit with a
