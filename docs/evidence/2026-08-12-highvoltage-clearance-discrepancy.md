# HighVoltage netclass clearance: `pcb/temper.kicad_pro`'s 2.0mm is what fabrication actually enforces; `design_rules.py`'s 6.0mm is a legacy figure whose own citation is independently debunked — but "which is IEC-correct" is not fully closed by anything in this repo

**Verdict up front.** `pcb/temper.kicad_pro`'s `HighVoltage` netclass `clearance: 2.0` (line 219) is what kicad-cli's DRC actually applies to same-class, different-footprint `HighVoltage` pairs today, and it traces to a real, cited IEC 60335-1 clause derivation (`HV_INTERNAL_CLEARANCE_MM`, `scripts/generate_kicad_dru.py:63`). `design_rules.py`'s `clearance=6.0` (line 78) and `netclass_rules.yaml`'s matching `clearance: 6.0` (line 24) are **legacy figures that the repo's own prior research has already, independently, debunked the citation for** ("IEC 60335-1 Table 16 working isolation at 400V" — Table 16 has no 400V row and no 6.0mm value; see "How they diverged" below). **Do not sync `pcb/temper.kicad_pro` up to 6.0mm** — that would encode a debunked number into the fab-authoritative file and, measured below, breaches the committed DRC clearance ceiling by +25. Whether **2.0mm is itself sufficient** against IEC 60664-1 for the specific case it's silently covering (same-domain, different-potential `HighVoltage`-to-`HighVoltage` pairs that carry **no creepage backstop at all**) is **not resolved by any document in this repo** — flagged explicitly below as the human decision this investigation cannot close. Both measured blast-radius questions came back negative: raising `.kicad_pro` to 6.0mm buys no safety clarity (it's the debunked number) and costs +25 ceiling violations; lowering `design_rules.py` to 2.0mm buys **zero** isolator-placement feasibility (measured: U6 stays jointly UNSAT at both 2.0mm and 6.0mm — the isolation barrier's own corridor geometry is the sole bottleneck, not netclass clearance). No PR is opened.

## What `HighVoltage` actually covers

`pcb/temper.kicad_pro:356-406` assigns `HighVoltage` to `+170V_BUS`, `SW_NODE`, `DC_BUS+`, `DC_BUS-`, `DC_BUS_RTN`, `SWITCH_NODE`, `+15V_LS`, the resonant-tank nets (`a`, `w1_1`, `w1_2`, `zcd`, `tank-out`, `tank.c_tank1-p2`), and several component-internal HV pins. Per `docs/specs/HIGH_VOLTAGE_CLEARANCE_SPEC.md` §2.1, these sit in **Domain B (DC Bus)**: 170–340V DC working, 400V DC peak/transient. This is distinct from `ACMains` (Domain A, 120–240V AC) and `HighVoltageIsolated` (Domain C, the floating gate-drive bootstrap supply, 15V differential but 355V to earth) — both of which are correctly 6.0mm in **every** file (kicad_pro, design_rules.py, netclass_rules.yaml) and are **not** part of this discrepancy. Only `HighVoltage` disagrees across files.

**Clearance vs. creepage, kept separate throughout this doc, per the task's own instruction:** clearance is through-air; creepage is along-surface. `HighVoltage`'s **creepage** figure is consistent everywhere at 8.0mm (PD2, `HV_CREEPAGE_PD2_MM`, `scripts/generate_kicad_dru.py:77`, selected via `HV_CREEPAGE_ENFORCED_MM = HV_CREEPAGE_PD2_MM` at line 106) and is not in dispute. This document is about **clearance only**.

## Which value is correct

### Layer 1 — which number does the repo's own tooling actually enforce and cite

- `scripts/generate_kicad_dru.py:55-63` derives `HV_INTERNAL_CLEARANCE_MM = 2.0` from a real, traceable IEC 60335-1 clause chain: cl. 29.1 rated impulse voltage 1500V (120V nominal, OVC II, Table 15) → Table 16 basic clearance 0.5mm at that step → cl. 29.1.3 "next higher step" for reinforced → 1.5mm, + cl. 29.1's own +0.5mm soldered-construction adder = 2.0mm. This exact figure is what RULE 5 ("HV internal same footprint", lines 746-821) enforces for same-`HighVoltage`-class, same-component pin pairs (`A.NetClass == 'HighVoltage' && B.NetClass == 'HighVoltage' && A.Reference == B.Reference`, line 814-820).
- **For `HighVoltage`-to-`HighVoltage` pairs on *different* components** (e.g. `DC_BUS_RTN` vs `+15V_LS`, `SW_NODE` vs `w1_1`) — no custom `.kicad_dru` rule matches at all: RULE 2/3/4/4a/4b/6a/6b all require the two sides to be in *different* netclasses, and RULE 5 requires `A.Reference == B.Reference`. These pairs fall through entirely to KiCad's raw per-netclass `clearance` value from `pcb/temper.kicad_pro` — currently 2.0mm, **with zero creepage protection layered on** (confirmed below by measurement: every new violation at 6.0mm is a bare `clearance` finding, never paired with a `creepage` finding).
- `packages/temper-placer/configs/netclass_rules.yaml:51-55` (the placer's own config file, sitting directly next to its own duplicated `HighVoltage.clearance: 6.0`) states outright: *"this 6.0mm figure (like its ACMains/HighVoltage siblings above) is a legacy, not primary-cited, number; the fab-authoritative enforcement point is scripts/generate_kicad_dru.py's HV_CREEPAGE_ENFORCED_MM ... plus HV_INTERNAL_CLEARANCE_MM (2.0mm, cited) — not this placer-feasibility config."* This is the repo admitting, in its own words, that its own 6.0mm is not the number to trust.
- `scripts/check_creepage_clearance_drift.py` (the drift gate purpose-built to catch exactly this class of disagreement — see "Was there a gate" below) already reports a live `[clearance/reinforced]` **MISMATCH** family today: `2.0mm` at `scripts/generate_kicad_dru.py:63` vs `6.0mm` at `elec/src/constraints.ato:83` and `packages/temper-placer/configs/netclass_rules.yaml:57`. Measured directly this session (`uv run --no-sync python scripts/check_creepage_clearance_drift.py`, exit code 3).

### Layer 2 — is the 6.0mm figure's own citation actually sound

**No.** An unmerged prior research document in this repo's own history — `docs/evidence/2026-07-28-creepage-determination-brainstorm.md`, added at commit `880405ed9` on 2026-07-28, present on `origin/feat/provable-safety-place-and-route` / `origin/docs/methodology-loop-discipline` / `origin/fix/strategy-board-facts-gate` but **never merged to `main`** (confirmed: `git merge-base --is-ancestor 880405ed9 HEAD` → not an ancestor; `git show HEAD:docs/evidence/2026-07-28-creepage-determination-brainstorm.md` → missing) — traced every creepage/clearance figure in the repo against IEC 60335-1/60664-1 primary text and found (its own table, reproduced verbatim):

> **"6.0 mm clearance, `because: "IEC 60335-1 Table 16 working isolation at 400V"`** | `netclass_rules.yaml` (`ACMains`, `HighVoltage`, all 9 `class_pairs`) | HV-to-HV working isolation | **Misattributed twice over.** Table 16 is indexed by *rated impulse voltage*, not working voltage; 400 V is not one of its rows (rows are 330/500/800/1500/2500/4000/6000/8000/10000 V); and 6.0 mm is not one of its values.

The same document independently derived the 2.0mm figure via the identical clause chain that later became `HV_INTERNAL_CLEARANCE_MM` — so the citation trail behind 2.0mm is real and reproducible; the citation trail behind 6.0mm's "working isolation at 400V" label is fabricated (the value exists nowhere in the table it cites).

### Layer 3 — a plausible mechanical origin for the divergence, found in the project's own primary SSOT

`elec/src/constraints.ato` — the atopile-compiled netlist's own source of truth, and `check_creepage_clearance_drift.py`'s own docstring names it first among the four places these figures are independently declared — carries, for `HighVoltage` (lines 29-37):

```
module HighVoltage:
    trace_width = 3.0mm
    clearance = 2.0mm
    v_max = 400V
    i_max = 25A
    creepage = 8.0mm   # IEC 60335-1 reinforced insulation
    air_clearance = 6.0mm
```

**Two separate, differently-named fields, both real, both live in the compiled netlist today**: `clearance = 2.0mm` and `air_clearance = 6.0mm`. `pcb/temper.kicad_pro`'s netclass schema has exactly one clearance concept — and its value (2.0mm) matches `.ato`'s `clearance` field exactly. `packages/temper_placer.../design_rules.py`'s `NetClassRules` pyclass *also* has exactly one `clearance` attribute — and its value (6.0mm) matches `.ato`'s `air_clearance` field exactly, not its `clearance` field. `HV_to_LV.min_clearance = 6.0mm` (`.ato:83`, the module governing the reinforced HighVoltage→Default/LV crossing) also carries 6.0mm, consistent with `air_clearance` being that boundary's own shorthand copy, not the class's intrinsic self-clearance.

This is **measured as a striking correspondence, not confirmed as the actual authorial history** — no commit message says "I copied `air_clearance` into `NetClassRules.clearance` by mistake." What *is* confirmed by `git blame` (below) is that the two single-clearance-field files (kicad_pro, design_rules.py) each match a different one of `.ato`'s two same-class fields, exactly, which is consistent with a field-name conflation during the Python port and inconsistent with the divergence being a considered, still-live design decision on either side — nothing in `design_rules.py`, `netclass_rules.yaml`, or their git history explains *why* 6.0mm rather than 2.0mm should be the class's own intra-class figure, beyond the now-debunked "Table 16 working isolation at 400V" line.

### What is NOT resolved

The unmerged 2026-07-28 document's own conclusion — *"clearance is not binding anywhere on this board"* (its §4, because IEC 60335-1 cl. 29.2.3 requires creepage ≥ clearance always, and the board's 8.0mm creepage floor dominates any clearance figure below it) — is scoped explicitly to the **mains↔PELV barrier-crossing case**, where a creepage constraint is always present alongside the clearance one. It does **not** cover the case this document is actually about: `HighVoltage`-to-`HighVoltage`, different-footprint, same-domain pairs, which (confirmed above) get **no creepage constraint at all** in `generate_kicad_dru.py` — clearance is the *only* protection on these pairs, so "clearance is not binding" does not apply here. `docs/specs/HIGH_VOLTAGE_CLEARANCE_SPEC.md`'s own §4.1 table (IEC 60664-1 Table F.2, OVC III/PD2), if a **Basic** insulation tier is judged to apply to two different-potential conductors within the same hazardous domain (as opposed to **Functional**, which the same document's own §3.3 insulation-type table defines as governing "within the same voltage domain" and which the spec never populates with a same-domain, high-differential figure) — would put the 400V row at 2.5mm Basic / 6.0mm Design Value, a number that lands *between* the two contested figures and matches neither one's stated rationale. `scripts/generate_kicad_dru.py:475-476`'s own comment on the adjacent HV-to-LV clearance rule ("NOTE: IEC 60664-1 at 400V working voltage may require 3.0mm+ clearance -- verify before HV bring-up") shows the repo's own authors have not closed this for the closely related cross-domain figure either.

**This is the open human decision:** whether the intra-class-only, rated-impulse-voltage-based derivation behind `HV_INTERNAL_CLEARANCE_MM` (2.0mm) is the right methodology for same-domain, different-potential `HighVoltage` pairs with no creepage backstop, or whether a peak-working-voltage check (IEC 60664-1 cl. 5.1.6-style, as `HIGH_VOLTAGE_CLEARANCE_SPEC.md` §4.1's own table applies) independently governs and would require something closer to 2.5mm+. No document in this repository closes this. Cost of each answer, given the measurements below: keeping 2.0mm costs nothing measured (U6 gets no benefit either way, and 2.0mm is already what's enforced); moving to anything above 2.0mm reopens the +25-violation ceiling breach measured below, scaled to whatever the new figure is.

## How they diverged (git history)

- `pcb/temper.kicad_pro`'s `HighVoltage.clearance` was set to **2.0mm at its very introduction**, commit `651927a8e` ("syncing dec 15", 2025-12-15), and **has never been touched since** — confirmed by `git blame -L 219,219 pcb/temper.kicad_pro`, which attributes the line to `651927a8e2` with no later commit.
- `design_rules.py`'s `HighVoltage.clearance` also **started at 2.0mm** (commit `d7aec3fb8`, "Add ACMains/HighVoltage net classes and PowerPlaneStage (ROUTING-17)"), matching kicad_pro at the time. It was raised to 6.0mm at commit `cb3174510` (2026-06-28), `"fix(pcb): increase HV clearance/creepage to IEC 60335-1 minimums"`, whose own commit message justifies the raise by citing **cross-domain** violations — *"Fixes IEC 60335-1 Table 17 violations on +340V_BUS, DC_BUS_RTN, SW_NODE vs MAINS_240V nets"* — i.e. `HighVoltage`-to-`ACMains` pairs, not the class's own same-class self-clearance. `netclass_rules.yaml` carries the identical 6.0mm figure with the identical (now-debunked) "Table 16 working isolation at 400V" justification, consistent with the same 2026-06-28-era reasoning being applied to both placer files together.
- **PR #1023 and #1025 did not touch this field, and their titles inviting that assumption is itself worth flagging.** Both are titled around "netclass ... sync" (`#1023`: "correct kicad_pro netclass case/coverage mismatch"; `#1025`: "full sync of kicad_pro netclass_assignments from design_rules.py SSOT"). Read closely, both are scoped **only** to `net_settings.netclass_assignments` — the **net-name → class-name** mapping (e.g. "is `ac_l` classified `ACMains`") — never to the per-class numeric fields (`clearance`/`trace_width`/`via_diameter`) the classes themselves carry. Confirmed directly from both PRs' full commit messages (`git log -1 --format=%B 8e92559e2` / `28de4543d`): neither mentions clearance/trace_width/via values, and #1025's message explicitly frames its own scope as "kicad_pro's netclass_assignments are now DERIVED from TEMPER_NET_ASSIGNMENTS" — a different table (net→class) from the one this document is about (class→numbers). **A sync that never claimed to cover this field cannot have silently failed to fix it** — this is not the "gate reported success while the artifact still disagreed" pattern the task asked me to check for; it is closer to "two same-day PRs whose names are easy to over-read as having covered ground they explicitly did not."

2. **Even enabled, it cannot see `pcb/temper.kicad_pro` at all.** `scripts/check_creepage_clearance_drift.py:274`: `SCAN_ROOT_NAMES = ("elec", "scripts", "packages", "configs")` — `pcb/` is not among them. The gate discovers declarations by walking `.ato`/`.py`/`.yaml` files under those four roots only; `pcb/temper.kicad_pro`'s JSON netclass table is invisible to it structurally, not by a scoping bug that could silently regress — it was never in scope.

## Blast radius, measured

### Direction 1: `pcb/temper.kicad_pro` 2.0mm → 6.0mm

Measured against a scratch copy of the committed board (`pcb/temper.kicad_pcb`, sha256 `6928b7c89...` — matching `drc_ceiling.json`'s recorded provenance exactly, unchanged), `pcb/temper.kicad_dru` freshly regenerated from `scripts/generate_kicad_dru.py`, kicad-cli 10.0.5, `--format json --severity-all --exit-code-violations --all-track-errors`, project sidecar preserved (per `validation/_drc_api.py`'s `DrcProjectContextError` warning — an early run without the `.kicad_dru` sidecar silently dropped the `creepage`/`track_width` categories entirely, caught and corrected before trusting any number below).

| | clearance | creepage | total violations |
|---|---:|---:|---:|
| baseline (2.0mm), 3 samples | **386, 386, 386** | 184, 183, 184 | 1888, 1887, 1888 |
| HighVoltage → 6.0mm, 3 samples | **411, 411, 411** | 182, 183, 183 | 1911, 1912, 1912 |

Clearance is fully deterministic at both values (matches the repo's own established convention that this category is deterministic while creepage is not, due to a known upstream kicad-cli pointer-dedup nondeterminism, issue #20048). **+25 clearance violations**, creepage unaffected (as expected — a different DRU mechanism entirely; the netclass clearance change touches no creepage constraint). All 27 raw new findings (25 net distinct pairs after de-duplication) are `"netclass 'HighVoltage' clearance 6.0000 mm"` violations between two *different* `HighVoltage`-classified components at actual measured gaps from 1.505mm to 5.297mm — e.g. `PTH pad 2 [DC_BUS_RTN] of C24` vs `Via [discharge.k_dis1-nc]`, `Pad 2 [DC_BUS_RTN] of R5` vs `Pad 2 [+15V_LS] of U8`, `PTH pad 1 [SW_NODE] of C25` vs `PTH pad 1 [w1_1] of RV1` — exactly the same-class, different-footprint, no-creepage-backstop category identified in Layer 1 above. **None carry an accompanying creepage finding**, confirming these pairs have zero creepage protection today regardless of which clearance figure governs them.

**This breaches `power_pcb_dataset/drc_ceiling.json`'s committed `clearance` ceiling (386, `provenance.measured_at_commit=f70296adc`) by +25.** Landing this change would require a `Ceiling-Approval:` trailer under this repo's R27 monotone-ceiling contract (`scripts/check_drc_ceiling_approval.py`) — it cannot land silently, and per the rules of this task, it is not being proposed.

## What this means for the task's two framed failure modes

Neither framed hazard materializes as stated: the fab-facing rules are **not** under-enforcing by 4mm relative to a correct 6.0mm requirement (6.0mm's own citation is fabricated, and the number that *is* enforced, 2.0mm, has a real if narrowly-scoped citation); and the placer's over-constraint is **not** what's driving U6's infeasibility (measured: zero effect). The genuine open item is narrower and lower-stakes than either framing suggested: whether 2.0mm itself is IEC-adequate for a same-domain, no-creepage-backstop pairing that no cited document in this repo has directly evaluated.

## Recommendation

No PR. Per this task's own rule, a PR that changes either value requires the correct answer to be unambiguous **and** not breach the DRC ceiling; direction 1 (2.0→6.0) fails both (the number is debunked, and it breaches the ceiling by +25); direction 2 (6.0→2.0) is not currently justified by a safety citation strong enough to promote it into the fab-authoritative file, even though it costs nothing measured to leave `design_rules.py` as-is (the placer is not actually solving a harder problem than the fab file allows — U6 is unaffected either way) or to fix it later for SSOT-honesty reasons alone.
