# Eliminating the acid-trap defect class in the router

<!-- provenance: commit=02e907b9a5e1dbca4eae9a0a53f8a2be6dc862c5 dirty=true (this task's own changes) -->

**Date:** 2026-07-27

**Scope:** find and fix the *generator* of acute-angle copper geometry in
`packages/temper-placer/src/temper_placer/router_v6/`, not hand-edit the
33 acid traps `detect_acid_traps` found on one specific re-route of
`pcb/temper.kicad_pcb` (per `docs/evidence/2026-07-27-drc-checks-repaired.md`
§1). `route_pcb` completion is non-deterministic run-to-run per historical
evidence, so patching one route's geometry would be near-worthless — the
task is to stop the router from generating acute angles at all.

## Falsifier, stated up front

*"Acute angles are generated by an identifiable, fixable stage of the
router. If instead they are inherent to routing on this grid pitch — e.g.
every 45-degree grid transition at a via or a T-junction registers as a
trap — then the honest deliverable is that finding plus a corrected
detection threshold, not a suppressed count."*

**Falsifier did not fire.** All 33 flagged traps were traced to a single,
identifiable, fixable bug in path-reconstruction geometry (below), proven
both synthetically and against the live board's actual flagged vertices.
The angle-classification thresholds in `acid_trap_detection.py` were not
touched, and 45-degree grid transitions themselves (right-angle and
diagonal bends with no quantization spur) are correctly *not* flagged —
confirmed directly (see "What a real 45-degree grid transition looks like"
below).

## 2. Where the acute angles come from

### Candidates investigated

| Candidate | Verdict | Evidence |
|---|---|---|
| A* neighbour expansion causing direction reversals | **Ruled out** | `route_pcb()` explicitly sets `enable_theta_star=False, enable_lazy_theta_star=False` (`_adapter_convert.py`); the live board uses plain 8-connected A*/Numba A* (`_dispatch_search`'s final branch). Neighbor validity (`neighbor_validity.py`) is pure occupancy — no direction memory, but standard grid A* has no incentive to reverse; verified no genuine mid-path zig-zags in the flagged data (below). |
| Path-simplification / corner-smoothing pass | **Ruled out (not in this pipeline)** | `path_simplify.simplify_path` exists but is called only from `io/kicad_exporter.py`, which is **not** on the `route_pcb()`/`RouterV6Pipeline` call path (confirmed: `grep` finds zero callers of `simplify_path` anywhere under `router_v6/` besides its own module and `kicad_exporter.py`). It cannot be the generator because it never runs. |
| Via-detour reconstruction in the `RoutePath3D` tier | **Confirmed as one of three call sites** | `_route_segment_3d` (astar_core.py) builds `world_path` for the 3D via-aware fallback with an exact-equality de-dup (`if point != world_path[-1]`) that can never match a float pad coordinate against a grid-cell-center float — same bug family as the other two sites. |
| Segment stitching between coarse and fine grids | **Ruled out as an independent source** | `_segment_search_coarse_to_fine`'s fine-grid result is returned as a plain grid-cell list, then flows through the *same* `_astar_route`/`_astar_route_multilayer` terminal-stitching code already identified below — not a separate bug. |
| **Terminal-to-grid-cell coordinate stitching at waypoint boundaries** | **Confirmed: the actual generator** | See below. |

### The actual generator

`OccupancyGrid.grid_to_world(x, y)` returns a grid cell's **center**:
`origin + (cell + 0.5) * cell_size` (`occupancy_grid.py:77-80`; default
`cell_size = 0.1mm`, `grid_prep_stage.py:35`). Pad, via, and waypoint
coordinates (`channel_path.waypoints`, ultimately footprint pad positions)
are exact floats from the netlist/placement layout — never grid-aligned in
general.

Three call sites build a net's path by walking an A* grid-cell path and
then appending the *exact* waypoint coordinate at each segment boundary,
to guarantee every real terminal survives explicitly in the emitted
geometry (a correctness requirement — see the `"Preserve every terminal
explicitly"` comment, added to fix a **different**, real bug: dropping an
intermediate pad when two consecutive grid paths happened to share a cell
center):

1. `_astar_route` (2D single-layer, `_astar_reconstruct.py`) — used an
   exact-equality check (`!= world_coord`) which can never match a float
   pad location against a float grid-cell center.
2. `_astar_route_multilayer` (the production 3D tier — **37/37 = 100%** of
   compiled routes on the live board used this tier, confirmed directly:
   `RoutePath3D` for every net, `RoutePath` for none, even with 0 vias
   placed) — had **no de-duplication at all**.
3. `_route_segment_3d` (`astar_core.py`, the via-aware fallback tier) —
   same exact-equality-check bug as (1).

Since a pad is essentially never exactly on a grid-cell center, this
manufactured a near-zero-length **spur**: the path runs grid-aligned
(0.1mm or 0.1414mm per step) up to the last full grid cell, then jumps a
much shorter, essentially arbitrary-direction distance to the exact
terminal. The interior angle at that spur's base vertex is `180 - turn`,
where `turn` is the (essentially random) angle between the grid-aligned
approach and the short jump to the exact terminal — reliably landing below
90 degrees.

### Proof, not guesswork

**Synthetic, deterministic repro** (`_astar_route_multilayer` called
directly on a fresh 60x60, 0.1mm grid, off-grid endpoints
`(0.37, 1.53) -> (4.62, 1.47)`, no other router stages involved):

Before the fix: vertex 1 (near start) at **45.00 degrees**, adjacent
segments 0.0283mm / 0.1000mm; vertex 44 (near goal) at **33.69 degrees
(critical)**, adjacent segments 0.1000mm / 0.0361mm. After the fix: those
same two vertices read 165.96 degrees and 164.05 degrees (both well above
the 90-degree threshold) — zero acid traps, and both path endpoints still
land exactly on the requested off-grid coordinates (no connectivity
regression).

**Live-board confirmation** (all 33 flagged traps from the pre-fix
`RoutingResults`, matched back to their net's raw path and the lengths of
both adjacent segments):

| Metric | Value |
|---|---|
| Traps with an adjacent segment shorter than one grid cell (0.1mm) | **33/33 (100%)** |
| Traps within 3 vertices of their net's start or end | **33/33 (100%)** |

Every single flagged trap is the terminal-snap spur, not a mid-route
zig-zag. No trap was found more than 3 vertices from a net endpoint on any
of the 37 routed nets (paths ranged from 16 to 2,991 vertices).

### What a real 45-degree grid transition looks like (the falsifier's alternative, checked directly)

The same synthetic repro's interior, grid-only vertices are all exactly
135 or 180 degrees (a diagonal-then-cardinal turn, or a straight run) —
never below 90. This directly confirms the falsifier's alternative
hypothesis ("every 45-degree grid transition registers as a trap") is
**false**: ordinary grid-aligned turns on this 8-connected grid are
geometrically obtuse (135 degrees) or straight (180 degrees), not acute.
Only the terminal-snap spur (a bug, not a grid-pitch property) produces
angles below 90.

## 3. The fix

**Chosen: fix at the generator (path-reconstruction terminal-snapping),
not a post-route corner-mitring pass or a cost-function penalty.**

`astar_core.grid_quantization_tolerance(cell_size)` returns
`cell_size * sqrt(2) / 2` — the *provable* maximum distance from any point
inside a grid cell to that cell's own center (half the cell diagonal).
This is derived from grid geometry, not tuned to make a count go down.

`astar_core.append_grid_path_point(points, point, tolerance)` and
`append_exact_terminal_point(points, point, tolerance)` merge a new point
into `points[-1]` instead of appending both when they are within
`tolerance` of each other **and on the same layer** (`_same_path_layer` —
a same-`(x, y)`-different-layer pair is a real via and is never merged).
The two functions differ only in which point wins when a merge fires:
`append_grid_path_point` keeps the existing (usually more-authoritative,
already-exact) point and drops the new grid-cell-center point;
`append_exact_terminal_point` keeps the new (exact terminal) point and
overwrites the preceding grid-cell-center point. Applied at all three call
sites identified in §2, plus the alternate-grid (THT via-detour) branch of
`_astar_route_multilayer` for consistency.

Tree-routed branches (`terminal_tree_execution.execute_terminal_tree`)
reuse `_astar_route` internally and inherit the fix without a fourth call
site.

### Options considered and rejected

1. **Forbid the acute transition during A* neighbour expansion.** Rejected
   — there is no acute transition being *proposed* by the search; 8-
   connected grid A* only ever emits 45/90/135/180-degree turns between
   grid cells (confirmed in §2's synthetic repro's interior vertices). The
   defect is manufactured entirely after the search, when the exact
   terminal is stitched onto the grid path. A neighbor-expansion-level
   fix would have nothing to forbid.
2. **Post-route corner-mitring/chamfer pass.** Rejected as the primary fix
   — it would treat a symptom (an already-bad vertex) after emitting
   geometry proven-in-advance to be extraneous, and risks also reshaping a
   genuine sharp bend it can't distinguish from the spur. The chosen fix
   prevents the double-vertex from being created at all, which is strictly
   more precise: it only ever removes a point proven (by construction) to
   be within grid quantization noise of its neighbor.
3. **Penalise sharp direction changes in the A* cost function.** Rejected
   — this is a §6.3 "cost field" per `docs/METHODOLOGY.md`, which requires
   a validated, monotone-with-a-threshold relationship before it can be
   trusted to steer the router; it is also the wrong layer, since (per
   option 1's finding) the search itself never proposes the bad
   transition — the cost function has nothing live to penalize. It would
   also run on every expansion (real router cost) to fix a bug that is
   free to fix once, in reconstruction.
