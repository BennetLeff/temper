## Method — three-way cross-check, not eyeballing coordinates

`endpoint_off_grid`'s own description field (`"Symbol pin or wire end off
connection grid"`) says only that a point isn't on KiCad's visual/snap grid
(default 1.27 mm / 50 mil) — nothing about whether that point is where two
things fail to touch. Two disconnected-but-visually-adjacent points would
show up as a *different* KiCad connectivity check (`pin_not_connected`, or a
net-name collision across two disjoint net codes), not this one. Rather than
assert that from KiCad's rule description alone, three independent
data sources were cross-checked:

1. **ERC JSON** (`kicad-cli sch erc --format json --severity-all`) — the
   163 flagged `(ref, pin)` pairs, and confirmation of 0 connectivity-error
   violations elsewhere in the same run.
2. **Schematic-exported netlist** (`kicad-cli sch export netlist --format
   kicadxml`) — KiCad's own exact-coordinate connectivity engine's answer to
   "what net is each pin actually on," independent of the visual grid.
3. **atopile-compiled netlist** (`make netlist` → `elec/build/default.net`)
   — the design's stated intent, independent of how `scripts/gen_schematics.py`
   happened to lay pins out on the page.

Three checks, each of which would have caught a real "looks connected,
isn't" defect:

- **Net-name collision check**: does any net *base label* (e.g. `SW_NODE`)
  map to more than one distinct compiled net code in the schematic export?
  **0 collisions** across all 139 schematic nets. A split net under a shared
  label is exactly the signature of "two wires that look joined by a common
  label but aren't" (the class this warning's own description in
  `docs/STRATEGY.md` worried about) — none found.
- **Connectivity-error check**: does ERC report any floating/unconnected
  pin anywhere in the full-hierarchy run? **0**, as above. If any of the 163
  off-grid pins were sitting at a coordinate its supposed wire *didn't*
  actually reach, KiCad's own `pin_not_connected` check — unrelated to the
  grid — would have caught it, because KiCad connectivity is exact-coordinate
  matching regardless of grid alignment.
- **Member-set cross-check** (the one that actually answers "is this pin on
  the net it should be on"): for each of the 163 `(ref, pin)` pairs, does
  the schematic net it's actually on (source 2) contain *exactly* the same
  `(ref, pin)` members as the atopile net of the same name (source 3)? Ran
  via `scripts/check_erc_off_grid_consequence.py` (added this session, see
  below) — **0 of 163 mismatches**. Every off-grid pin's schematic net is
  member-for-member identical to what the design source says it should be.

## Root cause (why they're off-grid, and why that doesn't matter here)

`scripts/gen_schematics.py:739-761` places every symbol on a
`GRID_X = 40.0 mm, GRID_Y = 30.0 mm` layout grid, chosen (per its own
comment) purely so adjacent components' 15.24 mm pin reach doesn't collide
visually — **not** chosen to be a multiple of KiCad's 1.27 mm (50 mil)
connection grid. `30.0 / 1.27 = 23.62…`, not an integer, so as row index
increases, each row's symbol origin — and therefore its pins — drift off
the standard schematic grid by a residual that accumulates mod 1.27 mm per
row. That's the entire mechanism: a layout-clearance grid that was never
meant to double as the wiring-hygiene grid.

Critically, `gen_schematics.py` computes wire/label endpoints from the
*same* arithmetic it uses to place the pin — it never "snaps to the nearest
half-inch" the way a human dragging a wire in the KiCad GUI would. Endpoint
coordinates are written as exact floats to both the symbol's pin and
whatever the generator connects it to, so pin and wire terminate at
bit-identical positions even when that position isn't a multiple of 1.27 mm.
That is *why* the off-grid warning fires (KiCad's hygiene check only cares
about the visual grid) and *why* it carries no connectivity risk on this
board specifically (KiCad's connectivity engine never used that grid to
begin with — it was always exact-coordinate matching, confirmed empirically
above). The risk the warning exists to flag — a human later editing this
schematic with grid-snap enabled and silently pulling a wire off an
off-grid pin — is real in general, just not evidence of an *existing*
defect today.

## What this does *not* establish

- This is a **grid-hygiene / connectivity-existence** check, not a circuit
  correctness check. It says nothing about whether a resistor divider's
  *value* is right, whether a comparator threshold is well-derived, or
  whether a net that's correctly wired is nonetheless the wrong net to wire
  (a design decision, not an ERC-detectable fact). `docs/STRATEGY.md`'s own
  caveat about ERC ("validates schematic hygiene, not circuit correctness")
  still applies fully.
- It only checked `(ref, pin)` endpoints, i.e. `endpoint_off_grid`
  violations whose item description matched `Symbol <ref> Pin <pin>`. All
  163 current entries were of this form (confirmed: the parser matched 163
  of 163) — there were no bare *wire*-endpoint-off-grid entries this run to
  separately check, but a future run that produces one would need the same
  treatment via coordinate proximity rather than `(ref, pin)` identity.
- It does not re-validate `lib_symbol_issues` or `footprint_link_issues`,
  the board's other two ERC warning categories — out of scope for this task.

## Reproducing this

```
make netlist                                                        # elec/build/default.net
<kicad-cli 10.0.5> sch erc --format json --severity-all \
    -o /tmp/temper_erc.json pcb/temper.kicad_sch
<kicad-cli 10.0.5> sch export netlist --format kicadxml \
    -o /tmp/temper_netlist.xml pcb/temper.kicad_sch
uv run python scripts/check_erc_off_grid_consequence.py \
    --erc-json /tmp/temper_erc.json \
    --sch-netlist-xml /tmp/temper_netlist.xml
```

`scripts/check_erc_off_grid_consequence.py` (added this session, manifest
entry in `scripts/manifest.yaml`) automates the member-set cross-check and
domain triage above; exit 0 means every off-grid pin's schematic net
matches its atopile net member-for-member (as found here), exit 1 prints
each mismatch with its net domain for immediate triage, exit 2 is a
fail-closed gate error (missing/empty/unparsable input — never silently
"0 violations"). It is **not** wired into CI: it needs a working `kicad-cli`
to regenerate its two KiCad-derived inputs, and this session had to build
one from a PPA `.deb` in userspace to get it at all — not something to
assume is available in every CI runner or agent sandbox without the same
provisioning step. It is meant to be re-run by hand (or from a `/loop`) the
next time this warning count moves, not as an automatic gate.
