# Dead-Parameter and Silent-Wiring-Gap Sweep — Requirements

**Date:** 2026-07-23
**Status:** Requirements — ready for planning

## Problem

The `route_pcb()` `design_rules` wiring bug fixed earlier today (see `docs/plans/2026-07-23-005-fix-router-design-rules-wiring-plan.md`) had a specific, recognizable shape: a parameter is accepted, looks used by inspection (docstring, naming, or partial use for one purpose), but is never actually forwarded to the code that would make it change behavior. Two symptoms of the same shape (`_seed`, `_net_class_assignments` on `route_pcb()`) were found first; the deeper `design_rules`-never-reaches-the-A*-engine bug was the same pattern at a larger scale. This sweep asks: does this pattern recur elsewhere in `router_v6`, and is it worse in the places nobody's looked at recently?

Two variants of the pattern, both confirmed to exist:
1. **Leading-underscore parameter, never read in the function body** (the `_seed` shape) — cheap to grep for, unambiguous once found.
2. **Parameter stored or partially used, but the specific mechanism a caller would expect it to drive is never wired** (the `design_rules` shape) — requires tracing, not just grepping; static reading alone previously produced a fix that looked correct and was a runtime no-op (confirmed only by an actual probe during a live `route_pcb()` run).

## Verified current state

### `V6RouterAdapter` (`_adapter_core.py`) — NOT dormant; has real callers this sweep's grep missed

**Correction (post-review):** the original pass here searched only `packages/temper-placer/src/` and `packages/temper-placer/tests/` and concluded "never instantiated anywhere" / "dormant" / "unreachable from any production path." That conclusion was wrong — the search scope was too narrow. Verified real callers exist:

- `scripts/internal_route.py:499` — `V6RouterAdapter.from_board(...)`, invoked by the `route` target in the repo's `Makefile` (`uv run python3 scripts/internal_route.py ...`). Per `scripts/manifest.yaml`, this script is `disposition: shell-invoked`, `category: keep`, `last_run: '2026-06-22'` — 31 days stale as of today (2026-07-23), i.e. right at this project's own 30-day sunset-warning threshold, not actively run but not dead either.
- `packages/temper-placer/benchmarks/routing_benchmark.py:171,331,344` — three call sites via the `MazeRouter` alias (`from temper_placer.router_v6.adapter import MazeRouter`). The original grep searched for the literal string `V6RouterAdapter` and missed these because this file only ever uses the `MazeRouter` name.
- Neither call site is referenced by any `.github/workflows/` job — this is not a CI-automated path. So "dormant" is wrong, but "live in production" would overstate it too: it's a real gap sitting in a manual dev command (`make route`) and a benchmark script, exploitable the moment either actually runs, not something exercised automatically every PR.

It is a "MazeRouter-compatible" shim implementing an older router interface (`core/interfaces.py`'s `RouterProtocol`), also referenced in one narrow regression test (`test_adapter_repair_verification.py`, which only checks `_build_temp_pcb` is callable, not that routing behaves correctly — so even the real callers above have no test coverage confirming their routing output is correct).

Despite being dormant, it has the identical wiring gap `route_pcb()` had, and worse:
- `from_board(...)` accepts `_congestion_via_discount`, `_min_clearance`, `_drc_oracle`, `_strict_mode`, `_wrong_way_penalty` — **none are passed to `cls(...)` in the return statement** (`_adapter_core.py:96-110`). Pure interface-compatibility padding, silently discarded.
- `block_components(..., _margin: float = 0.5)` and `block_pads(..., _netlist, _trace_width, _clearance)` — none referenced in either method body (`_adapter_core.py:112-127`).
- `rrr_route_all_nets(...)` accepts thirteen parameters (`_assignments`, `_max_iterations`, `_history_increment`, `_history_decay`, `_p_scale_start`, `_p_scale_step`, `_progress_callback`, `_incremental`, `_validate_final`, `_pin_positions_overrides`, `_component_margin`, `_soft_c_spaces`, plus `_cost_maps` which *is* used). Only `_cost_maps` is read (for a thermal-field seam, docstring-acknowledged as "the dormant `_cost_maps` seam"). The other twelve — all named for rip-up-reroute (RRR) convergence tuning, matching the method's own name — do nothing; the method calls `RouterV6Pipeline.run()` exactly once with none of them.
- **Confirmed, `route_pcb()`-identical gap:** `self._design_rules` (stored from `from_board`'s real `design_rules` parameter in `__init__`) is **never referenced anywhere in `rrr_route_all_nets`'s body**. The method builds a `RouterV6Pipeline` with no `layer_constraints`, no `enable_all_pad_tree`/`enable_zone_pours`, and calls `pipeline.run(Path(temp_path))` with zero `net_class_assignments`/`net_classes` kwargs — the exact call shape `route_pcb()` had before today's fix. If this class is ever instantiated for real routing, it inherits the flat-0.2mm-clearance bug in full, with no zone-pour or connectivity-verifier support at all.

### `_astar_route_with_ripup` (`_astar_reconstruct.py:1073`) — two genuinely dead params, one real one

- `_routed_paths: dict[str, RoutePath | RoutePath3D]` (positional) and `_pad_centers: dict[...]` — **neither referenced anywhere in the function body** (verified: the function is the last in the file, full body checked to EOF at line 1169). Likely vestigial from a refactor that moved the logic they'd have fed (rip-up detection now goes through grid net_id lookup via `id_to_net`, not a passed-in `routed_paths` dict; pad-avoidance is handled by the caller's `_unblock_net_pads` before this function is invoked). Probably benign dead code, not a behavior bug — but confirm before assuming, per the R2 discipline below.
- `_design_rules: DesignRules` (positional) **is** used — forwarded once, to the `_route_segment_3d` 3D-fallback tier's `design_rules=` kwarg. This is the same fallback tier already confirmed correctly netclass-aware before today's fix (it independently resolved `net_rules.clearance_mm` — the plain path's one pre-existing correct spot). Not dead; naming convention (underscore) is misleading here, since it *is* consumed.

### `RouterV6Pipeline`'s stored-but-unread `enable_connectivity_verifier`

`_pipeline_core.py:160` sets `self.enable_connectivity_verifier = enable_connectivity_verifier` in the constructor — **this attribute is never read anywhere else in `_pipeline_core.py` or `_pipeline_route.py`.** Lower severity than the above: the actual connectivity-verifier feature still works, because `route_pcb()` threads `enable_connectivity_verifier` to `_build_routing_result(...)` as a *separate*, independently-passed parameter (`_adapter_convert.py:231/253`, consumed at line 813), bypassing the pipeline object entirely. So the feature isn't broken — but the pipeline's own copy of the flag is redundant, unread plumbing that could confuse a future reader into thinking `self.enable_connectivity_verifier` gates something inside the pipeline's stages. It doesn't.

### What a grep-only pass would have missed

The design_rules bug itself was **not** underscore-prefixed and would not have been caught by a naive underscore grep — it required tracing "is this object's content actually consulted downstream," which is exactly variant 2 above. This sweep's method (2) is inherently incomplete: it depends on knowing which objects are "supposed to" flow somewhere, which requires reading docstrings/comments claiming a purpose and checking the claim. A full pass over every parameter in the package for variant 2 was out of scope for this sweep's time budget; only the seams adjacent to today's confirmed bug (`enable_connectivity_verifier`, the two pipeline `.run()` call sites) were checked.

## Requirements

- **R1 — Fix or retire `V6RouterAdapter`'s design_rules gap; this is active, not preventative.** It has real callers (`scripts/internal_route.py`'s `make route` target, `packages/temper-placer/benchmarks/routing_benchmark.py`), so this is fixing currently-reachable incorrect behavior, not guarding against a hypothetical future activation. Two constraints any fix must account for: (a) deleting `V6RouterAdapter`/`MazeRouter` outright would break the Makefile `route` target and the benchmark suite — not a clean no-op removal; (b) `scripts/internal_route.py` is 31 days past its last recorded run per `scripts/manifest.yaml`, one day from this project's own 30-day sunset-warning — worth checking with whoever owns it (`owner: unassigned` currently) whether it's still wanted before investing in fixing vs. formally sunsetting it. Options remain the same as before: (a) fix its wiring to match `route_pcb()`'s corrected pattern, or (b) sunset it deliberately (update the manifest, remove the Makefile target) rather than leaving a known-broken, occasionally-used path in place by default.
- **R2 — Confirm `_astar_route_with_ripup`'s `_routed_paths`/`_pad_centers` are genuinely dead, not silently-broken.** Static reading says unreferenced; today's design_rules "fix" looked correct by inspection too and was a no-op. Verify with a cheap runtime check (e.g., a probe confirming rip-up decisions are equally correct with vs. without a populated `_routed_paths` argument) before deleting them, in case they're read via some indirect mechanism (e.g., mutated in place by a helper) that a plain reference-grep misses.
- **R3 — Remove or wire `RouterV6Pipeline.enable_connectivity_verifier`.** Either delete the stored-but-unread constructor attribute (the real flag already flows correctly via `route_pcb()`'s separate parameter), or, if the intent was for pipeline-internal stages to someday consult it directly, wire that instead of leaving a second, silently-inert copy of the same flag.
- **R4 — Decide the fate of `rrr_route_all_nets`'s twelve unused RRR-tuning parameters.** If `V6RouterAdapter` survives R1, these need the same treatment: either wire them to something real or remove them so the signature stops promising rip-up-reroute tuning it doesn't perform. If `V6RouterAdapter` is deleted, this is moot.
- **R5 — Extend variant-2 tracing (parameter used-for-one-purpose-but-silently-not-another) beyond the seams checked today.** This sweep only checked `enable_connectivity_verifier` and the two `.run()` call sites adjacent to the design_rules fix. A full pass would mean: for every object threaded through more than one pipeline layer (`layer_constraints`, `thermal_flat`/`thermal_weight`, `enable_all_pad_tree`, `enable_zone_pours`), confirm each one is actually read at *every* layer it's supposed to affect, not just the first. Scope this as its own follow-up rather than assuming today's sweep was exhaustive — it wasn't; variant 2 requires judgment per-parameter, not a mechanical grep, and time-boxing this session's pass means later layers (deep inside `_pipeline_route.py`'s stage3/stage4 orchestration) were not individually re-verified.

## Scope boundaries

**In scope:** cataloguing dead/silently-broken parameters found by this sweep (done, above); deciding priority (R1 > R2/R3 > R4/R5, since R1 is the only one with a live safety-relevant blast radius *if* the dormant class is ever activated).

**Out of scope:** implementing any of R1–R5 — this document is requirements only, per the sweep's own directive. **Out of scope:** a fully exhaustive variant-2 trace of every multi-layer-threaded parameter in `router_v6` (flagged as R5, not attempted here — time-boxed). **Out of scope:** anything outside `router_v6`/its direct adapters (`adapters/router_v6_stage_adapter.py` was checked only for whether it calls `V6RouterAdapter`/`rrr_route_all_nets` — it does not; it uses `RouterV6Pipeline` directly, and was not separately audited for its own wiring gaps beyond confirming it isn't a caller of the dormant path).
