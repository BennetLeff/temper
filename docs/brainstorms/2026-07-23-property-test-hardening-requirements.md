# Router Design-Rules Representations and Forced-Segment Bypass — Property-Test Hardening Requirements

**Date:** 2026-07-23
**Status:** Requirements — ready for planning

## Problem

Two fragile areas were found in the same-day investigation that root-caused the `enable_all_pad_tree` DRC regression (`docs/plans/2026-07-23-005-fix-router-design-rules-wiring-plan.md`):

1. **Three parallel, only-partially-reconciled representations of "netclass rules."** `route_pcb()`'s rich caller-supplied `design_rules` was silently never reaching the A* engine; the fix added `_to_stage0_netclass_rules()` as a conversion adapter between two of the three shapes. This investigation found the adapter itself has the same failure signature it was built to close: it silently drops a field and silently fabricates flat defaults for unrecognized input, rather than failing loudly.
2. **The forced-segment fallback is invisible to every downstream consumer.** When plain A* (not tree-executed nets) cannot find a legal path, it draws a raw straight line with zero clearance/obstacle checking, and reports `success=True`. `forced_segment_count` is tracked per-path but the aggregate (`total_forced_segments`) is dead code — read nowhere else in the codebase — and `RoutingResult`, the public output of `route_pcb()`, has no field exposing forced-segment nets at all. A caller cannot distinguish a clean route from a fabricated one.

Both are instances of the same underlying pattern: **a real invariant the rest of the system assumes holds (rules survive representation conversion; a "routed" net is actually clearance-legal) is not checked anywhere, so it silently stops holding and nothing notices.**

## Verified current state

### Area A — netclass rules representations

- `temper_placer.router_v6.stage0_data.NetClassRules` (`.clearance_mm`, `.trace_width_mm`, `.via_diameter_mm`, `.via_drill_mm`, `.diff_pair_gap_mm`, `.diff_pair_width_mm`, `.current_rating_amps`) is what the A* engine (`_astar_reconstruct.py`, `terminal_tree_execution.py`) consumes via `design_rules.get_rules_for_net()`.
- `temper_placer.core.netclass_rules_gen.NetClassRules` (pydantic, frozen: `.clearance`, `.trace_width`, `.via_diameter`, `.via_drill`, `.max_current_rating`, plus HV-specific fields `creepage_mm`/`voltage_v`/`safety_category`/`routing_strategy`/`via_cost_multiplier`/`layer_costs` with no stage0 equivalent at all) is the `netclass_rules.yaml` SSOT shape, used for layer_constraints and zone-pour emission.
- A **third** source exists and is live: `temper_placer.io._parse_nets._extract_design_rules()` extracts `net_classes`/`net_class_assignments` directly from the raw `.kicad_pcb` file's own embedded netclass sections (`extract_net_classes(pcb_content)` regex-based manual parse, or `ki_board.netClasses` from the kicad-parser library) — populating a `stage0_data.DesignRules` independent of anything YAML-sourced. On the current production board this returns empty (confirmed empirically this session: `assignments_size=0` pre-fix), but the mechanism is real and would activate for a board whose file embeds native KiCad net classes.
- `route_pcb()`'s fix (`_pipeline_core.py`) merges the caller's injected `net_class_assignments`/`net_classes` into `pcb.design_rules` via `.update()`, which runs **after** the native file-embedded extraction above — so injected (YAML SSOT) values win over native ones for same-named classes, by accident of ordering, not by an asserted contract. Nothing tests this precedence; nothing prevents it from silently flipping if the merge call ordering changes.
- The new `_to_stage0_netclass_rules()` adapter (`_adapter_convert.py:36-59`) drops `max_current_rating` → `current_rating_amps` entirely (no mapping line for it), and its `hasattr(rules, "clearance_mm")` duck-type check has no failure path: an object with neither `.clearance_mm` nor `.clearance` silently produces a `NetClassRules` seeded from the same hardcoded constants (`0.2`, `0.2`, `0.6`, `0.3`) that caused this session's original bug, rather than raising.

### Area B — forced-segment invisibility

- `_astar_reconstruct.py:809-825` (plain A*, `allow_forced_segments=True` for every net except tree-executed ones, `not tree_route_active` at line ~350): on legal-path failure, appends `goal_world` directly to `detailed_coords` with no obstacle/clearance check, sets `forced_segment_count`.
- `attempt_route`'s handling (line ~447): `if route_path.forced_segment_count > 0: return True, "congestion_forced", ...` — a forced segment is reported as `success=True`. The caller (`run_astar_pathfinding`'s outer loop) treats this identically to a clean success: added to `routed_paths`, never added to `failed_nets_set`.
- `PathfindingResult.total_forced_segments` (`_astar_reconstruct.py:114-116`) is the only aggregate, and it is **never read anywhere else in the codebase** (`grep -rn "total_forced_segments"` returns only its own definition).
- `RoutingResult` (`_adapter_types.py:94-112`, the public dataclass `route_pcb()` returns) exposes `completion_rate`, `unrouted_nets`, `drc_violations`, `congestion_regions`, `routed_pcb_content`, `enable_zone_pours`, `connectivity` — no forced-segment field of any kind. A caller of `route_pcb()` has no way to learn that a net it believes is cleanly routed was actually drawn as an obstacle-ignoring straight line.
- Tree-executed nets (`enforce_all_pad_tree=True`, >2 waypoints) do not have this specific gap — `allow_forced_segments=not tree_route_active` means they fail closed (`NetDisposition.INCOMPLETE`) instead. The gap is specific to the plain-path fallback, which is still the path taken by every 2-terminal net and by >2-waypoint nets whenever `enforce_all_pad_tree=False` (today's default).

## Requirements

- **R1** — Property test: `_to_stage0_netclass_rules()` round-trip totality. Generate arbitrary `core.netclass_rules_gen.NetClassRules` instances via Hypothesis (`st.builds` over `name`, `trace_width`, `clearance`, `via_diameter`, `via_drill`, `max_current_rating` — vary the optional fields including `None`), assert the stage0 output's `.clearance_mm`/`.trace_width_mm`/`.via_diameter_mm`/`.via_drill_mm`/`.name` equal the source's corresponding fields, **and** assert `.current_rating_amps == source.max_current_rating` (this last assertion fails today — the mapping line doesn't exist — making this test red-then-green work, not a test of already-correct behavior). Lives in `test_adapter.py` alongside the existing `_to_stage0_netclass_rules` call sites. **Would this have caught a real bug?** Yes — a live one, found during this scoping pass, distinct from but structurally identical to the session's original bug (silent data loss at a representation boundary).
- **R1b** (post-review addition — R1 as originally scoped ignored this) — `core.netclass_rules_gen.NetClassRules` has six fields with **no stage0 equivalent at all**: `creepage_mm`, `voltage_v`, `safety_category`, `routing_strategy`, `via_cost_multiplier`, `layer_costs`. `_to_stage0_netclass_rules()` silently drops all six on every conversion — R1's round-trip test as scoped only covers the fields that *do* map, which means it would pass today (once R1's `current_rating_amps` fix lands) while these six keep vanishing unremarked. This is the same silent-drop failure class the whole investigation is about, and `safety_category` (`"HV"`/`"LV"`/`"AC"`/`"iso"`) is specifically safety-relevant — dropping it during the exact conversion built to fix a safety-relevant clearance bug is a real gap, not a cosmetic one. Requirement: either (a) extend `stage0_data.NetClassRules` with slots for at least `safety_category` and `creepage_mm`/`voltage_v` (the three with clear safety relevance) so they survive conversion, or (b) if they're deliberately out of scope for the A* engine's concerns, assert that loudly in the adapter (e.g. log/raise on a non-default `safety_category` being dropped) rather than silently discarding it. **R6 below depends on whichever option is chosen** — it needs `safety_category` to survive into whatever the A* engine's forced-segment logic can see.
- **R2** — Property test: fail-loud on unrecognized shape. Generate objects lacking both `.clearance_mm` and `.clearance` (e.g. bare namespaces, objects with only some of the expected attributes) via `st.sampled_from`/`st.builds` over deliberately malformed shapes. Assert `_to_stage0_netclass_rules()` raises rather than silently returning a `NetClassRules` seeded from the hardcoded fallback constants. This is currently false (it fabricates silently) — implementing R2 requires changing `_to_stage0_netclass_rules()` to raise on an unrecognized shape instead of `getattr(..., default)`, which is a real code change, not just a test addition. **Would this have caught this session's bug?** This is the same failure family one layer deeper — the adapter meant to fix "silently falls back to flat defaults" can itself silently fall back to flat defaults given a bad input. Highest-value item in Area A.
- **R3** — Property test: injected assignments are never silently dropped. Generalizes the already-shipped `test_route_pcb_forwards_real_netclass_rules_to_pipeline_engine` (which sweeps one clearance value on one net) to a Hypothesis-generated **set** of `{net_name: class_name}` assignments of varying size, asserting every entry survives intact from `route_pcb(design_rules=...)` through to what `pipeline.run()` is called with. **Would this have caught this session's bug?** Yes, directly — this is R3/R5's original test generalized.
- **R4** — Regression test (not property-based; a single deterministic scenario is sufficient): assert the precedence between native-file-embedded netclasses and `route_pcb()`-injected ones is explicit and intentional, not accidental ordering. Construct a `.kicad_pcb` fixture with an embedded `(net_class ...)` section for a class name that collides with an injected class of the same name but different clearance value; assert the injected value wins (matching current behavior) — or, if the team decides native-file values should take precedence instead, that this is a deliberate decision recorded here, not silent. **Would this have caught this session's bug?** No — this is an adjacent gap found while investigating Area A, not part of the original bug's causal chain. Flagged because it's the same "silent representation conflict" shape and is currently completely untested.
- **R7** (post-review addition — this doc originally buried this in Scope Boundaries as a footnote; a reviewer correctly flagged that treating an architectural problem purely as a testing problem understates it) — **Evaluate consolidating the three netclass-rules representations, not only testing around them.** R1-R4 make the *existing* three-way split (`stage0_data.NetClassRules`, `core.netclass_rules_gen.NetClassRules`, native `.kicad_pcb`-embedded classes) safer to operate with — they pin down current behavior and catch silent data loss at the boundaries. They do not address *why* three representations exist or whether that's still justified. This is a real, separate question this doc should surface explicitly rather than wave off: is the native-file-embedded extraction path (`io/_parse_nets.py::_extract_design_rules`) still needed now that `route_pcb()` injects the YAML SSOT directly, or is it vestigial from before the SSOT existed? If vestigial, removing it (rather than just testing its precedence behavior per R4) would eliminate one whole representation and its silent-precedence-conflict risk at the source, which is a stronger fix than any test can be. This requirement doesn't replace R1-R4 (tests are still needed regardless of the outcome) — it makes explicit that "add tests" and "reduce representations" are different, complementary responses to the same root problem, and this doc had only scoped the former.
- **R5** — Requirements/design test: `RoutingResult` must expose forced-segment visibility. Add a field (e.g. `forced_segment_nets: list[str]`) to `RoutingResult`, threaded from `PathfindingResult.total_forced_segments`/per-path `forced_segment_count` through `_build_routing_result`. Write the test first (asserting the field exists and is populated for a net forced into a straight-line fallback via a constructed all-obstacle grid, reusing the wall-obstacle pattern already used in `test_all_pad_tree_routing.py`'s `grid.grid[:, 8] = 1`), confirm it fails (field doesn't exist today), then implement. **Would this have caught this session's bug?** Not the DRC shorting numbers directly (that needs a real `kicad-cli` DRC pass), but it would have caught — cheaply, in a unit test, without ever running KiCad — the structural reason nobody noticed: forced/fabricated nets are indistinguishable from clean ones at every level the router itself reports through.
- **R6** — Property test: HighVoltage-class forced-segment escalation. **Corrected (post-review): use the existing `safety_category` field (`"HV"`/`"AC"`), not an arbitrary numeric clearance threshold.** The originally-scoped "≥1.0mm" cutoff was ungrounded — a coincidental proxy for "probably HV" rather than the actual classification this codebase already carries. `safety_category` is precisely the field meant for this distinction; using it instead of a magic number is both more correct and self-documenting. This requirement is **gated on R1b**: `safety_category` must survive `_to_stage0_netclass_rules()` before the A* engine's forced-segment logic can see it at all — sequence R1b first. Reuse R5's Hypothesis clearance-sweep strategy; for nets whose `safety_category` is `"HV"` or `"AC"`, force a legal-path failure and assert the net does **not** silently return `success=True, reason="congestion_forced"` with no differentiation. Three concrete options, not two — the originally-scoped list ("raise, return a distinguishable status, or populate R5's field") omitted the simplest one:
  1. **Fail-closed (simplest, and already precedented in this exact codebase):** set `allow_forced_segments=False` for HV/AC-class nets specifically, mirroring `allow_forced_segments=not tree_route_active` — tree-executed nets already fail to `NetDisposition.INCOMPLETE` instead of fabricating copper; extending the same `False` gate to safety-critical netclasses on the plain path requires no new status type, no new field, just reusing the flag that already exists for exactly this purpose.
  2. Raise or return a distinguishable failure/warning status (more invasive — a new signal type).
  3. Populate R5's `forced_segment_nets` field as a minimum bar, leaving the net formally "successful" but visible to a downstream gate.

  Option 1 should be evaluated first, not assumed away — it's the least code, reuses an established pattern, and matches this codebase's stated fail-closed/`UNMEASURED` discipline (`docs/solutions/architecture-patterns/two-tier-acceptance-gate-unsat-surfacing-2026-07-05.md`) most directly of the three. **Would this have caught this session's bug?** Yes, most directly of everything scoped here — `SW_NODE` (HighVoltage) is among the nets that persistently shorted post-fix; enforcing "HV/AC nets must not silently forced-segment" would have forced this exact net class to be visibly flagged (or honestly left unrouted) instead of silently drawn as an out-of-clearance straight line.

## Scope Boundaries

**In scope:** the property/regression tests above (R1-R6), written TDD-first (red before any implementation change) per this session's established practice, plus R7's evaluation (not implementation) of representation consolidation.

**Out of scope:**
- Deciding *how* R2/R5/R6 should behave once made loud (raise vs. warn vs. new `NetDisposition`-style status) — these requirements establish the test and the invariant; the exact failure-mode API is an implementation decision for whoever picks this up, consistent with `docs/plans/2026-07-23-005`'s R8 already flagging this as its own decision point (fail-closed to `INCOMPLETE` vs. keep-but-flag).
- *Implementing* the consolidation R7 evaluates (R7 is a decision/evaluation step — actually merging or removing a representation is a larger follow-up, not scoped here).
- Any other pinch points beyond Areas A and B — this doc does not attempt a broader sweep (that's the dead-parameter-wiring-sweep fork's job).
