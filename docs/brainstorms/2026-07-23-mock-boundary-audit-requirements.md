# Mock-Boundary Audit: RouterV6Pipeline and Related Config-Bridging Seams — Requirements

**Date:** 2026-07-23
**Status:** Requirements — ready for planning

## Problem

The `design_rules` wiring bug (found and fixed the same day this doc was written — see `docs/plans/2026-07-23-005-fix-router-design-rules-wiring-plan.md`) survived undetected because the only test near the break, `test_route_pcb_e2e_threads_design_rules` (`packages/temper-placer/tests/router_v6/test_adapter.py`), mocked `RouterV6Pipeline` out entirely and asserted only on the writer's zone-pour output — never on what was actually passed *into* `pipeline.run()`. The mock's presence in a passing test suite created the appearance of coverage over a boundary that was, for the specific concern that broke, unverified. This is a general risk pattern, not a one-off: any test that fully mocks a component and only checks the mock's *return value* (not its *call arguments*) proves the caller can survive a crash-free round trip through the mock, and nothing about whether the caller sends the mock — or the real thing — sensible input.

## Verified current state

Grepped `packages/temper-placer/tests/` for `patch(`/`MagicMock`/`Mock()` targeting `RouterV6Pipeline`, `route_pcb`, `parse_kicad_pcb_v6`, `execute_terminal_tree`, and `_write_routes_to_content`. Four sites mock `RouterV6Pipeline`; nothing mocks the other four.

1. **`test_adapter.py:210`** (`TestRoutePcbLayerConstraintsResolution._patched_pipeline`, used by 3 tests) — mocks `RouterV6Pipeline`, but *does* spy on `mock_pipe_cls.call_args` to assert `layer_constraints` construction kwargs are correctly populated/empty/warned-on. This is the right pattern, already in place — but it only covers `layer_constraints`, one of the several things `design_rules` is used for. It does not (and structurally cannot, since it's a constructor-kwargs check) cover anything passed to `.run()`.
2. **`test_adapter.py:455`** (`test_route_pcb_e2e_threads_design_rules`) — mocks `RouterV6Pipeline` entirely, asserts only `result.routed_pcb_content` (the writer's zone-pour clearance output). Never inspects `mock_pipe.run.call_args`. This is the exact test that should have caught the bug and didn't — its name promises "threads design_rules" but only verifies one specific downstream consumer (the writer), not the pipeline invocation itself.
3. **`test_adapter.py:~530`** (`test_route_pcb_forwards_real_netclass_rules_to_pipeline_engine`, added same day as the fix) — spies on `mock_pipe.run.call_args` for `net_class_assignments`/`net_classes`. This closes the specific gap found. Good pattern, now established in this file.
4. **`packages/temper-placer/tests/placer/cp_sat/test_router_integration.py:216`** (`test_route_pcb_with_placements`) — mocks `RouterV6Pipeline`, sets `mock_pipe.run.return_value = mock_result`, asserts only `result.completion_rate == 0.85`. **This is the return-value-only anti-pattern, live and uncorrected.** It proves `route_pcb()` passes through whatever the pipeline returns; it proves nothing about what `route_pcb()` sends to `RouterV6Pipeline(...)` or `.run(...)` for the `placements` code path this test exists to cover. Note it also doesn't pass `design_rules` at all, so it wouldn't have caught this specific bug regardless — but it's the same shape of blind spot for whatever *this* test's actual subject (placement application) needs verified.

A second, independent blind spot (not a mock, a parsing gap): **`parse_kicad_pcb_v6`'s own extraction of `design_rules` from a real `.kicad_pcb` file is untested.** `test_stage0_loader.py::test_parse_kicad_pcb_v6_basic` is a stub (`pass`, no body). Every other test that calls `parse_kicad_pcb_v6` on a real board (`test_routability_check.py`, `test_capacity_check.py`, `test_stage2_golden_parity.py`, `test_net_ordering.py`, etc.) uses the result for placement/topology/capacity checks, never asserting on `pcb.design_rules.net_class_assignments`/`net_classes` content. This matters because it's the *other* half of the three-`DesignRules` story (`core.design_rules.DesignRules` loaded from YAML vs. `router_v6.stage0_data.DesignRules` built by parsing vs. whatever the raw `.kicad_pcb` file's own `(net_class ...)` sections contain) — nobody has verified whether real KiCad-native netclass sections, if present in the file, get extracted at all, independent of the explicit post-parse injection this session's fix added. If they don't, that's fine today (the fix bypasses native parsing entirely), but it's an unverified assumption baked into "R2: reconcile the three representations" from the `2026-07-23-005` plan, and worth confirming rather than continuing to assume.

## Requirements

- **R1** — Add a `.run()` call-args assertion to `test_route_pcb_e2e_threads_design_rules` (or split it) so the zone-pour-focused test and the pipeline-wiring-focused test are separately, explicitly covered — currently one test's name claims broader coverage than its assertions provide.
- **R2** — Fix or replace `test_route_pcb_with_placements` (`test_router_integration.py:216`) to assert on `RouterV6Pipeline(...)` constructor kwargs and/or `mock_pipe.run.call_args`, verifying `placements` (and, ideally, `design_rules`) are actually forwarded correctly, not merely that the mock's return value survives the round trip.
- **R3** — Write a real (non-mocked) test for `parse_kicad_pcb_v6` that parses an actual `.kicad_pcb` fixture with known embedded netclass data (if any exists) and asserts what lands in `pcb.design_rules.net_class_assignments`/`net_classes`. **Gated (post-review): this depends on a decision `2026-07-23-005`'s "Dependencies/Assumptions" section already flagged as open** — whether `parse_kicad_pcb_v6` native extraction or `route_pcb()`'s post-parse injection is the intended long-term mechanism. If injection wins, this test is documenting (and locking in) a code path that may be deliberately left thin or superseded — effort spent here could be wasted or need rework once that decision lands. Sequence this *after* that decision, not before; if written now, keep it to the cheap documentation-test form only (asserting today's actual behavior, whatever it is) rather than investing in comprehensive fixture coverage.
- **R4** — Replace the still-stubbed `test_parse_kicad_pcb_v6_basic` (`test_stage0_loader.py:9-12`, currently `pass`) with a real assertion — either delete it (dead test, no value) or give it actual content. **Corrected harm mechanism (post-review):** this isn't primarily a "false coverage confidence" problem (a body-less `pass` test contributes nothing to coverage percentage and always trivially passes) — the real harm is **name-squatting**: the function name `test_parse_kicad_pcb_v6_basic` occupies the slot a real "does basic parsing work" test should have, so a future contributor grepping/scanning test names sees it "exists," and either assumes it's covered or has to notice it's empty before adding real coverage under a different name. Deletion alone fixes the name-squatting harm; it doesn't require replacing the stub with content unless basic-parsing coverage is independently wanted.
- **R5** — Establish a lint/review convention (not a runtime check): any test that does `patch(...RouterV6Pipeline...)` or similar full-object mocking of a router_v6 entry point must either (a) assert on the mock's call arguments for the specific behavior under test, or (b) have an explicit comment noting which sibling test covers the real, non-mocked path for the same concern. **Caveat (post-review): a convention with no automation behind it is unenforceable** — the exact same review process that let the `test_parse_kicad_pcb_v6_basic` stub and the `test_router_integration.py:216` return-value-only pattern through would just as easily miss a missing comment. If this is worth doing, it needs a cheap mechanical backstop to have teeth: e.g. a grep-based CI check (matching this repo's existing `scripts/manifest.yaml`/`check_manifest_gate` pattern) that flags any `patch(...RouterV6Pipeline...)`-containing test file with no `call_args` reference and no `# sibling-coverage:` comment tag. Without that, downgrade this from "requirement" to "aspiration" — worth writing down, not worth treating as done once documented.

## Scope Boundaries

**In scope:** the four specific test-coverage gaps above (R1-R4) and the review-convention proposal (R5).

**Out of scope:** auditing mock usage outside `router_v6`/`placer/cp_sat` router-adjacent tests (e.g., firmware codegen tests, PCL parser tests) — those are different subsystems with their own risk profiles; this doc is scoped to the exact area the `2026-07-23-005` bug came from.

**Out of scope:** actually writing R1-R4's test code — this is requirements-gathering only, per the parent conversation's instruction not to implement.

**Deferred:** a broader "does mocking hide real integration failures" sweep across the rest of the `temper-placer` test suite (firmware, DRC, PCL, placement) — worth doing eventually given how much this pattern paid off here, but a much larger effort than this session's scope.
