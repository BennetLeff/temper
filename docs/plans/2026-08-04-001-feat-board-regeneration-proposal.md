# Board Regeneration for the WASM Verification Tier - Proposal

## Goal Capsule

- **Objective:** Answer `docs/plans/2026-08-03-002-feat-wasm-verification-tier-plan.md` Q2 — what automated board regeneration under R3 consists of, and whether it runs per-change or on a schedule — with an investigation grounded in the `Makefile`, the placer/router source, and the repo's own DRC-ratchet machinery. This document is analysis only; nothing in it builds a pipeline.
- **Headline finding:** `make build`'s dependency chain (`netlist footprints schematics route drc`, `Makefile:34`) contains no placement step. `footprints` is a stub that only creates a directory and echoes (`Makefile:54-59`). `route` reads footprint positions off whatever board `PCB_FILE` points at and only routes traces (`Makefile:78-80`; confirmed by `docs/evidence/2026-07-27-router-determinism.md:14-17`, "empty placements --> reads existing positions off disk, no CP-SAT placement"). Every change to `pcb/temper.kicad_pcb` in the last two weeks of git history (`de59c0458`, `0f0a13412`, `55226f8ad`, `27ea686c5`) was a *placement* change — a scoped CP-SAT re-solve invoked directly from Python, with human judgment on which candidate to write. `make build` cannot regenerate that. Automating `make build` on a trigger would not track "whenever the placer... harness changes" (R3's own stated reason for the tier); it would track only netlist/schematic/routing changes, which is a narrower harness than the one the plan names.
- **Scope:** Answers 1-4 below and recommends one option under 5. No workflow, `Makefile`, or board file was modified or executed to produce this document.

## 1. What does regeneration actually consist of?

`Makefile:34`: `build: netlist footprints schematics route drc`.

| Target | What it does | Needs | Deterministic? |
|---|---|---|---|
| `netlist` (`Makefile:43-48`) | `uv tool run atopile ... build`, then stamps the artifact (`scripts/write_build_stamp.py`) | `atopile` (network-fetched tool), and per `.github/workflows/python-tests.yml:1091` it invokes `kicad-cli` internally in CI containers (`continue-on-error: true` there today, "hard-fail after 2026-09-01") | Not separately measured here; CI caches it by content hash of `elec/src/**` (`.github/workflows/python-tests.yml:527-537`), and the comment at `python-tests.yml:682-684` records it running in "well under a minute" of the ~225s job prologue on a cache miss. |
| `footprints` (`Makefile:54-59`) | `mkdir -p pcb/footprints.pretty` and an `@echo` | nothing | trivially deterministic — it does no real work; the comment on line 56 says this is interim until "FaC is fully integrated." |
| `schematics` (`Makefile:50-52`) | `python3 scripts/gen_schematics.py`, driven by the netlist | Python only | Not measured here; a `--check --no-oracle` variant runs in CI today as a drift check against committed `.kicad_sch` files (`.github/workflows/python-tests.yml:1088-1092`), currently `continue-on-error: true`. |
| `route` (`Makefile:75-80`) | `scripts/internal_route.py $(PCB_FILE) -o $(ROUTED_PCB)` — router V6 + a CaDiCaL SAT solve for track routing, reading **existing footprint positions off disk** | Python, `ortools`/CaDiCaL, `jax.numpy` (`scripts/internal_route.py:13`) for a cost-field step (line 588-589) | **Yes, as of 2026-07-27**, conditionally. `docs/evidence/2026-07-27-router-determinism.md` root-caused a prior nondeterminism to `uuid.uuid4()` tstamp generation (fixed by a deterministic `uuid5`+counter scheme) and proved 5 fresh-process runs byte-identical (`sha256 ae049ae4...`, lines 120-125), plus 2 more with pinned `PYTHONHASHSEED`. **But** those 17 runs never reproduced the *committed* board's 53.1% net-completion rate — every run produced 37.5% (36/96 nets), the low end of a historically observed 37.5%-53.1% range (lines 138-148). | `drc` (`Makefile:82-84`) | `kicad-cli pcb drc --exit-code-violations $(ROUTED_PCB)` | `kicad-cli` (native, not portable to `wasm32` — already out of scope per the WASM plan's Scope Boundaries, `docs/plans/2026-08-03-002-...md:99`) | **Notably weaker than the repo's own measurement standard.** The Makefile's invocation omits `--all-track-errors`. `packages/temper-placer/src/temper_placer/validation/_drc_api.py:305-320` documents that flag as load-bearing for determinism: without it, `clearance` varied 334-343 and `shorting_items` 148-174 across 11 runs on a byte-identical board; with it, `shorting_items`/`tracks_crossing` are stable and `clearance` varies "by at most 1." `AGENTS.md:56-71` and every board-write evidence doc (`docs/evidence/2026-07-31-k2k3-relay-swap-placement.md:73-102`, `docs/evidence/2026-08-02-k3-swap-and-board-write.md:77-116`, etc.) treat a single DRC run as insufficient and require **120 samples**, taking the observed range, before trusting a count. `make drc` as written runs `kicad-cli` once with no `--all-track-errors`, which is the exact invocation the codebase's own evidence says is not reproducible. |

**Placement — the part actually missing from `make build`:** no target builds it. The repo's real placement changes go through `run_clearance_repair_solve` / `solve_placement` (CP-SAT, `packages/temper-placer/src/temper_placer/placer/cp_sat/`), invoked ad hoc with hand-picked `free_refs`, a displacement cap, and a fixed seed (e.g. "seed 0, 180s/round, max 4 rounds," `git show de59c0458` commit body), then evaluated against multiple candidates (Run A vs. Run B in the same commit) before one is written. `docs/evidence/2026-08-01-ortools-cpsat-spike.md:171-185` states the determinism bound precisely: bit-identical only for solves that terminate deterministically (`OPTIMAL`/`INFEASIBLE`/`FEASIBLE`) under frozen params (`num_search_workers` 8 in `model.py:436` or 4 in `_encoder_solve.py:500`, `random_seed=0`); a solve that hits `max_time_in_seconds` (`model.py:435`, `_encoder_solve.py:498`) terminates non-deterministically across machines/load. The scoped repair solves in recent commits ran up to 4×180s rounds — a full-board from-scratch placement solve is unmeasured here but has no reason to be cheaper, and nothing in the repo runs it as a single automatable step today.

## 2. What should trigger it?

Two different things are being asked to trigger, and they have different costs:

- **Netlist + route + DRC** (deterministic today, per §1) is comparatively cheap: `make netlist` is cache-hit-fast in CI already; `make route`'s cost is unmeasured here (not run, per this task's constraints) but is bounded by a single SAT solve over a fixed placement; `make drc`'s honest cost is 120 `kicad-cli` invocations if held to the repo's own reproducibility bar (§1), each individually bounded by the 60s subprocess timeout in `_drc_api.py:339` but not measured here at the 120-run level.
- **Placement** is the expensive, judgment-heavy part (§1) and has no single-command trigger today.

Weighed against capacity: `.github/workflows/required-checks.yml:19`, `codeql.yml:20`, and `literal-removal-advisory.yml:11` all independently record the same measurement — "account concurrency ceiling of ~24 jobs" against "a single push already requests ~40" — and `python-tests.yml:684-685` states the 2026-08-03 measurement directly: 79% of that workflow's job-time was setup, merged from three jobs specifically to reclaim capacity. Adding a new per-push job that touches `pcb/**` or `packages/temper-placer/**` (paths that change multiple times a day per the git log in this section) competes for exactly the pool the WASM plan's D3 says is the reason Workers were chosen at all (`docs/plans/2026-08-03-002-...md:42`).

Recommendation on cadence: **on-demand and nightly for the deterministic subset (netlist/route/DRC-as-artifact), never per-push for placement.** A per-push trigger scoped narrowly to the kernels the tier actually consumes — `packages/temper-drc-rs/**`, `temper-geometry`, and `temper_placer/router_v6/**` — is plausible once §1's route/DRC costs are actually measured (not done here); a repo-wide `pcb/**` or `packages/temper-placer/**` trigger is not, given the same paths already drive 31 `make netlist` invocations across workflows (measured by the task's own count) without headroom for a new recurring native job.

## 3. What are the failure modes, and how is a bad regeneration prevented from landing?

Four existing mechanisms, and where each one does and doesn't reach:

- **`power_pcb_dataset/drc_ceiling.json` ratchet.** `scripts/check_drc_ceiling_approval.py` diffs the *committed ceiling file* between HEAD and the merge-base and requires a `Ceiling-Approval:` trailer on any PR commit if any category rose (lines 26-38 of the script's docstring, confirmed by reading `run_gate()` at lines 142-225). **This only fires on a diff to the ceiling file itself** — it does not independently re-run DRC. A regenerated board that legitimately differs would need its ceiling re-measured and committed in the same change (`AGENTS.md:45-97` states this is mandatory, "not a follow-up"), or this gate has nothing to compare and silently passes (`run_gate()` line 191-194: a ceiling file absent at the merge-base is treated as `PASS: ... nothing to ratchet against`).
- **The trailer itself is currently unchecked content.** `docs/plans/2026-08-02-023-feat-drc-ceiling-monotone-contract-plan.md:24-28` (readiness: `implementation-ready`, not yet built) states plainly: "'Ceiling-Approval:' is a free-text commit trailer; any commit containing the string passes the approval gate." A raise needs no attributed cause and no measurement to pass today — that plan exists specifically to close this gap by requiring "an attributed cause... and a fresh measured-live provenance record satisfying the 120-sample all-track-errors contract" as *checked* artifacts, not review convention. **An automated regeneration pipeline that writes its own `Ceiling-Approval:` trailer would pass the gate as written today with no verification that a real re-measurement backs it** — this is the sharpest risk in this section.
- **48 committed goldens (`power_pcb_dataset/goldens/**`) + `golden-check.yml`.** This workflow runs `uv run temper-placer regression` in a container with `kicad-cli` preinstalled (`.github/workflows/golden-check.yml:19-59`) on any PR touching `packages/temper-placer/src/temper_placer/**`, `power_pcb_dataset/goldens/**`, or `pcb/**`. It catches regressions against baselines it has — but a board with **no** baseline is reported `SKIP` and excluded from the failure count (comment at lines 84-88, citing `corpus_runner.py:109,238`); the workflow's own comment names `bitaxe_ultra` as a board that "has had no baseline since it was added and nothing surfaced that." A newly regenerated production board is exactly the shape of input this gap does not catch by construction.
- **No branch protection today.** `AGENTS.md:90-92` states plainly (verified by the maintainer via `gh api .../branches/main/protection` → `404`): "main currently has no branch-protection required status checks... a red 'Provenance & Anti-Vacuity Gates' run does not block the merge button." Every mechanism above is a signal a reviewer can see, not a hard gate a bot-authored PR is mechanically stopped by. `AGENTS.md`'s own stated defense is procedural — "landing the re-measurement inside the same commit... there is no red window to begin with" — which assumes a human wrote the commit.

**Net finding:** the repo's gates are well-built for a *human* re-measuring after a *deliberate* change (which is what every recent `pcb/temper.kicad_pcb` commit is). They are not yet hardened against an *automated* writer producing a plausible-looking `Ceiling-Approval:` trailer with no real measurement behind it, and `docs/plans/2026-08-02-023-...md` is the (currently unbuilt) plan that closes exactly that gap. Automated board regeneration should not be built ahead of that plan landing, or should never itself hold write access to `drc_ceiling.json`'s approval trailer.

## 4. Where does the regenerated board live?

Two options, not one, once §1's finding is taken seriously — there are two candidate regeneration classes, and they don't need the same answer:

- **Deterministic subset (netlist/route/DRC over the *current, committed* placement):** Best produced as a **CI artifact, not committed.** `pcb/temper.kicad_pcb` is a 1,032,079-byte text (S-expression) file (measured via `ls -la`, `git log` shows it at 999 KB-ish historically, growing). Committing a machine-regenerated copy on every trigger would churn a ~1MB file at a cadence disconnected from the human review that currently accompanies every change to it (`de59c0458` shows 411 changed lines for one relay swap plus a 60-line ceiling update, all hand-authored and hand-attributed). Content-hashing the artifact instead (R6 in the WASM plan already requires this: "Board and netlist inputs are addressed by content hash, so every finding names the exact artifact it came from," `docs/plans/2026-08-03-002-...md:61`) gets the tier a stable, comparable, git-independent input without adding commits.
- **Placement (the part that actually changes when the harness changes):** stays exactly as it is today — a human-gated, evidence-documented, PR-committed change (per §1/§3). Nothing here should change that path; it is the one part of "regeneration" this repo has already proven needs judgment (Run A vs. Run B selection in `de59c0458`'s own commit body) rather than a cron job.

## 5. Recommendation

**Recommended: narrow-scope CI-artifact regeneration of the deterministic subset only (netlist → route → DRC, run against the currently-committed placement), triggered nightly plus on-demand, never committed and never touching `drc_ceiling.json`; placement stays entirely human-gated as it is today.**

What this buys R3: the WASM tier gets a real, changing input whenever the router/DRC-relevant kernels change, satisfying the plan's stated worry ("a single sweep of a single artifact answers a question that expires," `docs/plans/2026-08-03-002-...md:34`) for the part of the harness that is actually automatable and actually proven deterministic (§1).

What it honestly costs:
- It does **not** satisfy R3's literal text ("input that changes when the harness changes") for the placement harness, which is the harness component that has produced every recent board change. That gap is real and this proposal does not close it — closing it safely would mean automating a process the repo currently treats as requiring human candidate selection (§1), which is a materially larger and riskier undertaking than R3's phrasing suggests. Phase 0 should record this as a scope narrowing, not a silent success.
- It adds a recurring native (non-WASM) CI job — `kicad-cli` cannot run on Workers (already out of scope per the WASM plan), so this producer runs in GitHub Actions or an equivalent native runner, consuming the same constrained pool the WASM tier exists to avoid. Nightly-plus-on-demand, not per-push, is the mitigation; the actual per-run cost (route + a real 120-sample DRC pass) is unmeasured in this investigation and should be Phase 0's first task before committing to a cadence.
- It requires `docs/plans/2026-08-02-023-feat-drc-ceiling-monotone-contract-plan.md` to land, or an equivalent hard rule that automated writers cannot author `Ceiling-Approval:` trailers, before this producer's output is ever allowed to influence the committed ceiling — otherwise §3's sharpest gap (a free-text trailer with no verification) is directly exploitable by the very automation this proposal builds.
- Golden-check's `SKIP`-on-missing-baseline gap (§3) means a regenerated board with no golden entry would not be caught by that gate either; this proposal doesn't fix that, it just doesn't make it worse (the artifact is never committed, so it never enters a PR that golden-check would run against).

**What would change this recommendation:**
- If §1's route/DRC timing, once actually measured (not done here, per this task's constraint), turns out to be small enough (low minutes) that per-push on the narrow kernel paths is affordable within the ~24-job ceiling without starving PR CI — the trigger could tighten from nightly to per-push on `temper-drc-rs`/`temper-geometry`/`router_v6` changes specifically.
- If `docs/plans/2026-08-02-023-...md` lands and the ceiling-approval gate becomes a genuinely machine-checked contract (attributed cause + real measurement, not substring match) — automated placement regeneration becomes a smaller step, because the gate that currently depends on human honesty would instead depend on a verifiable measurement artifact this pipeline could actually produce.
- If a full from-scratch CP-SAT placement solve is measured to complete well inside `max_time_in_seconds` on the production board size (not the scoped multi-round repairs seen in recent commits) — that would undercut §1's central objection (placement solves are the part proven non-deterministic under timeout, `docs/evidence/2026-08-01-ortools-cpsat-spike.md:179-183`) and placement automation would move from "not recommended" to "worth a Phase 0 spike."
