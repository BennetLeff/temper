# Custom Design Rules for Temper Induction Heater
# IEC 60335-1 / IEC 60664-1 compliant
#
# NOTE: This board carries NO qualified conformal coating.
# No coating process exists in the BOM or assembly, and IEC 60664-3 cl. 4.3
# requires full-path coverage for any Pollution Degree 1 credit -- measured,
# 100.0% of every declared isolator's shortest HV<->PELV path lies under its
# own component body and cannot be shown to be coated. This file therefore
# enforces FAIL-CLOSED, uncoated clearance figures throughout. See
# docs/evidence/2026-07-28-conformal-coating-pd1.md.
#
# CREEPAGE IS ENFORCED HERE (2026-07-28): kicad-cli 10.0.4 supports a real
# `creepage` constraint (confirmed against kicad-source-mirror @ 10.0.4 and
# empirically -- see docs/evidence/2026-07-28-drc-creepage-constraint.md). RULES
# 2 and 4 below enforce 12.6mm reinforced creepage across the
# AC-Mains/HighVoltage <-> everything-else boundary, in addition to their
# existing clearance figures. The enforced figure is PD3 (12.6mm) -- the
# as-built, decision-documented bar (docs/evidence/2026-08-15-pd2-pd3-data-
# driven-decision.md: the board is forced-air vented with no sealed
# compartment, so PD3 governs per IEC 60335-2-6 cl. 29.2 Addition). PD2
# (8.0mm) is retained as the fallback should the compartment ever be built;
# see the source comment on HV_CREEPAGE_ENFORCED_MM for the
# selection rule and
# `scripts/check_isolation_keepout.py` remains the
# other, independent creepage enforcement point on this board (a conservative
# straight-line-corridor sufficient bound, not a surface-path measure); this
# generator's new rules are the fab-authoritative KiCad DRC path. The keepout
# gate's own MIN_BARRIER_WIDTH_MM is ALSO 12.6mm/PD3 (fixed alongside this
# file's own PD3 switch, PR #1229, same day as the text above first went in;
# this comment used to say 'still PD2-pinned, a separate follow-up' -- that
# was true only briefly and is corrected here, 2026-08-17, to match the
# already-correct statement earlier in this file, at HV_CREEPAGE_ENFORCED_MM's
# own comment). Both enforcement points emit/enforce 12.6mm. See
# docs/evidence/2026-07-28-creepage-determination-brainstorm.md for the full
# clause-cited derivation.
#
# TO-247 IGBT packages have a 1.95mm edge-to-edge internal pin gap (see RULE
# 5 below); this is a package-geometry fact, not something this script or a
# coating can fix. Expect this rule to now flag those packages -- that is
# the correct, honest result of removing the prior relaxation.
#
# Generated by scripts/generate_kicad_dru.py -- do not edit by hand.

# ==================================================================
# RULE 1: Allow reduced clearance within same footprint
# This handles TO-247, SOT-23, QFN packages where pad pitch < net class clearance
#
# CONDITION FIX (2026-07-28, redo): A.Footprint == B.Footprint never binds -- "Footprint" is not a property KiCad's PROPERTY_MANAGER
# registers on Pad or Footprint (confirmed against pcbnew/pad.cpp and pcbnew/footprint.cpp at kicad-cli 10.0.4/10.0.5), so this rule
# silently matched zero pad pairs, on the fixture AND on the real board. Replaced the same-footprint-instance test with
# A.Reference == B.Reference, the same construction already confirmed to bind for Rules 5/7 (see
# docs/evidence/2026-07-28-drc-courtyard-condition-fix.md) and directly measured against pcb/temper.kicad_pcb to produce 214
# violations as a lone condition at a 999mm threshold (see docs/evidence/2026-07-28-drc-rule1-netclass-redo.md).
#
# CROSS-DOMAIN GUARD (new): the bare same-footprint test is too broad on its own -- several declared isolators in
# elec/domain_manifest.yaml (the gate driver, the aux supply, the Y-cap, the relays) have HV-side and SELV-side pins on the SAME
# footprint instance, and this rule must never grant THOSE pin pairs a manufacturability allowance meant for a single package's
# own tight pin pitch. KiCad's rule language has no direct notion of "safety domain" -- domain membership lives in
# elec/domain_manifest.yaml, which a static per-pad kicad-cli rule cannot reference. A.NetClass == B.NetClass is the finest dynamic
# proxy KiCad actually offers: NetClass, unlike Footprint, IS a specially-handled property that resolves correctly (measured:
# 499 violations as a lone condition at 999mm -- see the evidence doc). Net class is not a perfect stand-in for safety domain --
# it is a NECESSARY but not SUFFICIENT proxy, and the evidence doc documents one measured real-board counterexample (U7, the
# UCC21550 gate driver: its GateDrive netclass spans both the primary-side PWM input pins and the secondary-side gate-output
# pins across its own reinforced-isolation barrier) where same-NetClass does not imply same-domain. Reported, not fixed here --
# fixing it means re-partitioning the GateDrive net class itself, which is a design_rules.py/elec modeling decision out of this
# generator's scope, not a DRC-rule-syntax defect. Still a strict improvement over the previous always-dead condition and over a
# hardcoded literal-net-name exclusion (which reproduces the exact failure mode -- an unnoticed net rename orphaning the rule -- that
# produced the +340V_BUS defect this task is named after).
# ==================================================================
(rule "Same footprint pads"
   (condition "A.Reference == B.Reference && A.NetClass == B.NetClass")
   (constraint clearance (min 0.1mm))
)

# ==================================================================
# RULE 1a: Fine-pitch IC pads (QFN, BGA with 0.4mm pitch)
# Same condition-fix and same cross-domain guard as RULE 1 above -- see that rule's comment.
#
# SECOND CONDITION FIX (2026-07-28, redo): A.Attribute is ALSO not a registered KiCad property -- confirmed against pcbnew/pad.cpp at
# kicad-cli 10.0.4/10.0.5, which registers this pad field under the display name "Pad Type" (PROPERTY_ENUM<PAD, PAD_ATTRIB>), not
# "Attribute". KiCad's rule compiler looks up properties by exact display name (underscores in the rule field become spaces before
# the lookup), so A.Attribute resolved to nothing and this half of the condition never bound either -- a third, independent instance
# of the same undefined-property failure class as A.Footprint (see docs/evidence/2026-07-28-drc-rule1-netclass-redo.md). Replaced
# with A.Pad_Type == 'SMD' (measured to bind: 483 matches as a lone condition at a 999mm threshold on the real board, vs. 0 for
# A.Attribute == 'SMD').
# ==================================================================
(rule "Fine pitch IC pads"
   (condition "A.Type == 'Pad' && A.Pad_Type == 'SMD' && B.Type == 'Pad' && B.Pad_Type == 'SMD' && A.Reference == B.Reference && A.NetClass == B.NetClass")
   (constraint clearance (min 0.1mm))
)

# ==================================================================
# RULE 5a: THE HV<->HV FUNCTIONAL CREEPAGE RULE (NEW 2026-08-12). This is the constraint this whole class carve-out exists to carry.
#
# Every other creepage constraint in this file (RULES 2, 4, 4b, 4c) requires one side to be non-HV -- they dimension the reinforced
# barrier to LV/SELV. This rule is the first one in this repository for which BOTH sides are HV. Before it, the highest-voltage pair
# on the board -- the resonant tank's cap<->coil junction against the DC bus rails, 923.7 V peak / 570.5 Vrms measured -- was checked
# against no creepage requirement whatsoever. See docs/evidence/2026-08-12-hv-clearance-adequacy.md sec 3.2 for the
# rule-inventory and empirical proof of that gap, and docs/evidence/2026-08-12-hv-hv-creepage-determination.md for the
# Table 18 derivation of the 6.3mm figure (see HV_TANK_CREEPAGE_PD2_MM's comment at the top of this script).
#
# SCOPE. B is restricted to HighVoltage and HighVoltageTank itself: those are exactly the classes carrying the nets the 570.5 Vrms
# working voltage was MEASURED against (+170V_BUS, DC_BUS_RTN, SW_NODE). The pairs to LV/Default, including the unclassed PWR_RTN,
# are covered by RULE 4c at the stricter 8.0mm and are not repeated here.
#
# ONE PAIR IS OVER-CONSTRAINED BY ONE TABLE ROW, DELIBERATELY. tank.c_tank1-p2 <-> SW_NODE (the voltage ACROSS the tank caps)
# measures 411.5 Vrms, which is Table 18 band v (>400-500 V) = 4.0mm at PD2, not band vi's 6.3mm. Splitting it out would need a
# NetName-keyed override whose rule-precedence behaviour this repo has not established; the measured cost of NOT splitting it is zero,
# because the only components carrying both nets are C25/C26/C27, whose pads sit 40mm apart. Recorded so the conservatism is visible
# rather than silently baked in.
# HighVoltageSignal INCLUDED on B (2026-08-13, docs/evidence/2026-08-13-netclass-current-scoping.md): the RULE 4d exclusion above means a (HighVoltageTank, HighVoltageSignal) pair -- e.g. tank.c_tank1-p2 vs. a same-domain bleed/signal tap -- no longer matches "HighVoltageTank to LV", so without this inclusion it would get ZERO creepage protection against the highest-voltage node on the board (570.5 Vrms). This rule is what supplies it.
# ==================================================================
(rule "HighVoltageTank functional creepage"
   (condition "A.NetClass == 'HighVoltageTank' && (B.NetClass == 'HighVoltage' || B.NetClass == 'HighVoltageTank' || B.NetClass == 'HighVoltageSignal')")
   (constraint creepage (min 10.0mm))
)

# RULE 5: High Voltage internal - same footprint
# TO-247 IGBTs have 5.45mm pin pitch (1.95mm edge-to-edge)
#
# FAIL-CLOSED: no conformal coating is qualified on this board, so no
# coating-based relaxation is granted here. This constraint is the
# uncoated reinforced clearance requirement -- IEC 60335-1 cl. 29.1: 1500V
# rated impulse voltage (120V nominal, OVC II) -> Table 16 basic 0.5mm ->
# cl. 29.1.3 next-higher-step reinforced 1.5mm, + cl. 29.1's +0.5mm
# soldered-construction adder (this is a soldered PCB) = 2.0mm. See
# docs/evidence/2026-07-28-conformal-coating-pd1.md sec 3.
#
# TO-247's 1.95mm edge-to-edge gap is BELOW this requirement. That is a real
# violation this rule is now expected to report, not a bug in this rule --
# a coating was never a valid fix for it (see docs/evidence/2026-07-28-
# conformal-coating-pd1.md sec 4, TO-247/SOIC-16W case). Resolving it needs
# a BOM/footprint/placement change, none of which this script performs.
#
# CONDITION FIX (2026-07-28): the same-footprint test used to be A.insideCourtyard(B.Reference), which does not match anything in
# kicad-cli 10.0.4/10.0.5 -- intersectsCourtyard()'s argument is matched against a footprint reference/wildcard string, but the
# dynamic B.Reference form (as opposed to a literal string) never binds, so this rule silently matched zero pad pairs. Replaced
# with A.Reference == B.Reference, a direct property-equality test confirmed (kicad-cli 10.0.4, isolated fixture) to fire correctly:
# see docs/evidence/2026-07-28-drc-courtyard-condition-fix.md.
# ==================================================================
# HighVoltageTank INCLUDED on both sides (2026-08-12): the three tank capacitors C25/C26/C27 each have pad 1 on SW_NODE (HighVoltage) and
# pad 2 on tank.c_tank1-p2 (HighVoltageTank), so after the carve-out this rule -- and the generic 'Same footprint pads' rule, which
# requires A.NetClass == B.NetClass -- would BOTH stop matching that intra-package pair. Widening the condition keeps the intent

# ==================================================================
(rule "HV internal same footprint"
   (condition "(A.NetClass == 'HighVoltage' || A.NetClass == 'HighVoltageTank') && (B.NetClass == 'HighVoltage' || B.NetClass == 'HighVoltageTank') && A.Reference == B.Reference")

)

   (condition "A.NetClass == 'HighVoltage' && B.NetClass != 'HighVoltage' && B.NetClass != 'HighVoltageTank' && B.NetClass != 'HighVoltageSignal' && B.NetClass != 'ACMains' && B.NetClass != 'GateDriveHV' && B.NetClass != 'HighVoltageIsolated'")
   (constraint clearance (min 2.0mm))
   (constraint creepage (min 12.6mm))
)

# ==================================================================
# RULE 4c: HighVoltageTank to LV -- an exact clone of RULE 4 above, for the class the tank node was carved out into.
# WITHOUT THIS RULE the carve-out would be a SAFETY REGRESSION: while tank.c_tank1-p2 was in HighVoltage it received RULE 4's 2.0mm
# clearance and 8.0mm reinforced creepage against every LV/SELV net, and moving it to a new class silently drops that coverage. The
# figures here are RULE 4's own, carried over unchanged -- this rule preserves an existing requirement, it does not introduce one.
# Note PWR_RTN, which has no netclass at all and so lands in Default (a known gap: docs/evidence/2026-08-12-hv-clearance-adequacy.md
# sec 6.3): the tank<->PWR_RTN pair measures 544.6 Vrms, genuinely needs 6.3mm functional, and is charged 8.0mm by this rule because
# Default reads as LV. That is conservative, not wrong, and it is the SAME treatment the pair already got before this change.
# ==================================================================
(rule "HighVoltageTank to LV"
   (condition "A.NetClass == 'HighVoltageTank' && B.NetClass != 'HighVoltageTank' && B.NetClass != 'HighVoltage' && B.NetClass != 'HighVoltageSignal' && B.NetClass != 'ACMains' && B.NetClass != 'GateDriveHV' && B.NetClass != 'HighVoltageIsolated'")
   (constraint clearance (min 2.0mm))
   (constraint creepage (min 12.6mm))
)

# ==================================================================
# RULE 4d: HighVoltageSignal to LV -- an exact clone of RULE 4/4c above, for the mA-scale current-tier carve-out of HighVoltage (docs/evidence/2026-08-13-netclass-current-scoping.md).
# WITHOUT THIS RULE the carve-out would be a SAFETY REGRESSION, the same shape RULE 4c's own comment records: while e.g. 'a' (U3's
# ZCD divider tap/opto-anode net -- one pin of a real isolator on this board) was HighVoltage, it received 2.0mm clearance and
# 8.0mm reinforced creepage against every LV/SELV net (measured: U3 pin 'a' vs. U3 pin 'gnd', same footprint, real board). Moving
# it to this class must not silently drop that coverage.
# ==================================================================
(rule "HighVoltageSignal to LV"
   (condition "A.NetClass == 'HighVoltageSignal' && B.NetClass != 'HighVoltageSignal' && B.NetClass != 'HighVoltage' && B.NetClass != 'HighVoltageTank' && B.NetClass != 'ACMains' && B.NetClass != 'GateDriveHV' && B.NetClass != 'HighVoltageIsolated'")
   (constraint clearance (min 2.0mm))
   (constraint creepage (min 12.6mm))
)

# ==================================================================
# RULE 6a/6b: GateDriveHV same side (ACMains, HighVoltageIsolated)
#
# GAP CLOSED (2026-08-11): GATE_HS/GATE_LS (netclass GateDriveHV, pcb/temper.kicad_pro netclass_patterns 'GATE_*') are the UCC21550
# gate driver's own secondary-side gate outputs -- elec/domain_manifest.yaml lines ~111-116 declare them members of
# the SAME HV domain as ac_l/+170V_BUS/SW_NODE/hb.gate_hs.driver-p1-1/-p2 (float WITH the switch node, one gate resistor
# downstream), and packages/temper-placer/configs/netclass_rules.yaml's own GateDriveHV class comment says the same thing in so
# many words. Before RULE 2/4/4b's 2026-08-11 GateDriveHV exclusions above, none of the three existing 'to LV' rules
# treated GateDriveHV as same-side, so ACMains/HighVoltage/HighVoltageIsolated vs. GateDriveHV pairs were charged the full
# 8.0mm reinforced creepage figure meant for a genuine mains/HV <-> SELV boundary -- a false positive against the project's own
# domain model, not a real shock-hazard pair (both sides float at the same potential relative to SW_NODE). Measured directly
# against pcb/temper.kicad_pcb (kicad-cli 10.0.5): 7 of the 186 creepage violations name a GATE_HS/GATE_LS net opposite an
# ACMains/HighVoltage/HighVoltageIsolated net -- see docs/evidence/2026-08-11-creepage-gatedrivehv-false-positive.md.
#
# This closes the gap the same way RULE 3 ("AC Mains to HV") and RULE 4a ("HighVoltageIsolated same side") already closed
# it for their own same-side pairs: GateDriveHV vs. ACMains and vs. HighVoltageIsolated now get RULE 6's own existing 0.5mm
# functional figure (the same number already accepted for GateDriveHV vs. HighVoltage above -- not a new value) instead of
# falling through to the reinforced boundary. GateDriveSELV is deliberately NOT given an equivalent pair here -- it is the real
# SELV/primary-side half of the same gate-driver split (elec/domain_manifest.yaml keeps PWM_HS/PWM_LS out of every HV domain
# list) and still needs the full reinforced boundary against ACMains/HighVoltage/HighVoltageIsolated -- RULE 2/4/4b apply to
# it unchanged, correctly.
# ==================================================================
(rule "GateDriveHV to ACMains"
   (condition "A.NetClass == 'GateDriveHV' && B.NetClass == 'ACMains'")
   (constraint clearance (min 0.5mm))
)

(rule "GateDriveHV to HighVoltageIsolated"
   (condition "A.NetClass == 'GateDriveHV' && B.NetClass == 'HighVoltageIsolated'")
   (constraint clearance (min 0.5mm))
)
