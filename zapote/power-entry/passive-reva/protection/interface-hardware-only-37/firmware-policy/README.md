# ESP-only source policy prototype

This portable C model explores source-side sequencing for the ESP-only Rev37
candidate. It is not linked to ESP-IDF firmware and is not a schematic,
hardware integration, or safety claim.

## Policy modeled

At boot/reset, the source PERMIT request, ARM, and HOT_REARM requests are low.
The reset-event call also withholds WDI, even if both readbacks are low and a
fresh local cycle event is present in that call.
WDI is withheld until both physical source `PERMIT_TX` and HOT-side PERMIT
readbacks are observed low. If the source watchdog has timed out, WDI may then
recover it only from a current `fresh_local_cycle_event` while raw HOT health
is good. This input represents one completed synchronous local control/safety
cycle; it must not be generated by an independent periodic timer, DMA engine,
interrupt, or queued event. A new start still requires button release, the
source-session reset pulse, then a fresh button press after watchdog-good.

The fresh press requests source PERMIT high first. The policy waits for both
physical readbacks high and then requires `hot_permit_delay_elapsed` to be
observed false followed by true in that transaction. It then emits one
HOT_REARM-high request; ARM is emitted as a one-step request on the next policy
call and is low again in ACTIVE. WDI can continue during the blanking interval
only on fresh local control/safety cycle events, with both permit readbacks,
raw health, and watchdog-good valid. Every output is returned by this same
synchronous step function. No command or heartbeat is queued or emitted by an
autonomous pulse path.

After a fault, the policy requests source PERMIT low and waits until both the
local source readback and separate HOT-side readback are low and the button is
released. It then requests a one-step active-low `SOURCE_SESSION_RESET_N`
clear for the retained source `PERMIT_SEEN` state. Only a later press can
request source PERMIT again. The pulse output must be released before the next
policy call and must meet the HCS74 minimum low pulse width (11 ns). Its GPIO
driver must also prevent a CPU-only reset from retaining this active-low clear
through an active session.

Loss of raw HOT health, watchdog-good after authorization starts, or either
permit readback after it has risen returns the policy to lockout. During the
initial `WAIT_PERMIT_HIGH` transition, low readbacks are expected until they
first rise. A missing HOT-side readback suppresses WDI in that phase, allowing
the independent source watchdog to time out and clear the source latch.

## Timing and observability limits

`hot_health_raw` represents raw HOT rails/fault status. That signal alone does
**not** report an open HOT-side PERMIT wire. The policy therefore has a
separate `hot_permit_readback` input. If the actual design has no independent,
electrically suitable HOT-side readback, the wire break remains invisible to
firmware while raw health and source Q1 remain high. Firmware polling also
cannot guarantee immediate fault clearing: the circuit needs direct hardware
clear or a proven watchdog response bound, including preemption from sensor
sampling through the GPIO writes.

`hot_permit_delay_elapsed` is a **software timing qualification**, not a
TPS3890 output or physical timer readback. The firmware driver must start a
monotonic wait only after both permit readbacks are high, use a duration at
least as long as the HOT supervisor's worst-case CT delay, and cancel/restart
it on either readback falling or any health loss. It must provide a fresh
not-done observation before completion; if that sample is missed, the policy
fails off and waits indefinitely. The host model does not prove the CT bounds,
monotonic timer accuracy, scheduling latency, or correct timer cancellation.

The one-step ARM, HOT_REARM, and source-session-reset outputs still require a
real GPIO driver with bounded write ordering and pulse widths. A policy call
does not make sampling and subsequent writes atomic. In particular, a fault
that arrives after sampling but before writes can leave stale output briefly
asserted unless hardware clears it or a separately bounded response handles
the race. The Rev37 circuit and this policy have not been joined or measured.

## Host tests

The 11 tests cover reset with a held button, no WDI on the reset-event call,
low-readback and session-reset
sequencing, new button intent, watchdog recovery after physical permit-low
feedback, WDI through a 250 ms HOT blanking wait, fresh timer qualification,
missing HOT readback behavior, fault aborts, stalled-step WDI withholding,
one-step ARM/HOT_REARM behavior, and a counterexample where an independent WDI
task keeps a stale rearm path alive.

Run them with:

```sh
cc -std=c11 -Wall -Wextra -Werror -pedantic \
  test_source_policy.c source_policy.c -o /tmp/temper37-policy-test
/tmp/temper37-policy-test
```

Passing these host tests establishes only the modeled software policy. It does
not establish that the ESP-only circuit is safe to build.
